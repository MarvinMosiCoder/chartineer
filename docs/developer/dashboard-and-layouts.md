# Dashboard and Layouts

## Purpose

Authenticated pages share a role-aware shell. Traders receive compact market navigation; superadmins receive administration navigation and dashboard statistics.

| File | Responsibility |
|---|---|
| `DashboardController.php` | Build dashboard Inertia props |
| `Pages/Dashboard/Dashboard.jsx` | Role-specific dashboard/workspace |
| `Context/WatchlistContext.jsx` | Watchlist state/CRUD/persistence, shared by the sidebar and fullscreen chart tree |
| `Components/Market/WatchlistPanel.jsx` | Watchlist UI, rendered from both `Dashboard.jsx` and `MarketChart.jsx` |
| `Layouts/layout/layout.jsx` | Main authenticated composition |
| `AppNavbar.jsx`, `AdminNavbar.jsx`, `TraderNavbar.jsx` | Header variants |
| `AppSidebar.jsx`, `TraderSidebar.jsx`, `AdminSidebar.jsx` | Navigation variants |
| `AppContent.jsx` | Main content sizing/scrolling |
| `ContentLoader.jsx` | Per-navigation loading overlay, content area only |
| `app.jsx` | Public/auth page layout selection |

## Flow

1. An authenticated route returns an Inertia page.
2. `app.jsx` wraps it with contexts and `Layout`.
3. Layout reads the authenticated privilege/session state.
4. Admin or trader navigation is selected.
5. The page renders inside `AppContent`; navigation actions use Inertia or JSON endpoints.

`GET /dashboard` uses `auth` and `account.active`. `GET /market` is the normal trader workspace.

For superadmins, `/dashboard` includes user health, verified PHP subscription revenue and transaction status, live subscriber access status, customer-support workload, and the five latest subscription and feedback records. Thirty-day values use a rolling window; subscription revenue includes only verified `paid` PHP transactions and uses `paid_at`.

### Subscriber status (Active / Expired / Not yet subscribed)

The "Subscriber status" section (`subscriptionStatusMetrics` prop, `DashboardController::index()`) counts every `adm_users` row into exactly one of three buckets, computed live off `replay_access_ends_at` rather than a stored status column:

- **Active** — `replay_access_ends_at` is set and `>= now()`.
- **Expired** — `replay_access_ends_at` is set and `< now()`.
- **Not yet subscribed** — `replay_access_ends_at` is `null` (never completed a paid subscription; trial-only users still land here since trial and paid access are tracked separately).

This mirrors the exact active/expired computation `ReplayAccessController::userPage()`/`status()` already use for a single user's own subscription page (see [Subscriptions, trials, and PayMongo](subscriptions-trials-and-paymongo.md)) — there is no separate cron job or migration keeping these in sync. A user renewing (`ReplayAccessController::adminRestoreAccess`, reachable from the `/admin/subscriptions` Payments page) pushes `replay_access_ends_at` into the future, so they fall out of Expired and into Active automatically the next time `/dashboard` loads; an access period lapsing naturally does the reverse. Like the existing `userMetrics.total`/`active` counts on this same dashboard, this does **not** exclude superadmin/staff accounts from the tally.

`GET /admin/workspace` is superadmin-only and reuses the complete trader workspace in an explicit workspace mode. Its **Workspace Chart** link is an `adm_menuses` record with a superadmin privilege mapping, so it is loaded into the main `MENU` sidebar exactly like Market and PNL rather than being hard-coded or placed in the legacy `ADMIN MENU` section. It keeps the administration overview at `/dashboard` while giving administrators access to watchlists, chart controls, Replay, drawings, alerts, and simulated orders.

### Trade insights widget

`Components/Market/TradeInsightsWidget.jsx` renders at the top of the trader workspace branch (`workspaceMode || !isSuperAdmin`, so it also shows on the superadmin's `/admin/workspace`), directly above the chart container — there is no standalone `WatchlistPanel` between them any more (see below). It fetches `GET /market-backtest/report/insights` on mount and, if the account is eligible (≥10 closed trades) and at least one coaching heuristic fired, shows only the single highest-severity tip as a one-line, dismissible teaser linking to `/trade-report` (see [Trade reports and journals](trade-reports-and-journals.md)). It renders nothing while ineligible, tip-free, or dismissed; dismissal is local component state, not persisted, so the tip reappears on the next visit if it still fires.

### Watchlists

Named groups of saved-market symbol keys (`exchange:category:SYMBOL`). State/CRUD/persistence live in `Context/WatchlistContext.jsx` (`WatchlistProvider` + `useWatchlist()`), not in `Dashboard.jsx` — the UI itself is `Components/Market/WatchlistPanel.jsx`, a presentational component that pulls everything from `useWatchlist()`.

**`Dashboard.jsx`'s embedded workspace sidebar instance of `WatchlistPanel` was removed** (it used to render as a large standalone block above the chart, showing `setActiveSymbol`/`chartKey`-driven remount on selection). The header dropdown described below — previously fullscreen-only — is now the *only* way to reach watchlists from the chart, in both fullscreen and normal (embedded) mode: it toggles from a "Watchlists" button in `MarketChart/FullscreenChartHeader.jsx` (the header bar shown at the top of the chart in every mode), no longer gated behind `isFullscreen`. This freed the vertical space the standalone block used to occupy and made the two modes visually consistent — a normal-mode user now sees the same compact header (symbol picker, timeframe, Watchlists, Enter Position, fullscreen toggle) fullscreen always had. Same underlying `WatchlistPanel` component either way (`compact` styling only), so no CRUD feature (add/edit/delete watchlist, add/remove symbol) was lost. `Dashboard.jsx` still wraps the whole workspace branch in `<WatchlistProvider userId={...}>`, so the header dropdown and `ChartHeader.jsx`'s own add-to-watchlist picker (see [Trading chart](trading-chart.md)) share one source of truth — a symbol added from the chart's own search shows up in the dropdown too, and vice versa, with no manual sync code.

`FullscreenChartHeader.jsx` gets everything the dropdown needs (`symbol`/`exchange`/`marketCategory`/`onSymbolChange`) from the `chartHeaderProps` bundle it already receives for `ChartHeader` — no new props were added. Selecting a chip there calls `chartHeaderProps.onSymbolChange`, the chart's own internal symbol-switch handler, so it changes the chart in place without a remount — this is now the *only* symbol-selection path from a watchlist (the old `Dashboard.jsx`-level `setActiveSymbol`/`chartKey` remount path only fires from the unrelated top navbar's global symbol search now, not from watchlist selection).

**Enter Position** (the order-entry panel) followed the same pattern: `FullscreenChartHeader.jsx`'s "Enter Position" button (`Wallet` icon, shows cash balance) was also fullscreen-only (`showEntryWallet={isFullscreen}`) and is now always shown. `ReplayPanel.jsx`'s left drawing-tool rail used to have its own separate, redundant "Enter Position" wallet icon in normal (`groupedWorkspaceRail`) mode, driven by a local `toggleGroup('backtest')` call independent of the header button's state — removed, since fullscreen's rail never had one either (one trigger, not two). The `fullscreenEntryPanelOpen` prop that drives the panel's `activeGroup` now activates in both `fullscreenDrawingOnly` (fullscreen) and `groupedWorkspaceRail` (normal) modes — previously it only worked in fullscreen, so the header button would have been a dead click in normal mode without this.

**Why Context, not props**: the panel needs the full CRUD surface (create/rename/delete list, add/remove symbol, expand state, saved-symbols + metadata for logos/prices, modal state) in both call sites. Threading that through `MarketChart.jsx`'s already-large prop list and its `chartHeaderProps` bundle would make an already sprawling file worse. Follow this same pattern (Context, not deeper prop-threading) for anything else that needs to reach both the Dashboard shell and deep inside the chart tree.

Server persistence is unchanged from before: `GET/PUT /market-watchlists` (`MarketWatchlistController`, `market_watchlists` table — one JSON `data` row per user), mirroring `MarketToolSettingController`'s single-JSON-blob-per-user pattern. `localStorage` (`backtradelab-watchlists:{userId}`) is a fast-paint cache, not the source of truth — the server value wins once fetched (`exists: true`), and changes push back with a 500ms debounce once hydrated. A brand-new account has no server row yet, so whatever was in `localStorage` becomes the first server write — the entire migration path, no separate script.

**The create/rename/delete-watchlist modals render via `createPortal(..., document.body)`** inside `WatchlistProvider`, not inline in whichever panel triggered them. This is required, not stylistic: triggering one from the fullscreen-docked panel would otherwise render it as a DOM child of a subtree that's still visually *inside* the `z-[9999]` fullscreen container's stacking context in some cases, or simply be positioned confusingly. The portal always attaches to `document.body`, so the existing `z-[10020]`/`z-[10021]` values (already above fullscreen's `z-[9999]`) display correctly regardless of which panel instance opened them, and only one instance ever renders.

`WatchlistPanel` takes `isFullscreen`, `compact`, `className`, `activeSymbolKey`, and `onSelectSymbol` as props. With the `Dashboard.jsx` embedded instance removed, `FullscreenChartHeader.jsx`'s header-dropdown instance is now the sole renderer, always passing `chartHeaderProps.onSymbolChange` (the chart's own internal symbol-switch handler — switches the symbol in place, no remount) regardless of fullscreen state. The panel's own root `className` prop is unused by this call site, which instead wraps the panel in its own `absolute`-positioned dropdown container, same as `TraderNavbar.jsx`'s Assets flyout. The panel's whole-panel collapse toggle (separate from per-list expand/collapse) is collapsed by default whenever `isFullscreen` is passed — true for both fullscreen and normal mode now, since the dropdown container is space-constrained either way.

Multiple watchlists can be expanded at once within a panel (`expandedWatchlists` is a toggled `Set`, not a single active entry). Symbols within an expanded list render as a vertical, scrollable row list (`max-h-56 overflow-y-auto`), not wrapped chips — matching the row layout `ChartHeader.jsx`'s own symbol search results use (logo left, symbol/exchange center, price/change right, action button trailing), so the two "list of markets" UIs in this app look consistent. Each row shows a coin logo, last price, and 24h % change, fetched via `POST /market-metadata/batch` and the `exchange:category:SYMBOL` (uppercase symbol, lowercase exchange/category) keying convention used by `Pages/Market/Market.jsx`'s `SavedMarket`/`FeaturedMarket` cards — reuse that exact key shape for any new watchlist-adjacent metadata lookup; the logo comes from `fundamentals.logo_url` (CoinMarketCap primary, CoinGecko fallback — see [Market data and symbols](market-data-and-symbols.md)) with a `CandlestickChart` icon fallback, matching Market.jsx's own convention. The "add a saved market" control is `react-select`, not `CustomSelect` (that component assumes an admin-form context — its own label, chevron — that doesn't fit this compact inline control); its options carry logo/price from a second, separate `/market-metadata/batch` call scoped to *all* saved symbols (`savedSymbolsMetadata`), not just symbols already in a watchlist (`watchlistMetadata`).

That `react-select` instance sets `menuPortalTarget={document.body}` plus a `menuPortal` z-index (`10050`, above the fullscreen chart's `z-[9999]` and the watchlist-modal portal's `z-[10020]`/`z-[10021]`) in `watchlistSelectStyles()`. This isn't optional styling — the fullscreen-docked `WatchlistPanel` instance wraps itself in `overflow-hidden` (`WatchlistPanel.jsx`'s outer `isFullscreen` branch), and without the portal, react-select renders its open menu inline as a DOM child of that wrapper, so the menu gets clipped instead of floating over the chart. Keep any new `react-select` (or similar inline-rendering dropdown) usage inside `WatchlistPanel.jsx` or other `overflow-hidden` fullscreen surfaces portaled the same way.

Every option in that same list also carries an always-visible `X` button (previously this only appeared on options already in the watchlist, styled as a remove-from-this-list toggle — that read as confusing since most rows in this "add" list aren't in the watchlist yet, so it was replaced with an unconditional delete). Unlike the watchlist's own item-list `X` (`WatchlistPanel.jsx`'s `items.map(...)` below this select, which only removes membership in *that one* watchlist via `removeSymbolFromWatchlist`), this dropdown's `X` calls `WatchlistContext`'s `deleteSavedSymbol(item)` — it deletes the saved market symbol itself (`DELETE /market-symbols/{id}`), the same destructive action as the trash-can button on the chart header. `deleteSavedSymbol` also prunes the symbol's key out of every watchlist's `items` array (not just this one) and dispatches `backtradelab-symbols-changed`, since a deleted symbol shouldn't linger as a dangling reference anywhere. Both `X`s route through the same `useConfirm()` modal, just with different messages for "remove from this list" vs. "delete entirely" — read the message before wiring up a new one here, they are not interchangeable. The `X`'s `onMouseDown`/`onClick` both call `stopPropagation()` (and `onMouseDown` also `preventDefault()`) — required, not defensive, because `formatOptionLabel`'s markup renders *inside* react-select's own Option wrapper, which has its own click handling for "select this option"; without stopping propagation, clicking the `X` would also fire the select's `onChange` (add-to-watchlist).

**Fixed: deleting a saved symbol from this dropdown's `X` looked like it silently did nothing.** `useConfirm()`'s modal was fixed at `z-[10021]` — below this select's own `menuPortal` (`z-[10050]`, see above). Clicking `X` correctly called `confirm()` and the dialog correctly mounted, but it rendered *underneath* the still-open react-select menu, which was both visually covering it and, being on top, absorbing the click before it could reach the confirm dialog's buttons — so the delete's own confirmation step was unreachable specifically when triggered from inside this still-open dropdown (the watchlist's own item-list `X`, a plain unportaled button with nothing else open over it at that moment, was never affected). `useConfirm.jsx`'s modal is now `z-[10060]`, deliberately above every other portal in the app rather than tuned to any one caller, since the hook is shared across many surfaces that can each have their own popover open when `confirm()` fires.

**Added: a "Remove all" action next to "Add watchlist"** in `WatchlistPanel.jsx`'s header, shown only when `savedSymbols.length > 0`. It confirms (naming the count, and that it clears every watchlist's assignments too) then calls `WatchlistContext`'s `removeAllSavedSymbols()`, which hits a new `DELETE /market-symbols` route (`MarketDataController::destroyAllSymbols()`, scoped to `adm_user_id`) rather than looping `deleteSavedSymbol()` once per row — a client-side loop would fire one request per saved symbol and hit the `market-write` limiter (15/min) before a user with more than 15 saved symbols finished clearing them. One request, one transaction, and the frontend clears `savedSymbols` and every watchlist's `items` array in a single state update instead of pruning them one key at a time.

**Known gap, not fixed here**: `MarketChart.jsx` keeps its own separate `symbols` state fetched independently from `WatchlistContext`'s `savedSymbols` (see the dual-source-of-truth note in [Trading chart](trading-chart.md)). Deleting a saved symbol from this dropdown updates `WatchlistContext` and dispatches `backtradelab-symbols-changed` (which only `TraderNavbar.jsx` listens for), but `MarketChart.jsx`'s own symbol list won't reflect the deletion until it independently refetches. If this divergence causes a real bug, the fix is unifying both onto one source of truth, not adding a third listener.

Reordering watchlists or symbols within one is not implemented — there is no drag/reorder precedent anywhere in this codebase, and adding it would mean changing `data` from an object keyed by name to an order-preserving array. If it's added later, keep the JSON-blob persistence approach; don't introduce a relational per-item table without a concrete reason this simple structure can't satisfy.

**`SidebarContext.jsx`'s `isSidebarOpen` used to default to `true` unconditionally.** On desktop that's correct (the sidebar sits in normal flow via `lg:relative` and pushes content over), but on mobile `TraderSidebar.jsx` renders the same open state as a `fixed`, `z-[100]` panel with no backdrop — so every trader on a phone landed on `/market` (or any authenticated page) with roughly 60% of the screen permanently covered by the nav list, no dimmed scrim to signal it was an overlay, and no way to dismiss it except tapping a nav link (which closes it) or the header hamburger (`TraderNavbar.jsx`'s `Menu` button, `toggleSidebar()` with no argument). `AppSidebar.jsx` (the admin/legacy sidebar) already avoided this via its own `matchMedia('(max-width: 640px)')` mount effect that force-closes/opens on load and on breakpoint change — `TraderSidebar.jsx` had no equivalent. Fixed at the shared context level instead of duplicating that effect: `isSidebarOpen` now lazy-initializes from `window.innerWidth >= 1024` (matching `TraderSidebar.jsx`'s own `lg` breakpoint), and `TraderSidebar.jsx` renders a `lg:hidden` backdrop (`fixed inset-0 top-14 z-[90] bg-black/50`) beneath the `z-[100]` panel that calls `toggleSidebar(false)` on tap — the standard mobile-drawer pattern the admin sidebar was still missing a backdrop for too (a smaller, follow-up gap — admin pages need a superadmin session to verify, so it wasn't changed here; replicate the same backdrop div in `AppSidebar.jsx` if that's fixed later). Test opening the trader sidebar via hamburger on a fresh mobile session (not just after resizing down from desktop, which only `AppSidebar.jsx` handled) whenever touching sidebar state.

**Collapsed-sidebar hover labels now use the shared anchored-portal tooltip** (`Components/Tooltip/AnchoredTooltip.jsx`, see "Header command buttons: icon-only with anchored tooltips" in [Trading chart](trading-chart.md)) instead of the plain browser-native tooltip, or — in the admin/legacy sidebar's case — instead of nothing at all. `TraderSidebar.jsx`'s nav `Link`s and its "Collapse navigation" button previously used a native `title=` attribute (the unstyled OS tooltip); they're now wired with `useAnchoredTooltip`/`AnchoredTooltipPortal` (manual wiring for the `Link`, since it isn't a `<button>`) and `IconTooltipButton` respectively. `Components/Sidebar/SidebarMenuCard.jsx` and `SidebarMenuCardMultiple.jsx` (the admin/legacy `AppSidebar.jsx` tree, shared by both `UserSidebar.jsx` and `AdminSidebar.jsx`) had no hover tooltip at all — when collapsed to the icon-only rail, there was no way to see what an icon meant — so the same pattern was added there too (`placement="right"` for all, matching the sidebar's position on the left edge). `SidebarMenuCardMultiple.jsx`'s expandable parent row isn't a `Link`/`button` either, so its `ref`/hover handlers are wired directly onto the row `<div>`. Child rows inside an expanded submenu aren't included — that submenu only renders while the sidebar is open, so the label is never hidden there.

**`SidebarMenuCard.jsx`'s and `SidebarMenuCardMultiple.jsx`'s icons rendered as bare glyphs with no background**, and `SidebarMenuCardMultiple.jsx`'s child-row indent line (`border-l border-[#2a2e39]`) was hardcoded to the dark-theme color with no light-theme branch — exactly the pattern the "never hardcode a dark-only color" rule below warns about, just not yet fixed at the time that rule was written. Both components now wrap each icon in a rounded chip (`h-7 w-7` on parent rows, `h-5 w-5` on child rows — `bg-slate-100`/`bg-white/5` at rest, a darker/lighter shade on hover, `bg-white/15` when the row is the solid-blue active state) instead of a bare `<i>`, echoing the soft icon-chip treatment the dashboard's own stat tiles already use. The child-row border now branches on `isDark` like the rest of the file, and parent rows moved from `rounded-md` to `rounded-xl` for a softer corner radius. Since both components are shared by `UserSidebar.jsx` and `AdminSidebar.jsx`, this affects the trader "MENU" section identically to the admin "ADMIN MENU" section — there is no separate per-role styling variant to keep in sync.

**`TraderNavbar.jsx`'s notification and Assets dropdowns used `absolute right-0` on a `relative` wrapper scoped to just that one icon button**, not the icon cluster or header. On mobile, the bell and wallet icons sit two-to-four icon-widths left of the header's true right edge (theme toggle, avatar, and logout icons follow them), so `right: 0` resolved against that narrow per-icon wrapper instead of the screen edge — the `w-[min(92vw,380px)]` panel's left edge landed off-screen to the left by roughly a third of its width, with no scrollbar to reach it (CSS doesn't create horizontal scroll for content overflowing past the initial containing block's left edge in an LTR document), so labels like "Notifications"/"Assets" and most row content were simply unreachable. Fixed by moving `relative` from each per-icon `<div>` up to their shared parent (`<div className="ml-2 flex items-center gap-1 border-l pl-2">`, which does span to the header's true right edge on every viewport) — both dropdowns now anchor correctly regardless of which icon opened them. Any new icon-triggered dropdown added to that cluster should anchor the same way rather than adding its own `relative` wrapper.

The admin header keeps two distinct controls below the large-screen breakpoint: the left button toggles the database-driven sidebar and the right button opens the compact core-module menu (now just Overview and Users — see below). The visible legacy operations are Privileges, Announcements, Notifications, Log User Access, and the "Payments" dropdown (children: Transactions, Pricing, Payment Activity). Menu Management, Module Generator, and API Generator remain implemented but are inactive in navigation. See [Roles, privileges, and menus](roles-privileges-menus.md) for how `adm_admin_menuses` drives this section, including the recent repointing of two previously dead-link entries ("System Error Logs", "Module Activity History") at their now-real pages.

`AdminNavbar.jsx`'s top nav and mobile module menu only keep "Overview" and "Users" — Customer Support, Payments, Pricing, Payment Activity, Error Logs, and Settings were removed from there once equivalent entries existed in the sidebar's "ADMIN MENU" section, so the same destination isn't offered from two different nav surfaces with different labels. The admin's profile link there also gained an avatar circle (uploaded photo, system avatar, or initials — same resolution as the other navbars, see [Users, profiles, and deactivation](users-profiles-and-deactivation.md)) instead of being text-only.

**`AdminNavbar.jsx`'s profile link had no way to reach `/change_password`** — `TraderSidebar.jsx` still lists "Change password" as a hardcoded nav item for traders, but when the admin header was rebuilt (replacing the old, now-dead `AppNavbar.jsx`, which *did* have a profile dropdown with a "Change password" entry) that link never got carried over, so a superadmin had no in-app way to reach the change-password flow except the forced first-login redirect (`ForceChangePassword.jsx`, see [Users, profiles, and deactivation](users-profiles-and-deactivation.md)). Fixed by turning the profile `<Link>` into a `showProfileMenu`-toggled dropdown button (same pattern as the existing notifications dropdown in this file) with two entries: "View profile" (`/profile`) and "Change password" (`/change_password`, `ChangePasswordController::getIndex`). No outside-click dismissal was added, matching how the notifications dropdown in this same file already behaves.

**The app name shown next to the logo is now a two-tone "wordmark"** (`Components/SystemSettings/AppNameWordmark.jsx`) instead of plain text — it splits the fetched name at its midpoint (`Math.ceil(length / 2)`, first half inherits the surrounding text color, second half gets `text-[#2dd4bf]`), so "Chartineer" renders as "Chart" + "ineer" the way the brand's own logo does, for any configured name. Used by `AdminNavbar.jsx` and `TraderNavbar.jsx`'s header brand label and `FullscreenChartHeader.jsx`'s chart-header brand label. The five `Auth/*` pages (`AdminLogin.jsx`, `Login.jsx`, `ResetPassword.jsx`, `ResetPasswordEmail.jsx`, `SocialRegistrationConfirm.jsx`) previously hardcoded the literal string `"BacktradeLab"` in their header brand label, logo `alt` text, and (for `Login.jsx`/`AdminLogin.jsx`/`SocialRegistrationConfirm.jsx`) a line of copy — none of them fetched `getAppName()` at all, unlike `getAppLogo()`, which they already called. All five now fetch and display the real configured name (wordmark-styled only in the header brand label spot; the copy/alt-text mentions are plain interpolation). `Public/Home.jsx` and `Public/LegalPage.jsx` (Privacy Policy/Terms of Service) had the exact same gap — hardcoded `"BacktradeLab"` in their own header brand label, logo `alt`, and footer copyright, never calling `getAppName()` despite already calling `getAppLogo()` — fixed the same way. `Public/MentorReview.jsx` had one plain-text mention ("shared by a BacktradeLab trader") with no existing dynamic-value infrastructure at all (no `getAppLogo()`, no state/effects); given it's a single sentence, it got a minimal `useState`/`useEffect` fetch rather than the full wordmark treatment. See [System settings](system-settings.md) for the `/appname` endpoint these all call.

`AdminNavbar.jsx`'s notification bell used to be a plain `Link` straight to `/notifications/view-all-notifications`. Keep both in sync if the notification dropdown's shape changes.

### Content loader

`ContentLoader.jsx` shows the same candlestick-bar animation as the boot splash (see [Architecture](02-project-architecture.md#boot-splash)) but scoped to every Inertia page navigation, not just the first load. It subscribes to `router.on('start'/'finish')` the same way `AppInitializer.jsx` does for NProgress, and runs alongside it, not instead of it — the thin top bar stays for every navigation, this overlay adds a heavier in-content indicator.

It's mounted once in `layout.jsx`, as a sibling of the sidebar-adjacent content column (`<div className="relative flex min-w-0 w-full flex-col overflow-hidden">`), not nested inside the scrollable inner content div. That placement matters: the scrollable inner div grows to the height of whatever page content is currently mounted, which can exceed the viewport, so an overlay centered inside *that* box could render below the visible scroll position. The outer column is bounded by `h-screen` and never scrolls, so `absolute inset-0` there always matches the visible viewport area beside the sidebar and below the fixed navbar — both of which stay visible and interactive-looking during a navigation.

Shows only after a 150ms delay from `start` (cleared on `finish`) so a fast/cached navigation doesn't flash the backdrop-blur overlay for an instant — only the top bar shows for those. Only renders on pages using `Layout` (i.e. authenticated pages); `Auth/*`/`Public/*` pages never mount it.

## Legacy admin table components (`Components/Table/*`)

`ContentPanel`, `TopPanel`, `TableContainer`, `Thead`, `Tbody`, `Row`, `RowData`, `TableHeader`, `TableSearch`, `PerPage`, and `Pagination` are the shared primitives behind every legacy CRUD table — Users, Privileges, Announcements, Notifications (admin), Log User Access, Menu Management, Modules, and `TradeReportPage.jsx`. None of their props/behavior changed (sorting, search debounce, per-page selection, Laravel paginator link rendering, loading/empty states) — only internal class names, restyled to the same dark/light palette used everywhere else in this app (`border-[#2a2e39] bg-[#131722]` / `border-slate-200 bg-white`, brand-accent teal — see the Maintenance note below) instead of the older `border-secondary`/`bg-custom-gray`/`shadow-menus` tokens. `Thead.jsx` previously hardcoded `bg-white` with no theme check at all — a real dark-mode bug (a white sticky header over a dark table) — now fixed alongside the restyle. Since this is shared across ~15 pages, verify a page beyond Privileges/Users (e.g. Announcements or Log User Access) after any further change here. `Components/Table/Buttons/*` and `Filters.jsx`/`FilterFields.jsx` were intentionally left untouched — they take a page-supplied `extendClass` that already encodes page-specific color/padding, so restyling them safely needs auditing each call site first.

**`Pages/AdmVram/Logs.jsx` ("Log User Access") had an unrelated, pre-existing crash**, found while checking this page after the restyle above: `LogsController::getIndex()` eager-loads each `AdmLogs` row's `user` relation, but `adm_logs.id_adm_users` has no FK constraint enforcing referential integrity, and a real check found 133 of 204 rows already point at a since-deleted `adm_users` id — including several among the first page's default 10 most-recent rows. The page rendered `{item.user.name}` with no null check, so any orphaned row threw a JS `TypeError` and blanked the entire list. Fixed with `item.user?.name ?? 'Deleted user'` — audit log rows for a since-removed actor should still be visible, just labeled, not hidden. If another legacy table renders a `belongsTo` relation similarly, check for the same unguarded-null pattern before assuming a blank page is a styling regression.

## Maintenance

- **The brand accent is teal-green** (`#2dd4bf`, hover `#14b8a6`, light-on-dark tint `#5eead4`; CSS var `--terminal-accent` in `app.css`) — rebranded from blue (`#2962ff`/`#5b8cff`/`#1e53e5`, plus a couple of stray hover-only variants `#1f52e0`/`#254eda`) across the whole app: every admin and trader page, both auth flows, the sidebar, forms, and buttons. Prefer the Tailwind-named `teal-*` shades (matching an existing `blue-*` usage) for new UI chrome, or the arbitrary-hex triplet above where the existing code around it already uses arbitrary hex. **Not every `blue-*`/`#2962ff`-family color in the codebase is the brand accent** — some are deliberately distinct semantic/status colors that happen to be blue and must stay that way: `Components/Subscriptions/statusTones.js` (`available`/`trial` status), `TrainingChallengeCatalog.jsx`'s `STATUS_BADGES.active`, `Pages/Feedback/Index.jsx`'s `reviewing` tone, and the trading chart's own exceptions documented in [Trading chart](trading-chart.md#indicator-panes-volume-rsi-macd) (Fibonacci level colors, position entry-line color, flat-PnL color, SMA/MACD indicator defaults). Before changing a blue-ish color anywhere, check whether it's one color among several in a status/level/series map before assuming it's brand chrome.
- Keep `Auth/*` and `Public/*` outside the authenticated layout.
- Test content overflow when adding fixed headers/sidebars or fullscreen chart UI.
- Add new navigation in both server authorization and the correct role layout.
- Do not derive admin access only from client-rendered role labels.
- Never hardcode a dark-only color (`border-[#2a2e39]`, `bg-[#131722]`, `text-emerald-400`/`text-red-400`, etc.) without a light-theme counterpart — this codebase's light theme uses `border-slate-200`/`bg-white`/`bg-slate-50` and the `-600` shade of status colors (`text-emerald-600`/`text-red-600`) where the dark theme uses `-400`. A hardcoded dark value with no `isDark ? … : …` branch renders as a heavy, out-of-place dark accent on the light theme (found and fixed in `Components/Sidebar/AdminSidebar.jsx`'s section divider and `TraderNavbar.jsx`'s profile-avatar ring) — grep for the file's existing `isDark`/`theme` ternary pattern and match it rather than pasting a class from a dark-theme-only reference.
- Avatar/initials badges (`ProfilePage.jsx`, `AppNavbar.jsx`, `TraderNavbar.jsx`, `Notification.jsx`) render on top of `Components/Notification/ColorMap.js`'s fixed pastel palette, which is independent of the page theme — their text must stay a fixed dark color (`text-slate-800`) rather than following `isDark`, and the `colorMap[...]` lookup must never fall back to a theme class name (a past bug: several letters mapped to `''`/`'bg-white'`, which combined with hardcoded white text produced invisible initials).
