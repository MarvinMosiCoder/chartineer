# Chart Drawings and Settings

## Purpose

Users create chart annotations and save reusable tool defaults. Drawings are scoped to a user and market identity.

| Route/file | Responsibility |
|---|---|
| `GET/PUT /market-drawings` | Load/save drawing collection |
| `GET/PUT /market-tool-settings` | Load/save tool templates |
| `MarketDrawingController.php` | Drawing validation and ownership |
| `MarketToolSettingController.php` | Template validation and ownership |
| `MarketDrawing.php`, `MarketToolSetting.php` | Persistence |
| `ChartStage.jsx`, `ReplayPanel.jsx`, `utils.js` | Editing UI and geometry |

## Flow

1. Active exchange/category/symbol changes.
2. The chart requests that user's drawing record for the market.
3. Pointer actions create/select/move/resize drawing data.
4. Saves are serialized so an older request cannot overwrite newer state.
5. The server updates or creates the user-and-market record.
6. Tool templates load once per user and are saved independently of drawings. The persisted settings key remains `presets` for backward compatibility.

Browser mirrors use scoped keys such as `replay-drawings:{userId}:{exchange}:{category}:{symbol}`. They are recovery/cache aids, not authorization or the source of truth.

Drawings are market-scoped rather than timeframe-scoped. Loading drawings is independent from candle loading, a failed refresh retains the last local/server copy, and absolute drawing times are projected onto the active timeframe. Price Range uses a rectangular two-axis shape with corner and edge handles. Long/short Entry, TP, and SL values render in a dedicated right-axis label layer and remain visible whether or not the drawing is hovered or selected.

Price Range and Price & Date Range render a vertical directional arrow centered in the box (`ChartStage.jsx`, in the same `'rect'`/`'price-range'`/`'date-range'`/`'price-date-range'` box-render block, gated to `['price-range', 'price-date-range'].includes(d.type)`): green pointing up when `end.price > start.price`, red pointing down when lower, hidden while flat (`end.price === start.price`) or during the live drag preview (`temp-` id). Direction is based purely on the price delta, not which corner the user dragged from — reuses the existing `getArrowHeadPoints` helper already used for the `forecast`/`arrow` tool types rather than a new arrowhead implementation.

Date Range and Price & Date Range also get a *horizontal* arrow — gated to `['date-range', 'price-date-range'].includes(d.type)`, a separate block rendered before the vertical one — because their own numeric label includes duration/bar-count, and a box whose meaningful axis includes time needs a time-direction cue a vertical arrow can't give. Its shaft runs along the box's vertical center (`rect.top + rect.height / 2`) from `rect.left` to `rect.right`, gated on `d.end.time !== d.start.time` (not the price-equality check the vertical arrow uses — a date range can have zero price delta while still spanning real time, and that must still show an arrow) and pointing right when `end.time > start.time`, left otherwise — i.e. it reflects which direction the box was actually dragged in time, not corner position. Its color is still green/red off `end.price >= d.start.price`. **Price & Date Range is the one type that renders both blocks at once** — a horizontal arrow across its vertical center *and* a vertical arrow through its horizontal center, forming a plus through the box: horizontal orientation/color = time direction / price direction over the span, vertical orientation = price direction specifically. Price Range and plain Date Range each render only their own single arrow.

**Measure** (a two-point line tool, not a box) gets an analogous arrowhead rather than the shaft-in-box versions: alongside its existing dashed line and endpoint circles, `ChartStage.jsx`'s line-like render branch adds `getArrowHeadPoints(d.screen.p1, d.screen.p2, 8)` colored green/red by the same `end.price > start.price` check, under the same not-flat/not-`temp-` gating as the box tools. The arrowhead points from the first click toward the second, i.e. the actual drag direction, unlike Price Range's shaft which always points top-to-bottom-or-back regardless of which corner was dragged first.

Measure, Price Range, Date Range, and Price & Date Range each have their own rail/flyout icon now (`Ruler`, `MoveVertical`, `MoveHorizontal`, `Move` in `TOOL_BUTTONS`, `ReplayPanel.jsx`) instead of sharing `LocateFixed`. The rail's ready-tool button already looked up its icon per-type (`TOOL_BUTTONS.find(item => item.type === readyType)?.icon`, `ReplayPanel.jsx`'s `TOOL_GROUPS.map` for the compact rail), so this was purely a missing-icon-variety gap, not a lookup bug — the mechanism already changed icons by type, the four entries just all resolved to the same icon.

Measure, Price Range, Date Range, and Price & Date Range live in the **Forecasting** tool group (`TOOL_GROUPS` in `ReplayPanel.jsx`) alongside Long/Short position and Forecast, not Geometric Shape — they're directional/measurement tools, not shapes. Geometric Shape now holds only Box, Circle, Triangle, Arc, Curve, and Double Curve. Moving a tool between groups only changes `TOOL_GROUPS` membership; it does not change the tool's `type` string, so saved drawings, presets, and any user's persisted `readyTools.{groupName}` selection for the *old* group silently fall back to that group's first tool (`group.tools[0]`) since the moved type no longer matches — expected, not a bug to chase.

**A drawing's label is hidden once it no longer fits inside the drawing pane, rather than being clipped mid-glyph.** Labels are positioned at their drawing's anchor (`getLineLabelPosition`/`getPathLabelPosition`/`getBoxLabelPosition`, `ChartStage.jsx`) with no clamping, so a drawing whose anchor had scrolled past the pane still rendered its `<text>`; the overlay then sliced it, leaving the tail of the word plus its thick dark halo stroke (`paintOrder="stroke"`, `strokeWidth="4"`, not a background element) smeared against the chart's left edge. Reported as "I don't know what this is" — a column of `OS` fragments left over from `BOS` levels reads as corruption rather than as labels belonging to drawings that scrolled out of view. All four label render sites now gate on `isLabelFullyVisible(labelPosition, labelText, drawingPaneWidth)`, which derives the label's horizontal extent from its `textAnchor` (`start`/`end`/`middle`) and an approximate width — `estimateLabelWidth`, extracted from the constant `getLineLabelGapSegments` already used to break the line under its label, so the gap and the visibility test can't drift apart. Two details worth keeping: the bound is **`drawingPaneWidth` (`overlaySize.width - 88`), not `overlaySize.width`** — the drawing SVG stops short of the price scale, and that narrower edge is where clipping actually happens; and an unmeasured pane (width `0`/non-finite, i.e. first paint) counts as visible, so labels don't flicker out before layout settles. Only the label is affected — the drawing's line/box still renders and still extends past the pane as before.

## Maintenance

- Add a new tool in constants/tool menus, creation state, rendering, hit testing, movement, resizing, serialization, and validation.
- Preserve unknown/new drawing fields during compatible updates where appropriate.
- Keep SVG overlay boundaries aligned with the main price pane.
- Never query drawings or settings without `adm_user_id`.

## Verification

- Every drawing type create/select/move/resize/delete.
- Reload and market switching.
- With several labelled drawings on screen (e.g. horizontal levels with `BOS`/`FVG` text), pan the chart right until those drawings run off the left edge. Confirm each label disappears whole as it reaches the boundary — never sliced into a partial word, and never a stack of fragments beside the tool rail — while the drawings' own lines/boxes still extend off-screen as before. Repeat toward the right edge, where the boundary is the price scale, not the window.
- Create on 5m, switch to 1h and back to 5m, and confirm geometry and selection remain available.
- Resize Price Range independently from every edge and corner.
- Price Range arrow points up (green) when the box's end price is higher than its start price, down (red) when lower, regardless of which corner was dragged first; no arrow when the two prices are equal.
- Confirm long/short Entry, TP, and SL axis labels remain visible before, during, and after hover/selection.
- Hover each long/short profit or stop zone and confirm the centered Target/Stop and Open P&L details appear, then disappear on pointer leave when the drawing is not selected.
- Select a long/short drawing and confirm its detail labels remain visible after pointer leave. Target and Stop must each stay centered on one line; Open P&L and Risk/Reward remain a two-line badge.
- Two users in one browser remain isolated.
- Rapid saves preserve the latest state.
- Indicator panes do not receive drawing overlays.
- On a touch device (or a browser's device-emulation mode with touch enabled): tap Long or Short, tap two points on the chart, confirm the position box is created; drag an existing drawing and a resize handle with a finger and confirm both track correctly; two-finger pinch still zooms the chart instead of doing anything drawing-related. Tap a tool group's chevron (not just the main icon) and confirm the flyout opens and a non-default tool in that group (e.g. Short when Long is the group's current "ready" tool) can actually be selected.
- Clear Tools/Clear Drawings with at least one drawing present shows the in-app "Clear all drawings?" modal, not a native browser confirm popup; Cancel (or clicking the backdrop) leaves every drawing untouched, Clear all removes them and is still undoable with Ctrl/Cmd + Z. With zero drawings present, the action clears immediately with no modal (nothing to confirm).
- Select a Long or Short position drawing and confirm the rail's floating toolbar and the Settings gear's dialog both show no Color control at all (Width/Line style/Label controls still show where the tool supports them). Select any non-position tool (e.g. a rectangle or trend line) and confirm Color is present as before.
- Draw a line, change its color/width away from the system default (so that becomes the new default for that tool type — confirmed by drawing a *second*, fresh line of the same type and seeing it start with the customized style). Select the first line, open its Settings gear, click **Apply defaults**, then **Ok**. Confirm that one line reset to the system default, but a *third* new line of the same type still starts with your customized style, not the system default — i.e. Apply defaults didn't clobber the saved default. Repeat via the rail flyout's **Apply defaults** (no dialog) and confirm the same. Then, after clicking Apply defaults in the dialog, manually pick a different color before clicking Ok, and confirm *that* color does become the new default for future drawings of that type — a genuine manual edit after Apply defaults still updates the default normally.

# Ready tools and expanded drawing set

Each left-rail drawing category has a ready-tool button and a separate list trigger. Choosing a tool updates that category's ready icon and saves `readyTools` through `/market-tool-settings`, with the existing per-user local fallback. The ready button activates the saved tool immediately.

The chart supports lines, rays, extended lines, arrows, horizontal/vertical lines, paths, Fibonacci tools, parallel channels, position/forecast tools, rectangles, circles, annotations, and Price Range, Date Range, and Price & Date Range. Range labels show price/percentage movement, duration, and candle count as applicable. Saving a template over an existing case-insensitive name requires confirmation.

**Circle** (`'circle'`) is a `BOX_TOOL_TYPES` member, not a new interaction pattern — it reuses the rectangle tool's two-point bounding-box math verbatim (creation, drag-move, 8-point resize handles, hit testing all key off `BOX_TOOL_TYPES.includes(type)`, which doesn't care what shape gets drawn inside the box) and only diverges at the final render step in `ChartStage.jsx`, where `d.type === 'circle'` draws an `<ellipse>` inscribed in the box instead of a `<rect>`. `BOX_TOOL_TYPES` is unfortunately duplicated as a separate module-level constant in both `MarketChart.jsx` and `ChartStage.jsx` (not shared from `utils.js`), plus a third inline literal array at the box-rendering `if` check in `ChartStage.jsx` — all three needed the same addition and must stay in sync for any future box-style tool too.

**Extended Line** (`'extended-line'`) is a line-like tool (`isLineLikeDrawing`) that extends infinitely in both directions, unlike `ray` (extends one direction only). It follows `ray`'s established pattern exactly rather than `vertical-line`'s: the real click anchors stay at `screen.p1`/`screen.p2` (so resize handles and drag-to-move operate on the actual points the user placed, via the generic `isTwoPointDrawing` path), and two *additional* screen-only fields, `rayStart`/`rayEnd`, hold the edge-of-viewport extension for rendering and hit-testing only — computed from the same point-slope line equation as `ray`, just applied to both ends instead of one. Every place that reads `d.screen.rayEnd ?? d.screen.p2` to find the line's visible endpoint has a symmetric `d.screen.rayStart ?? d.screen.p1` counterpart for the visible start (`ChartStage.jsx`'s line renderer and label-gap calculation, `hitTestDrawing`'s click detection). `getLineLabelPosition` was deliberately left reading the real `p1` (not `rayStart`) for a centered label's anchor — the label sits nearer the drawn segment instead of drifting to the chart edge, a readability choice, not an oversight.

If another "extends beyond its two points" tool is ever added, extend from `extended-line`'s `rayStart`/`rayEnd` pattern (additive screen fields, real anchors preserved) rather than `vertical-line`'s (which overwrites `screen.p1`/`p2` outright and works only because a vertical line's real anchor point is meaningless once it's forced to span full height — that shortcut doesn't generalize to a tool where the anchors still matter for dragging).

The chart context menu's **Clear Tools** action clears drawings through the same confirmation, persistence, and undo path as the drawing rail. It is disabled when no drawings exist and does not remove indicators, alerts, positions, or templates.

**Market session bands are not drawings, deliberately.** There is already a `vertical-line` drawing type that spans the full overlay height at a projected x (`ChartStage.jsx`), and session boundaries are geometrically the same thing — but they are built as a separate derived layer (`renderedSessionBands`, `SessionOverlay`) rather than being pushed into the `drawings` array. Putting them there would make them selectable, draggable, persisted per market, part of undo/redo, and — worst — swept up by Clear Tools, so a user clearing their trendlines would silently lose their session shading too. If another auto-generated overlay is ever added (session highs/lows, daily opens), follow the same split: reuse the projection and SVG rendering path, never the `drawings` collection. See [Trading chart](trading-chart.md) for the session feature itself.

**Clearing all drawings confirms via an in-app modal, not the browser's native `window.confirm`.** `handleClearDrawings` (`MarketChart.jsx`) now only sets `showClearDrawingsConfirm` to `true` when `drawingsRef.current.length` is non-empty (calling straight through to the actual clear when the chart already has nothing to lose); the real clearing logic moved into a separate `performClearDrawings()` (undo snapshot, `saveDrawings([])`, deselect, close the modal) that both the modal's Confirm button and (when there's nothing to confirm) `handleClearDrawings` itself can call. The dialog is a plain conditional block in `MarketChart.jsx`'s own top-level render fragment (`showClearDrawingsConfirm && (...)`), matching how this file already renders its other simple confirm/info dialogs (e.g. the price-alert modal) inline rather than via `createPortal` — `MarketChart.jsx`'s root return is already a top-level fragment, so no portal target is needed the way `ReplayPanel.jsx`'s nested `ConfirmOverwriteDialog` needs one. Styled with the same `chartTheme.mode === 'dark'` dark/light token pair used by the price-alert modal right above it in the file, not `ReplayPanel.jsx`'s own token set — the two files intentionally keep separate small dialogs rather than sharing one across files for a single confirm prompt.

Selecting the toolbar settings action opens a staged drawing editor with Style, Text, Coordinates, and Visibility tabs. **Ok** persists the edited drawing while **Cancel** discards the draft. Coordinate fields update supported point-based drawings, visibility can be limited to the active timeframe, and locked drawings remain selectable but cannot be moved or resized.

**The dialog is draggable by its header**, same `translate3d`-on-top-of-the-existing-layout/Pointer-Events/viewport-clamp approach as `ChartSettingsModal` (see [Trading chart](trading-chart.md)) — `dragOffset` resets to `{x:0,y:0}` on the same `drawing?.id` effect that already reseeds `draft`/`activeTab` when a new drawing is edited, rather than a dedicated `open` prop (this component mounts fresh each time it's shown, unlike `ChartSettingsModal`, so there's no separate open transition to key off). The close (X) button is excluded from the drag handle the same way (`event.target.closest('button')`). `DIALOG_DRAG_MARGIN` (32px, module-level in `ReplayPanel.jsx`) is a separate constant from `ChartSettingsModal`'s own `DRAG_MARGIN` — keep both in sync if the clamp margin is ever tuned, since they're two independent implementations, not a shared hook.

The dialog's footer also has a **Template** dropdown (left of Cancel/Ok), matching TradingView's pattern: **Save as...** opens a second, focused modal (just a name field, Cancel/Save) that reuses the exact same save path as the Templates rail flyout — `onSaveSelectedToolPreset`/`handleSaveSelectedToolPreset` in `MarketChart.jsx`. The dropdown also lists every saved template for the tool's type below the Save as/Apply defaults actions (name to apply, trash icon to delete via `onDeleteToolPreset`), the same list shape as the rail flyout, instead of only exposing Save as/Apply defaults with no way to browse or reuse an existing template from inside the dialog. Clicking a template row stages `preset.settings` onto the in-progress `draft` (`handleApplyTemplate`, a `setDraft` call like `handleApplyDefaults`) rather than committing it live — Cancel still discards it and only Ok commits, consistent with every other edit in this dialog. **Apply defaults** resets the in-progress draft (color to `DRAWING_COLORS[0]`, width 1, solid line, non-bold/non-italic 12px text, top/center label alignment) without closing the dialog or touching any saved *named* preset. This is a second entry point onto the *same* preset system the Templates rail flyout already exposes (`presetItems`, `canUsePresets` computed once in the outer `ReplayPanel` component and passed down) — it does not duplicate storage or add a new persistence path.

**Found and fixed: "Apply defaults" was also silently overwriting the tool type's saved *default* style, not just the one drawing being reset.** Every style-editing handler in `MarketChart.jsx` (`handleDrawingColorChange`/`WidthChange`/`LineStyleChange`/`LabelChange`) unconditionally calls `saveToolSettingsForType(type, updates)` on every change — this is what makes "the last style you drew with" become the default a *new* drawing of that type is seeded with (`getToolSettingsForType(toolRef.current)`, read at drawing-creation time). Before this fix, clicking "Apply defaults" reused those exact same handlers to reset the live/draft drawing, so it *also* persisted the reset-to-system-default values as the new sticky default for every future drawing of that type — via both localStorage and a `PUT /market-tool-settings` round-trip — with no warning, silently discarding whatever custom default the user had built up simply by drawing normally. Fixed by giving all four handlers an optional second-argument `{ skipDefaultSave: true }` that skips the `saveToolSettingsForType` call while still updating the live drawing/draft; both "Apply defaults" call sites (`handleApplyToolDefaults` in the rail flyout, and the settings dialog's `handleApplyDefaults` + its **Ok** button) now pass it. The dialog version needed one more piece since it defers the actual handler calls until Ok is pressed: a local `defaultsJustApplied` boolean (`DrawingSettingsDialog`) is set `true` by `handleApplyDefaults` and cleared back to `false` by `updateStyleDraft` — the wrapper every Style/Text-tab field's `onChange` now goes through instead of calling `setDraft` directly — so that *manually* re-picking a value after clicking Apply defaults still counts as an explicit choice and updates the saved default normally on Ok; only an untouched post-reset Ok skips the save.

**`handleSaveTemplate` passes the dialog's current `draft` to `onSaveTemplate`, not just the template name** — `handleSaveSelectedToolPreset(presetName, overrideDrawing)` in `MarketChart.jsx` uses `overrideDrawing` (the draft) when present instead of re-reading the drawing from `drawingsRef.current`. Before this, clicking "Save as..." while the dialog had unapplied edits (Ok not yet pressed) silently saved the *original*, unedited drawing's style — the fix so an in-progress style/text edit is actually reflected in the template that gets saved, without requiring Ok first. The rail flyout's own save path (`onSaveSelectedToolPreset(presetNameDraft)`, no second argument) is unaffected — that flow already edits the live drawing directly, so `drawingsRef.current` is already current when it saves.

A duplicate-name overwrite (in this dialog and the rail flyout below) shows an in-app `ConfirmOverwriteDialog` (`ReplayPanel.jsx`) instead of the browser's native `window.confirm` — themed to match the rest of this dialog system (dark/light tokens, `role="alertdialog"`), portaled the same way as the modal it stacks above (`document.body` for the settings dialog's own Save-as, `chartBoundsRef.current` for the rail flyout's), one z-index layer above it (`z-[10032]`) so it visibly sits on top rather than closing its parent modal first.

The Templates rail flyout (`TopToolEditorBar` in `ReplayPanel.jsx`) mirrors that same "actions above the list" shape rather than pinning an always-open name field under the list. When a drawing is selected, the flyout opens with two action rows above the "Templates" list — **Save as...** and **Apply defaults** — matching TradingView's own Template-menu layout:
- **Save as...** opens a "Save drawing template as" modal — its own local `showSaveAsDialog` state inside `TopToolEditorBar`, not the settings dialog's. Its Save button/Enter key run `attemptSavePreset()` (also local to `TopToolEditorBar`), which checks `presetItems` for a case-insensitive name collision itself and only opens the `ConfirmOverwriteDialog` when one exists — `handleSavePreset` in the outer `ReplayPanel` (passed down as `onSavePreset`) is now a plain commit step (call `onSaveSelectedToolPreset`, clear `presetNameDraft`), not where the collision check lives. Unlike `DrawingSettingsDialog`'s save-as modal (which portals to `document.body` and centers on the full page), this one centers on the chart itself: `ReplayPanel` attaches `panelRootRef` to its own root — the element already absolutely/fixed-positioned to span the chart's drawing area — and passes it down as `chartBoundsRef`; the modal is `createPortal`-ed into that node with `absolute inset-0` (plus an explicit `pointer-events-auto`, since the portal target carries `pointer-events-none`) instead of `fixed inset-0`, so `items-center justify-center` centers it against the chart box rather than the browser viewport.
- **Apply defaults** (`handleApplyToolDefaults`) resets the *live* selected drawing's style immediately, unlike the settings dialog's same-named action which only touches an in-progress draft until Ok is pressed: it calls `onDrawingColorChange(DRAWING_COLORS[0], { skipDefaultSave: true })` when `canEditColor`, `onDrawingWidthChange(1, { skipDefaultSave: true })`/`onDrawingLineStyleChange('solid', { skipDefaultSave: true })` when `canEditWidth`/`canEditLineStyle` gate them for the tool, and `onDrawingLabelChange({ textBold: false, textItalic: false, textSize: 12, labelVertical: 'top', labelHorizontal: 'center' }, { skipDefaultSave: true })` when `canEditLabel || canEditText`. There is no draft to discard here — the change lands on the drawing as soon as it's clicked. `skipDefaultSave: true` (see the fixed-bug note above) is what stops this live reset from also overwriting the tool type's saved default style.

**Found and fixed: the Color control did nothing for Long/Short position tools.** Both entry points (this rail flyout's Color button and `DrawingSettingsDialog`'s Style/Text tab color fields) used to render unconditionally for every tool type — but `ChartStage.jsx`'s `isPositionDrawing` render branch never reads `drawing.color` at all; the profit zone, loss zone, and entry line are hardcoded (`rgba(34, 197, 94, ...)` green / `rgba(239, 68, 68, ...)` red / `#5b8cff` blue), by design, matching TradingView's own fixed-color long/short tool convention. A user could pick a color, see it save (it even round-tripped through `/market-tool-settings` as the tool type's default), and the drawing's zones would never visibly change — indistinguishable from the control being silently broken. Fixed by adding `canEditColor` (`COLOR_TOOL_TYPES = PRESET_TOOL_TYPES` minus `POSITION_TOOL_TYPES`, i.e. `['long-position', 'short-position']`, `ReplayPanel.jsx`) alongside the existing `canEditWidth`/`canEditLineStyle`/`canEditLabel` gates, and hiding the Color button/fields for those two types rather than trying to wire a color picker to a two-zone tool where "which zone does this color apply to?" has no clear single answer.

The list itself only renders template rows (apply on click, trash icon to delete); there is no persistent input row in the list.

The Text tab's Size select (`TEXT_SIZES` in `constants.js`, 10–32px) sets `drawing.textSize`, read by `ChartStage.jsx` wherever a drawing's text renders: the standalone `text` tool's floating `<span>` and every `labelText` badge on lines/paths/boxes (all default to 12px when unset, so existing saved drawings render unchanged). This field follows `textBold`/`textItalic`'s exact plumbing, but that plumbing has a non-obvious extra hop worth knowing before adding a fourth text-style field: the settings dialog's "Ok" button (`DrawingSettingsDialog`'s `onApply` in `ReplayPanel.jsx`) does **not** forward the whole draft — it re-lists specific fields into the object it hands to `onDrawingLabelChange`. A field only reaches the drawing (and, for the `text` tool type, `handleDrawingLabelChange`'s own separate persisted-preset whitelist in `MarketChart.jsx`) if it's named in *both* places; adding it to the tab's UI alone silently does nothing on Ok.

Long/short position drawings use an exchange-style risk/reward layout with distinct profit and stop zones and draggable entry, target, and stop handles. The zones have no outer, top, or bottom border; a thin entry divider separates them. TP/Entry/SL price-axis badges are always visible. Hovering anywhere inside either zone, or selecting the drawing, reveals the detailed labels: centered single-line Target and Stop badges plus a centered two-line Open P&L and Risk/Reward badge. Pointer leave hides those details only when the drawing is not selected. Long targets/stops are constrained above/below entry respectively; short drawings use the inverse ordering, including while creating or resizing the tool.

# Shapes (Triangle, Arc, Curve, Double Curve), text-marker family, lock-all, and Show/Hide

Four new shapes joined the Geometric Shape group and ten text-marker types joined Annotation, all reusing existing interaction machinery rather than inventing new ones:

- **Triangle, Curve, Double Curve** are 3-point tools (`THREE_POINT_SHAPE_TYPES` in `MarketChart.jsx` / `THREE_POINT_TYPES` in `ChartStage.jsx` — two names for an overlapping-but-not-identical concept, see below) added to the *same* `['fib-extension', 'parallel-channel']` special-case list that already collects a third `anchor` point on a 3rd click, at all four call sites (temp-drawing creation, mousemove preview, finalize-on-click, and the resize-handle generator) — search for `THREE_POINT_SHAPE_TYPES`/`THREE_POINT_TYPES` if adding a fifth. They're also added to `isLineLikeDrawing`, which means the generic `resized[handle] = coords` line already used for `fib-extension`'s anchor handle drag "just worked" for these too with no new resize code. Rendering intercepts `SHAPE_TOOL_TYPES` right after the `isFibonacciDrawing` branch (before the generic straight-line fallback) in `ChartStage.jsx`: triangle draws a `<polygon>` from p1/p2/p3, Curve draws a quadratic `<path>` (`Q p3`) using p3 as the control point, Double Curve derives two cubic control points by offsetting the p1–p2 midpoint by however far p3 sits from *that* midpoint (a hand-rolled S-curve approximation, not a real second anchor point — good enough to look visually distinct from Curve, not claiming more fidelity than that). Until the 3rd point exists (`d.screen.p3` unset), all three fall through to the plain two-point line preview, matching `parallel-channel`'s existing UX during creation.
- **Arc** is a plain 2-point tool (no anchor) rendered as a fixed-curvature SVG arc (`radius = distance(p1,p2) * 0.75`) — a simplification, not TradingView's real dynamically-adjustable arc. Hit-testing for all four shapes approximates against straight edges (p1–p2, plus p1–p3/p2–p3 for the 3-point ones) rather than the actual curve/arc geometry; clicking exactly on a pronounced bulge, away from those chords, may not select it. Good enough for now; revisit if it's reported as an actual usability problem.
- **Text-marker family** (`TEXT_MARKER_TYPES`, duplicated as a module constant in `MarketChart.jsx`, `ChartStage.jsx`, and `ReplayPanel.jsx` — same duplication pattern as `BOX_TOOL_TYPES`, all three must stay in sync): Anchored Text, Note, Anchored Note, Callout, Comment, Price Label, Price Note, Signpost, Flag Mark. All ten (including the original `text`) share one data shape (`point`, `text`, `color`, `textBold`, `textItalic`, `textSize`) and one creation flow (click → `TextInputPopover` → save) — every place that used to hardcode `drawing.type === 'text'` now checks `TEXT_MARKER_TYPES.includes(drawing.type)` instead (there were **13 such call sites** across the two files: settings/preset persistence, hit-testing, drag-anchor detection, `getDrawingTimes`, screen-coordinate computation, resize-handle exclusion, and both of `ReplayPanel.jsx`'s "what's the current drawing's display name" helpers). They're visually differentiated only by an icon in front of the text (`TEXT_MARKER_ICONS` in `ChartStage.jsx`) plus two special cases: **Signpost** gets an auto-incrementing number badge instead of an icon (`drawing.signpostNumber`, computed once at creation time as `count of existing signposts + 1`, never renumbered afterward even if earlier signposts are deleted) and **Callout** gets a bordered speech-bubble background. **Price Label**/**Price Note** additionally draw a dashed line from the marker to the right chart edge at the same Y (`PRICE_ANCHORED_MARKER_TYPES`, `d.screen.pRight`) to *suggest* price-axis anchoring, but they are not actually price-only anchored — dragging still moves them in time too, same as every other marker. This is a deliberately shallow set of variants (one interaction, one renderer, cosmetic differentiation) rather than bespoke widgets — do not assume Callout has real pointer-line geometry or Signpost renumbers on delete; check the code before relying on either.
- **Group icons**: `TOOL_GROUPS` entries gained a `groupIcon` field (`Spline`, `Sigma`, `Compass`, `Shapes`, `MessageSquare`), shown in the compact rail's `<details>` summary and the per-group flyout title in `ReplayPanel.jsx`. This is independent of each group's rail *button* icon, which intentionally still shows the last-used ("ready") tool in that group, not the group icon — don't conflate the two.
- **Lock all drawings** (rail button, `Lock`/`Unlock` icon) is a session-only override, not a bulk edit — `allDrawingsLocked` (state + `allDrawingsLockedRef` for the mouse handlers) is OR'd alongside each drawing's own `locked` flag at both places that gate drag/resize start. It never touches individual drawings' `locked` values, so turning it off doesn't reveal which ones were already locked before you turned it on — nothing to reconcile either way.
- **Show/Hide** (rail button, `Eye`/`EyeOff` icon) is `hiddenLayers: { drawings, indicators, positions }` in `MarketChart.jsx`, also session-only (not persisted, not synced to the server). "Hide drawings" and "Hide positions" filter `renderedDrawings` at the source (`isPositionDrawing` splits the two categories), so hidden items are also un-hit-testable — you can't select or drag something invisible. "Hide indicators" is ANDed into the existing per-indicator visibility effect (volume/SMA/EMA/RSI/MACD), so it composes with each indicator's own on/off state rather than overriding it permanently. "Hide all" is a single toggle: hides all three if any are visible, shows all three only when all three are already hidden. Scope note: "positions and orders" only covers `long-position`/`short-position` *drawings* — it does not touch live backtest order/position overlays rendered from `backtestAccount` state, which is a separate rendering path this didn't touch.

**Found and fixed two pre-existing bugs while wiring the above, unrelated to what was asked but directly adjacent to the code being touched:**
1. `parallel-channel`'s filled-two-line-channel rendering was dead code — it lived inside `if (isPathDrawing(d))`, but `d.type === 'parallel-channel'` can never be true there (`isPathDrawing` requires `type === 'path'`), so a parallel-channel drawing always silently fell through to the generic single-line renderer and never showed as an actual channel. Moved to the correct spot (alongside the new shape branches, inside `isLineLikeDrawing`, after the fibonacci branch) — it now renders as originally intended.
2. Its "drag the anchor" resize-handle *dot* also never appeared (a separate, visual-only handle list in `ChartStage.jsx` only checked `selectedDrawing.type === 'fib-extension'`, not `'parallel-channel'`, even though the actual anchor drag has always worked via the other, correct handle list in `MarketChart.jsx`) — the dot just never rendered. Both bugs were shipped together, likely from copy-pasting fib-extension's special case without extending it to its sibling. Fixed alongside adding the same handle for the three new 3-point shapes.

The settings modal's "Ok" whitelist (`onApply` in `ReplayPanel.jsx`, see the Template/Text-size note above) had a *third* undiscovered `nextDrawing.type === 'text'` check gating whether an edited marker's `text` field actually reached the drawing — found and fixed during this pass, since it would otherwise have silently no-op'd editing any of the nine new marker types' content via the settings modal (only the original `text` type would have worked). Anywhere this codebase says `=== 'text'`, check whether it should really say `TEXT_MARKER_TYPES.includes(...)` now.

# Patterns, Elliott Waves, and Cycles groups

14 new tool types (`ReplayPanel.jsx`), none of which existed before: **Patterns** (XABCD, Cypher, Head and Shoulders, ABCD, Triangle Pattern, Three Drives Pattern), **Elliott Waves** (Impulse 12345, Correction ABC, Triangle ABCDE, Double Combo WXY, Triple Combo WXYZ), and **Cycles** (Cyclic Lines, Time Cycles, Sine Line). None of this is TradingView's actual harmonic/Elliott pattern-recognition engine (ratio validation, auto-fit, etc.) — these are manual N-point/2-point drawing tools that let a user lay the shape out by eye, same spirit as this app's existing Fibonacci and shape tools.

They live under **one** `TOOL_GROUPS` rail entry (`{ name: 'Patterns', groupIcon: Workflow, ... }`), not three — one sidebar icon opens one flyout containing all 14 tools, split into three `Patterns`/`Elliott Waves`/`Cycles` sections separated by a divider line, matching TradingView's own single combined panel rather than three separate rail buttons. The group still carries a flat `tools` array (all 14 types, in the same order the sections list them) alongside a `sections: [{ title, tools }, ...]` array: `tools` is what every *other* piece of group-generic logic already keyed off before this change (`readyTools.{groupName}` ready-tool tracking, the compact rail's active/highlight state, the flat `group.tools[0]` icon fallback) and still does — untouched, no special-casing added there. `sections` is purely a display concern, read only where the flyout actually lists tools: the compact rail's per-group flyout (`ReplayPanel.jsx`, the `activeGroup === 'tools:${group.name}'` block) and the full "Tools" accordion flyout (the `<details>`-per-group listing used when `!fullscreenDrawingOnly && !groupedWorkspaceRail`) both branch on `group.sections ? (...) : (...)`, rendering the existing flat-list markup when a group has no `sections` (every group but this one) and a divided, sub-headed list when it does. Any future group that wants the same "one icon, several titled subsections" shape can reuse the identical `sections` field — the two render sites already handle it generically, keyed off presence rather than group name.

**Patterns and Elliott Waves are one family** (`MULTI_POINT_PATTERN_LABELS` in `utils.js`): a map from tool type to its per-vertex label sequence, e.g. `'xabcd-pattern': ['X', 'A', 'B', 'C', 'D']`, `'elliott-impulse-wave': ['', '1', '2', '3', '4', '5']` (leading `''` = the unlabeled wave-0 start point). The array's *length* doubles as the tool's fixed point count — that's the only per-tool config that exists; there's no separate count field to keep in sync. `head-and-shoulders`, `triangle-pattern`, and `three-drives-pattern` use all-empty label arrays (7, 5, and 7 points respectively) since TradingView doesn't badge those with letters either — the drawing is just the zigzag shape.

These are **not** a new interaction system — they extend the existing freehand `path` tool's points-array machinery rather than inventing multi-point creation from scratch:
- `isPathDrawing` (`utils.js`) now checks membership in `MULTI_POINT_TOOL_TYPES` (`['path', ...MULTI_POINT_PATTERN_TYPES]`) instead of `type === 'path'` only — the name is kept for the ~10 existing call sites across `MarketChart.jsx`/`ChartStage.jsx` (screen-coordinate projection, rendering, hit-testing, resize-handle generation, drag-move `offsetDrawing`, keyboard nudge, duplicate, undo) rather than renamed, matching this file's established pattern of broadening a predicate in place (`isLineLikeDrawing`, `isShapeDrawing`) instead of fanning a new one out to every call site.
- The mousedown creation handler in `MarketChart.jsx` (previously gated on `toolRef.current === PATH_TOOL_TYPE`) now checks `MULTI_POINT_TOOL_TYPES.includes(toolRef.current)` and builds/extends the same `{ type, points: [...], previewPoint }` temp shape for any of them. The one behavioral fork: after pushing a point, if `MULTI_POINT_PATTERN_LABELS[toolRef.current]?.length` is set and `points.length` has reached it, `handleFinishPathDrawing()` fires immediately — auto-completing the drawing on its last required click. `path` itself has no entry in that map, so it's unaffected and stays freehand-until-dblclick. The mousemove rubber-band-to-cursor update and the dblclick early-finish handler were broadened the same way, so dblclick can still finish a pattern early (fewer than its full point count, same ≥2-point minimum `handleFinishPathDrawing` already enforced for `path`) if a user wants to bail out partway through.
- `PATH_TOOL_TYPE` (the old single-purpose constant) was deleted since every reference became a `MULTI_POINT_TOOL_TYPES` check.
- Rendering reuses the exact `isPathDrawing(d)` branch in `ChartStage.jsx` (`buildPathData` over `d.screen.points`, endpoint circles, freeform preview segment to the cursor) and adds one thing on top: an `MULTI_POINT_PATTERN_LABELS[d.type]` lookup renders a small text badge above each vertex that has a non-empty label, keyed by index into `d.screen.points`. Labels appear incrementally as each point is placed (not gated on `!id.startsWith('temp-')`), so the letter/number appears immediately after each click rather than only once the shape is finished.
- Because `WIDTH_TOOL_TYPES`/`LINE_STYLE_TOOL_TYPES`/`LABEL_TOOL_TYPES`/`PRESET_TOOL_TYPES` (`ReplayPanel.jsx`) all derive from `TOOL_BUTTONS`, and `PRESET_ENABLED_TOOL_TYPES` (`MarketChart.jsx`) is the one hand-maintained exception, adding a tool only required appending it to `TOOL_BUTTONS` (for the rail/flyout icon and generic width/style/label editing) and to `PRESET_ENABLED_TOOL_TYPES` (for template save/apply) — no new per-feature lists.

**Cycles is a different family** — `cyclic-lines`, `time-cycles`, and `sine-line` are plain 2-point tools (`TWO_POINT_TOOL_TYPES` and `isLineLikeDrawing` in both `utils.js` and `MarketChart.jsx`, via the shared `CYCLE_TOOL_TYPES` constant), so they get the *existing* 2-click creation flow, `start`/`end` resize handles, and drag-move for free. `ChartStage.jsx` intercepts `CYCLE_TOOL_TYPES` inside the `isLineLikeDrawing` render branch — the same interception point as `parallel-channel` and `SHAPE_TOOL_TYPES` — before the generic straight-line fallback:
- **Cyclic Lines** / **Time Cycles**: the two clicked points define a period (`|p2.x - p1.x|` in screen space); the render then repeats vertical lines at that spacing across the full visible width (both directions from the anchor, capped at 60 lines as a safety valve against a near-zero period from two points dragged on top of each other). The two originally-clicked lines render at full opacity/weight; the repeated ones are dimmer and dashed so the "real" anchors stay visually distinguishable. Time Cycles is the same mechanism with a finer, fixed dotted stroke throughout — TradingView's real Time Cycles renders small arcs per interval, which this doesn't attempt; treat the current version as a placeholder differentiated by style only, not by a distinct visual language, until/unless that's reported as actually needed.
- **Sine Line**: renders one full sine cycle spanning `p1.x`→`p2.x` at a fixed 48-sample resolution, baseline at the vertical midpoint of the two points and amplitude derived from `|p2.y - p1.y| / 2` (minimum 20px) — a readable approximation, not TradingView's amplitude-adjustable version.
- Hit-testing for all three still runs through `isLineLikeDrawing`'s generic `distanceToSegment(point, p1, p2)` check against the *base* two-point segment only — same "good enough, not exact-geometry" tradeoff already accepted for Arc (see above). Clicking a repeated cycle line far from the original segment, or a sine crest away from the base chord, may not select the drawing; click near the original two anchor points instead.

New icons only — `Waypoints`, `Share2`, `Milestone`, `Route`, `Activity`, `ChartSpline`, `GitCommitHorizontal`, `GitFork`, `Shuffle`, `Split`, `Repeat`, `Repeat2`, `Radical` for the 14 tools plus `Workflow` for the one merged group icon (`TOOL_BUTTONS`/`TOOL_GROUPS` in `ReplayPanel.jsx`) — chosen for reasonable visual association, not a port of TradingView's actual glyphs.

# Brushes and Arrows, merged into Geometric Shape

Eight more new tool types, added the same "merge into an existing rail icon via `sections`" way as the Patterns group above — `Geometric Shape`'s flyout now has three sections instead of a flat list: **Shapes** (the pre-existing Box/Circle/Triangle/Arc/Curve/Double Curve), **Brushes** (Brush, Highlighter), and **Arrows** (Arrow Marker, Arrow, Arrow Mark Up/Down/Left/Right). `Geometric Shape.tools` grew to include all 8 new types (flat, for ready-tool tracking) alongside the new `sections` array (display-only) — same split responsibility documented above for the Patterns group.

**Brush and Highlighter reuse `path`'s exact freehand machinery** — they're in `FREEHAND_TOOL_TYPES` (`utils.js`, `['path', 'brush', 'highlighter']`), the set `MULTI_POINT_TOOL_TYPES` is built from alongside the fixed-count pattern types. Unlike TradingView's actual brush (a continuous mouse-drag trace), these are click-per-vertex + dblclick-to-finish, identical to Path — a deliberate scope simplification (no new drag-tracking interaction was added) rather than a faithful port; revisit only if that's reported as a real usability gap, same posture as the Arc/Time Cycles approximations above. The two tools differ only in default styling: `DEFAULT_FREEHAND_STROKE_WIDTH` (`MarketChart.jsx`) seeds Highlighter's first stroke at width 14 (Brush falls through to the normal width-1 default), and `ChartStage.jsx`'s path render branch sets `strokeOpacity={d.type === 'highlighter' ? 0.35 : 1}` so it reads as translucent marker ink. That same render branch also skips the per-vertex circle dots for `isFreehandPaint` types (`d.type === 'brush' || d.type === 'highlighter'`) — a freehand stroke shouldn't look like a connect-the-dots line — without losing editability: the selection resize-handle list is a separate, unconditional render path keyed off `screen.points` regardless of these decorative dots, so a selected brush stroke still exposes a drag handle per point.

**Arrow Marker, Arrow Mark Up/Down/Left/Right are icon-only point markers** — added to `TEXT_MARKER_TYPES` (still duplicated across `MarketChart.jsx`/`ChartStage.jsx`/`ReplayPanel.jsx`, same burden noted for the original nine markers) and to `ICON_ONLY_MARKER_TYPES` (`utils.js`), a short list checked once, at the point-marker click handler in `MarketChart.jsx`. Every *other* text marker (Signpost, Flag Mark, etc.) opens `TextInputPopover` and — via `handleSaveText`'s `!textDraft.trim()` guard — refuses to save without typed text; these five skip that popover entirely and `appendDrawing` straight from the click with `text: ''`, since a directional/pointer icon needs no caption. This is a different fix from relaxing `handleSaveText`'s guard: relaxing the guard would still force a popover open-then-immediately-close interaction, where placing directly on click matches TradingView's actual single-click arrow-mark behavior. `TEXT_MARKER_ICONS`/`TEXT_MARKER_LABELS` (`ChartStage.jsx`) map the five to `ArrowUpRight`/`ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight` for the marker icon; `TEXT_MARKER_LABELS` wasn't extended for them since it only feeds the (now-bypassed) popover's field label, unreachable for these five.

**Arrow** (the sixth Arrows-section entry, a two-point line with an arrowhead) is a *new* type, `arrow-line`, not a re-list of the pre-existing `arrow` type from the Trend Lines group. The two are functionally near-identical (`ChartStage.jsx` draws the same `getArrowHeadPoints` arrowhead for `d.type === 'forecast' || d.type === 'arrow' || d.type === 'arrow-line'`, plus `arrow-line` alone gets a small circle at its start point to match its distinct icon), but sharing the literal `arrow` type across two different `TOOL_GROUPS` entries would have made `readyTools.{groupName}` tracking and the compact rail's per-group active-highlight ambiguous about which group "owns" the tool when it's active — a new type sidesteps that rather than working around it. `arrow-line` was added everywhere `arrow` already appears in `isTwoPointDrawing`/`isLineLikeDrawing` (`utils.js`) and `TWO_POINT_TOOL_TYPES` (`MarketChart.jsx`), so it gets the exact same two-click creation, resize, and drag-move as every other two-point line tool for free.

## Compact rail (`groupedWorkspaceRail`/`fullscreenDrawingOnly`) column width

The compact vertical rail's outer panel (`ReplayPanel.jsx`, the `pointer-events-auto flex flex-col gap-2 ...` div) has no explicit width — it shrink-wraps to its widest child. Every row — both `TOOL_GROUPS` rows and the plain single-action rows (Play, Enter Position, Tool Style/Templates (Palette), Lock/Unlock, Show/Hide, Clear Drawings) — shares the identical `flex w-11 items-center` wrapper (44px, flush-start), matching a reference TradingView-style toolbar: `RailButton` (`h-9 w-9`, `<Icon size={18} />`) sits flush at the start of every row, group or plain, so its position never depends on whether that row happens to have a trailing chevron. `RailButton` has no border/shadow — inactive icons render in a muted gray (`text-[#b2b5be]` dark / `text-slate-700` light — the light value was `text-slate-500` until an 18px line icon on a white panel was reported as reading "disabled" rather than merely inactive) with a soft `hover:bg-white/10` (or `hover:bg-slate-100` light) tint on hover; `getControlStyle()`, the old bordered panel-colored fill helper, is dead and was removed. The **active** tool is the one exception that keeps a background — `bg-white/10 text-white` (dark) / `bg-slate-200 text-slate-900` (light), a solid rounded highlight, matching the reference's filled rounded-square behind the selected tool — so "no box" applies to resting/hover states only, not to marking which tool is currently active.

The group-row `ChevronRight` toggle is a dedicated trailing lane, `absolute right-0 top-0 h-9 w-2`, sitting *outside* the button's own 36px footprint rather than overlapping it — matching how the reference shows its small `>` sitting to the right of the icon, not as a badge on top of it. (A corner-overlay badge version was tried in between and reverted — it doesn't match this reference's actual layout, where the chevron is a separate inline element after the icon, not glued to a corner of it.) Plain rows have no chevron and so leave that trailing 8px empty, but since every row shares the same `w-11` flush-start wrapper, the icon itself still lands at the identical x-position across all rows regardless of which ones have a chevron. The Palette button, which also renders in the non-grouped/ungrouped rail layout (`!fullscreenDrawingOnly && !groupedWorkspaceRail`) alongside other unwrapped buttons there, keeps its wrapper's `w-11` conditional on `fullscreenDrawingOnly || groupedWorkspaceRail` so it doesn't widen that other, untouched layout.

The chevron used to be fully hover-revealed (`opacity-0 group-hover:opacity-100`, invisible until the row was hovered) to match a TradingView-style reference. **This broke touch entirely**: `:hover` never fires on a touchscreen, so a mobile user could tap the main icon (always the group's "ready" tool, e.g. Long) but had no way to reach the chevron's flyout to ever pick the group's *other* tools (e.g. Short) — confirmed as a real gap, not a hypothetical, once mobile support became a priority. It's now dimmed-but-present by default, full strength on hover, and slightly wider (`w-3` instead of `w-2`) — always visible and tappable, with hover still giving it a brighter/larger-feeling desktop affordance on top. If a future design pass wants the fully-hidden desktop look back, it needs a `(hover: hover)` media-query-aware variant instead of reverting to plain `group-hover`, or touch users lose access to every non-default tool in every group again.

**How it is dimmed differs by theme, and that asymmetry is the point.** Dark keeps the original `text-[#787b86] opacity-40`; light uses a solid `text-slate-500` with no opacity at all. Blending 40% of `#787b86` over the dark panel (`#151617`) lands in a usable mid-gray, but the same 40% over a *white* panel computes to roughly `#c9cacd` — close enough to invisible that the chevron stopped reading as a control, which is exactly the touch-reachability problem the hover-reveal fix above was meant to end. Reach for a darker solid color rather than an opacity whenever a muted element sits on the light panel; opacity toward white subtracts contrast much faster than opacity toward black adds it.

**Not a rail bug, logged so it isn't re-chased:** a small red circular "cancel price alert" button (`data-chart-ui="alert-line-cancel"`, `MarketChart.jsx`) renders inside the main chart at `absolute left-9`, with its vertical position driven by `candleSeriesRef.current.priceToCoordinate(alert.target_price)` — i.e. it tracks the *alert's price level* on screen, completely independent of the rail. In a tightly cropped screenshot showing mostly rail plus a sliver of chart, this can land right next to any rail row (a different one each time, since it moves whenever the visible price range changes) and reads as a misaligned rail element when it's actually an unrelated chart overlay ~36px away in the full view. If a price alert is active, expect this dot to appear somewhere down the left edge of the chart at the alert's price height — that's correct behavior, not a rail alignment defect.

The rail's row count grew substantially this session (Patterns/Elliott Waves/Cycles and Brushes/Arrows merged into existing groups, on top of the pre-existing groups) — enough that its total content height can exceed the space its `h-full` gives it, overflowing past the chart's own boundary. The panel now adds `overflow-y-auto overflow-x-hidden scrollbar-none` under the same `fullscreenDrawingOnly || groupedWorkspaceRail` condition that already gates `h-full` — i.e. scroll applies any time the compact rail is in play, fullscreen or not (initially shipped non-fullscreen-only, then widened to fullscreen too once it was confirmed the row count overflows there as well). `scrollbar-none` (the `tailwind-scrollbar` plugin, same utility `AppSidebar.jsx` already uses for its own scrollable nav) hides the scrollbar chrome while leaving the element fully wheel/touch-scrollable — the rail scrolls, it just doesn't show a track. This is safe to scope to just the panel div because the flyouts it opens (`Flyout`/`TOOL_GROUPS.map` popovers, the tool-editor bar, etc.) are siblings rendered *after* the panel's closing `</div>`, not children of it — they're laid out by the outer `flex items-start` row wrapper, so scrolling the rail's own button list doesn't clip or reposition any open popover.

The rail's bottom drawing-save-status bar (a thin `h-1.5` strip: green saved / amber pulsing while saving / red when a save fell back to local-only after a failed server sync) was removed from the rail entirely at request — it's no longer rendered anywhere. `drawingSaveStatus` remains a prop on `ReplayPanel` (still passed down from `MarketChart.jsx`, still tracks the real save state) but nothing in `ReplayPanel.jsx` reads it now, so there is currently **no visual indicator** if a drawing save silently falls back to local-only storage (the "Saved on this device; server sync failed" case) — a user in that state has no on-screen cue their drawings aren't actually synced. Reintroduce a status indicator (elsewhere in the UI, not necessarily this rail) if that gap is reported as an actual problem.

# Touch / mobile drawing support

Every drawing gesture (create, drag-move, resize-handle drag) previously only worked with a mouse: `MarketChart.jsx`'s creation/drag/resize state machine (`handleMouseDown`/`handleMouseMove`/`handleMouseUp`) was wired exclusively to `mousedown`/`mousemove`/`mouseup`. Panning/zooming the chart itself still worked on touch (`lightweight-charts` handles that natively, independent of this code), but actually drawing a Long/Short box — or any other tool — did nothing on a touchscreen.

The fix reuses the exact same handler logic rather than duplicating it: `handleTouchStart`/`handleTouchMove`/`handleTouchEnd` wrap the single active touch point (`event.touches[0]`, or `event.changedTouches[0]` on end) into a minimal object shaped like the subset of `MouseEvent` these handlers actually read (`target`, `clientX`, `clientY`, `preventDefault()`, `stopPropagation()` — nothing else), then call straight into `handleMouseDown`/`handleMouseMove`/`handleMouseUp`. This mirrors how `lightweight-charts` itself already normalizes touch internally, and means any future change to the mouse handlers' behavior automatically applies to touch too — there's no second copy of the drawing state machine to keep in sync.

- **Multi-touch is ignored** (`event.touches.length !== 1` returns early, before calling into the shared handler and before any `preventDefault`) — a two-finger pinch falls straight through, untouched, to `lightweight-charts`' own native pinch-zoom, exactly as before this change.
- **`touchmove` is registered `{ passive: false }`** — Chrome defaults `touchmove`/`touchstart` listeners on `window`/`document` to passive (for scroll perf), which would silently no-op every `event.preventDefault()` call inside the shared handler (the ones that stop the page from scrolling mid-drag) and log a console warning instead of actually blocking the scroll. Registering non-passive is what makes those existing `preventDefault()` calls (already present in the mouse-only code, for tool placement/dragging/resizing) actually take effect on touch.
- **Double-tap finishes multi-point tools** (Path, Brush, patterns, Elliott waves, etc. — anything in `MULTI_POINT_TOOL_TYPES`), since touch has no `dblclick` equivalent to hook into. `handleTouchEnd` tracks the last tap's timestamp in a closure-local variable (not a ref/state — this effect's cleanup already tears the whole listener down on unmount, so there's nothing to reset) and calls the existing `handleDoubleClick` if a second tap lands within 350ms.
- **Hit-test tolerance widens for touch.** `hitTestDrawing`'s line/path-segment/point distance checks and `hitTestResizeHandle`'s handle-corner checks used a flat 8px tolerance (fine for a mouse cursor, too tight for a fingertip). Both now read `isTouchInputRef.current` (set `true` the first time any `touchstart` fires, never reset back to `false` — once a session has shown it's touch-capable, keep the larger, friendlier tolerance for the rest of that session, including if the user also has a mouse/trackpad) and use ~16px instead of 8px when true. This only ever *enlarges* hit areas, so it can make an adjacent drawing on a dense chart slightly more ambiguous to pick between, but never regresses correctness.
- The **tool-group chevron** fix (always partially visible instead of hover-only, see above) is the other half of "tools actually work on mobile" — without it, the touch/hit-test work above still wouldn't let a mobile user ever select Short over the group's default-ready Long, since there'd be no way to open the picker.

**Known gap, not fixed yet:** `TopToolEditorBar` (`ReplayPanel.jsx`, the floating style/template bar that appears when a drawing is selected or a position tool is being configured — Templates, Color, Width, Line style, Settings, Duplicate, Delete, Lock, ~9-10 icon buttons for a Long/Short position) is a `flex-nowrap` row with `overflow-visible`, inside a container whose `maxWidth` is `Math.max(overlayWidth - 164, 140)`. On a narrow mobile chart this clamps to the 140px floor while the actual button row needs ~400px+, so the buttons visually spill out past the panel's own rounded border instead of clipping or scrolling — likely running off the edge of the screen, several controls unreachable by touch. The obvious fix (`overflow-x-auto` on the row) isn't safe to apply blind: CSS forces the paired `overflow-y` to also stop being `visible` once `overflow-x` isn't, which would clip every button's dropdown submenu (color picker, width picker, line-style, settings, presets) since those are `position: absolute` popouts that render *below* the row, not `document.body` portals like `RailTooltipPortal`. A real fix needs those submenus portal-ized first (same pattern as the rail tooltips) before the row itself can safely scroll — flagged here rather than guessed at blind, since a wrong fix here trades one mobile bug for a worse one (unreachable submenus instead of unreachable buttons).
