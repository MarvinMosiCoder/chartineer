# Backtesting and Orders

## Purpose

Backtesting maintains a simulated account, named sessions, pending/open/closed positions, risk levels, fees, PnL, snapshots, and trade records. It never places real exchange orders.

| Route group/file | Responsibility |
|---|---|
| `/market-backtest/account` | Account/session/position state |
| `/market-backtest/sessions*` | Start/end sessions |
| `/market-backtest/positions*` | Open, edit risk, trigger, cancel, close, snapshot |
| `/market-backtest/order-history` | Combined trade-fill + cancelled-order history for `PositionsPanel.jsx`'s Order History tab |
| `/market-backtest/reset` | Reset simulated account |
| `MarketBacktestController.php` | Validation, authorization, transactional calculations |
| `MarketBacktestAccount/Session/Position/Trade/Snapshot.php` | Domain records/relations |
| `MarketChart.jsx`, `ReplayPanel.jsx`, `TraderNavbar.jsx` | Entry and account UI |
| `PositionsPanel.jsx` | Positions/Open Orders table below the chart |

## Data flow

1. `GET /market-backtest/account` returns the authenticated user's active simulated account.
2. A session groups positions/trades for a replay exercise.

`MarketChart.jsx`'s auto-load effect (`useEffect(() => { loadBacktestAccount(); }, [loadBacktestAccount])`, keyed off `[exchange, marketCategory, symbol, timeframe]`) can fire twice within milliseconds on initial mount — those four values can each settle via separate, near-simultaneous state updates while saved-symbol restoration resolves, giving the `useCallback` two distinct identities that land on the same final param tuple. A `lastAutoBacktestAccountKeyRef` dedupes back-to-back identical auto-reloads (skips the fetch if the joined `symbol|exchange|category|timeframe` key matches the last auto-fired one); it never applies to the explicit `loadBacktestAccount(executionPrice)` call after an order fills (that path always passes a non-null `price`, which bypasses the dedupe key entirely), and any genuine param change still always refetches.
3. Position submission sends market identity, side, order type, quantity/risk, entry, leverage, stop loss, and take profit as applicable.
4. The controller validates access and uses database transactions/locking for balance and position mutations.
5. Pending orders trigger when replay price reaches their condition.
6. Closing writes realized results and trade history; snapshots use controlled file storage.

All state-changing routes require `replay.access` and named throttles. Every route-model-bound session/position must be checked against the authenticated account.

Chart position lines are draggable. Pending entries and every active SL/TP update use `PUT /market-backtest/positions/{position}/risk`. Repricing an open entry intentionally edits the simulated fill while preserving quantity: the server locks the account, position, and opening trade; recalculates notional, margin, entry fee, cash, fees, and PnL inputs; and rejects the complete transaction when funds or SL/TP ordering are invalid.

## Auto-trigger/close monitoring runs in live mode too, not only Replay

`MarketChart.jsx`'s two client-side effects that auto-trigger pending entries and auto-close open positions (calling `handleCloseBacktestPositionRef`/`triggerBacktestPositionRef` for plain SL/TP, or `POST /market-backtest/positions/{position}/process-candle` — `processPositionCandle()` — for any position carrying a `liquidationPrice`/trailing-stop/break-even/partial-TP — see the "managed vs. simple positions" note further down for why that's no longer *every* position) used to be gated on `replayMode` and keyed off `executionCandle`, which is `null` whenever `!replayMode`. A position opened while just watching the live chart (not scrubbing through Replay) therefore had no client-side monitor ever checking its SL/TP/liquidation against incoming price — it only closed on a manual action. `positionMonitorCandle` now resolves to `executionCandle` in Replay or to the latest live/forming candle (`visibleCandles.at(-1)`, the same running high/low/close the OHLC legend and price alerts already read) otherwise, and both effects key off that instead, so the same monitoring runs continuously in live mode.

The managed/`process-candle` branch's dedup key changed from `${id}:${candleTime}:managed` to `${id}:${candleTime}:${high}:${low}:managed`. In Replay, `candleTime` alone was enough to dedupe (one call per historical, already-final candle). In live mode the "current candle" keeps the same `candleTime` for its entire duration while ticks keep extending its `high`/`low`, so keying on time alone would have processed it only once, using whatever partial high/low existed on the first tick — under-checking trailing-stop/liquidation/SL/TP for the rest of that bar. Keying on the running high/low instead re-fires exactly when a tick sets a new extreme (the only case that could newly cross a level), and is a no-op cost the rest of the time since price ticks that don't move the extremes can't produce a new crossing.

**High/low-keyed dedup alone let overlapping requests for the same position race** — found live: a fast-moving market produces a new high/low (and therefore a new dedup key) on nearly every tick, so a fresh `process-candle` request could fire before the previous one for the *same position* had even resolved. Once one of those overlapping requests closed the position server-side, every other one already in flight reached `processPositionCandle()`'s `->where('status', 'open')->firstOrFail()` after the status had already flipped, threw `ModelNotFoundException`, and the frontend displayed that raw exception text (`No query results for model [App\Models\MarketBacktestPosition]`) via `setBacktestError` — a backend implementation detail leaking straight into the order panel, and easy to misread as "the SL/TP didn't fire" when in most cases it actually had.

`pendingManagedPositionRef` (a `Set<positionId>`, alongside `autoClosedPositionRef`) now gates the loop: a position already has an in-flight request is skipped outright, checked before the high/low-keyed dedup and cleared in a `finally` regardless of outcome. This bounds concurrency to one `process-candle` call per position at a time without losing the high/low re-check granularity above — a skipped tick's snapshot is simply picked up by the next effect run once the in-flight request clears. The catch block also now swallows a `404` specifically (the exact shape this race produces) rather than surfacing it through `setBacktestError` — a losing race against the app's own other check is not a failure worth alarming the trader over; any other status code still surfaces normally.

**Replay bars are checked one at a time by `replayIndex`, but `replayIndex` doesn't only ever advance by one.** Both monitoring effects derive their check from `positionMonitorCandle`, which in Replay is `allCandles[replayIndex]` — a single bar. Step Forward/Play always move `replayIndex` by exactly 1, so that single bar was always the right (and only) one to check. But `setReplayIndex` also gets called with an arbitrary target index from several other places — dragging/seeking the replay timeline (`setReplayPointFromCoordinates`), the Replay price-pick gesture, and jumping back to a saved progress point — any of which can move `replayIndex` by dozens or thousands of bars in one state update. Every one of those older, in-between bars was never looked at by either effect: only the single bar the playhead landed on. **A SL/TP/liquidation level crossed only on one of those skipped bars was gone for good** — a later bar's own high/low no longer reaches a level price has already moved back away from, so the position stayed open indefinitely despite genuinely having been hit, with no self-healing path (matching the exact user report this was diagnosed from: an open short position's SL badge clearly below a candle wick on the chart, yet still open with Replay's playhead already well past it). This reproduces the same "position stuck open" *symptom* as the stale-response bug just above, from an entirely different, non-overlapping *cause* — confirmed by checking the actual reported position's `adverse_price` (the running worst-price tracker `processPositionCandle()` maintains server-side, itself only ever updated from bars the server actually received) directly via `php artisan tinker`: it sat further from the stop level than the stop distance itself, meaning the server-recorded history never saw that price at all — consistent with an entire bar's high/low never having been sent, not a comparison bug in the trigger logic itself.

`lastMonitoredReplayIndexRef` now tracks the last `replayIndex` either monitoring effect actually checked. When the new `replayIndex` is more than one bar past it, `candlesToCheck` becomes every bar in that gap (`allCandles.slice(lastIndex + 1, replayIndex + 1)`, bounded to the most recent `POSITION_MONITOR_GAP_LIMIT` (500) bars of the gap so an extreme jump can't queue thousands of sequential requests) instead of just the landing bar, and both the managed (`process-candle`) and plain client-side SL/TP paths iterate it — per position, in bar order, each bar filtered to strictly after that position's own `openedAtTime` (a shared gap can span bars from before a position existed if it was opened partway through it), stopping early for a position the moment it closes rather than continuing to check its now-irrelevant remaining bars. The ref resets to `null` on symbol, timeframe, or Replay-mode change, so a stale index left over from a different chart context can never produce a bogus multi-thousand-bar gap-fill the next time a position is opened. Non-Replay (live) mode is unaffected — `positionMonitorCandle` there is always the single latest live/forming candle, there's no "seeking" concept, and `candlesToCheck` is always just that one candle.

**The pending-order auto-trigger effect (the one right above this one, filling limit/trigger/conditional orders once price reaches their entry) was deliberately left on the old single-bar check** — it has the identical structural gap (a skipped bar's entry-price crossing is never retroactively caught), but a missed *entry* just leaves an order sitting pending instead of silently losing money on an open position, so it's a smaller, self-evident failure mode (the order is still visibly there, uncorrupted, waiting) rather than a silently-stuck-open position. If this is ever reported as an actual problem, apply the same `lastMonitoredReplayIndexRef`/`candlesToCheck` gap-fill there too — the shapes are structurally identical, it just wasn't done pre-emptively for a path nobody had actually hit yet.

**Found and fixed: `managedPositions`/`triggeredPositions` were mutually exclusive within a single effect run, silently starving plain SL/TP checks on some positions.** The monitoring effect splits a symbol's open positions into two groups — "managed" (anything with `liquidationPrice`/trailing-stop/break-even/partial-TP, handled server-side via `process-candle`) and "simple" (plain SL/TP, compared client-side against `candle.high`/`low`). The code used to build `managedPositions` first and, if that array was non-empty, process it and `return` immediately — `triggeredPositions` (the simple group) was computed and checked only when `managedPositions` was *empty*. Reported as "Enter Position — TP/SL doesn't trigger a close." Root cause: every non-Spot position always gets a truthy `liquidation_price` (`MarketBacktestController::openPosition()`, `$isSpot ? null : $this->liquidationPrice(...)`, even at 1× leverage), so before Spot positions existed `triggeredPositions` was permanently empty and this `return` was unreachable dead code — every open position was always "managed." Once Spot positions shipped (`liquidation_price` is `null` for those — see "Spot support in the order ticket" below), a Spot position's plain TP/SL became reachable simple-path code for the first time, but only got checked when it was the *only* open position on that symbol: any other, already-managed position open on the same symbol (a leveraged Long/Short, or any position with trailing-stop/break-even/partial-TP set) made the early `return` fire first and skip the simple check entirely, every effect run, for as long as that managed position stayed open — the Spot position's TP/SL would never close it no matter how far price moved past the trigger. Fixed by computing both groups unconditionally and running `processManagedPositions()`/`closeTriggeredPositions()` side by side under one shared `cancelled` flag and cleanup, instead of one gating the other. While in this code, the simple/client-side auto-close (`handleCloseBacktestPosition`) also gained an optional `closeReason` argument (`'stop_loss'`/`'take_profit'`, forwarded as `close_reason` to `POST /market-backtest/positions/{id}/close`) — previously every simple auto-close landed in the trade journal labeled `manual` (the server's default when `close_reason` is omitted) since the field was never sent, same as a real manual Close button click; the managed/`process-candle` path already labels these correctly (`stop_loss`/`take_profit`/`liquidation`) and simple positions now match.

**Diagnosing this went through a wrong turn worth recording:** the first hypothesis, given the earlier stale-response fix above, was that `pendingManagedPositionRef`'s in-flight guard was silently dropping an overlapping candle-check during fast Replay playback. That guard only skips a *specific* position while its own request is still in flight — under normal `playbackSpeed` (≥250ms between bars) a request resolves well within one tick, and Play always advances `replayIndex` by exactly 1 (confirmed by reading the interval in the Play effect), so that path was ruled out before writing any fix. Checking `adverse_price` for the actually-reported position via `php artisan tinker` (see above) is what pointed at "an entire bar's data never reached the server" instead — worth the extra minute over guessing, since the two would have needed different fixes.

**A successful close response must be applied unconditionally, never gated on the effect's own `cancelled` flag.** This was the actual cause of positions appearing to "never close" even after the two fixes above — confirmed live: the server had genuinely closed the position (`status = 'closed'`, `close_reason = 'stop_loss'` in the database) while the chart kept rendering it as open indefinitely. The inline `processManagedPositions()` closure originally read `if (!cancelled) setBacktestAccount(nextAccount);` before applying a response — `cancelled` here means only "a newer candle/tick has already re-run this effect," which happens on essentially every tick during active replay or live streaming, not "this component unmounted." Once a request's response arrived after a newer effect run had already started, the guard discarded it — including a *successful* close. With the account state never updated, the position stayed in `openPositions` forever on the frontend, and every subsequent re-check hit the already-closed position server-side and 404'd (silently, per the fix above), so nothing ever corrected it — a stale response and a suppressed error combined into a permanently stuck UI state with no self-healing path. `setBacktestAccount(nextAccount)` (and the `setBacktestError` call in the catch branch) are no longer gated on `cancelled` — only *starting a new* request from a stale invocation still checks it (`if (cancelled) continue;`, before the in-flight/dedup checks), since that's the part actually worth skipping. `handleCloseBacktestPosition`/`handleTriggerBacktestPosition` (the plain, non-managed close/trigger paths) never had this bug — they apply their response unconditionally already; only this effect's own inline closure had the extra, incorrect guard. If a position was already stuck open in an open browser tab before this fix shipped, reloading the page re-fetches the account from the server and corrects it — the underlying data was never wrong, only the tab's in-memory copy of it.

## Order ticket UI (`ReplayPanel.jsx`)

The "Enter Position" flyout uses underline-style tabs (not boxed buttons) for Market/Limit/Trigger, a taller (`h-10`) full-width Long/Short segmented toggle, and a 25/50/75/100% quick-select row under the margin/leverage inputs (`handleMarginPercentClick`, computed from `backtestMetrics.cashBalance * pct` converted to the display currency via `quoteToDisplayAmount`). The order-submit action is a single full-width `h-11` button at the bottom of the section (below the Est profit/loss row), labeled `Open Long`/`Open Short` or `Place Long/Short Order` for pending order types — it is no longer a small icon button embedded in the margin/leverage input row.

**Leverage modal.** Leverage is no longer a free-text input — clicking the leverage field (now a button showing e.g. `20x`) opens `LeverageModal` (defined just above the `ReplayPanel` export in the same file), a `createPortal`-into-`document.body` dialog with a −/+ stepper, a native `<input type="range">` (1x–125x, matching `isLeverageValid`'s existing validated ceiling — not the 150x some exchanges show, since 125x is this app's real cap), tick labels at 6 evenly-spaced points, an info list (max position size at the currently-dragged leverage, a note that changing it also affects open positions/orders, and a liquidation-risk warning), and a Confirm button. The modal holds its own local `draft` state and only calls `onConfirm(draft)` (which sets `orderLeverage` and closes the modal) on Confirm — dragging the slider or the stepper does not touch `orderLeverage` until confirmed. The Confirm button uses the app's theme blue (`#2962ff`, the same accent as the order-type tab underline), not the amber/yellow some reference exchange UIs use for this button.

**Display currency moved out of the main flow, into a settings popover.** The Currency/PHP-rate pair used to render as two always-visible fields between the Available Balance card and the order type tabs — a display-only convenience (converts the same USDT figures to a PHP equivalent for Philippine users; it never changes what's actually submitted) that doesn't exist at all in the reference exchange layouts this ticket was redesigned against, and ate a full row for something most traders touch once and never again. A small gear icon (`Settings`, lucide) now sits next to the cash balance inside that same card; clicking it opens a `showCurrencySettings`-gated popover (`z-[10030]`, a backdrop-click-to-close button underneath at `z-[10029]`, matching this file's existing rail-flyout popover convention) holding the exact same two fields. No state, storage key, or currency-conversion logic changed — `displayCurrency`/`phpRate` and their `localStorage` persistence are untouched; only where the controls render moved.

**TP/SL is a checkbox-gated section with two separate detail links — `Advanced` for TP/SL trigger detail, `Managed Exits` for trailing-stop/break-even/partial-close** — replacing the previous always-three-visible-fields layout. This went through two rejected iterations before landing here: the first put trail/break-even/partial behind the `Advanced` link (rejected — the reference exchange's own "Advanced" is a TP/SL trigger-detail dialog, not a managed-exits one), and the second combined the leverage button with an "Isolated ·" prefix into one control (rejected — the reference shows margin-mode and leverage as two independent pill buttons). Both are now split apart correctly; see below.
- **`tpSlEnabled`** (state) gates a two-column SL/TP row rendered inside the same bordered card as the checkbox; unchecking calls `resetTpSlDraft()` (clears `orderStopLoss`/`orderStopLossPnl`/`orderTakeProfit`/`orderTakeProfitPnl` and resets both modes to `'price'`) so a value that was set and then hidden can never be submitted invisibly. `Entry`/`Price` is unaffected and stays in its own always-visible row above — it isn't part of the optional TP/SL concept, it's the order price itself.
- **Fixed: SL/TP used to be submitted even with the checkbox unchecked.** `plannedStopLoss`/`plannedTakeProfit` always fell back to `entryPrice * 0.99`/`* 1.01` whenever the price fields were empty, and that fallback was sent to `onOpenBacktestPosition` unconditionally — so an order placed with `TP / SL` left unchecked still silently got a ~1%-away stop and target. Both are now `null` whenever `!tpSlEnabled`, so unchecking the box really does mean no SL/TP is submitted; the risk/reward preview row (Risk/Reward/R:R/Est profit/Est loss) shows `---` in that state instead of numbers that wouldn't match what actually gets sent. The 1%-fallback itself is unchanged for when the box *is* checked but a price was left blank.
- **Every place that already cleared the SL/TP draft** (the fullscreen-exit effect, `orderDraftClearRequest`, `toggleGroup`, `removeOrderDraft`, the checkbox's own uncheck handler) now calls the shared `resetTpSlDraft()` helper instead of duplicating the field list, so the PnL-mode fields can't drift out of sync with the price fields. Conversely, the effect that watches `orderLineDraftPatch` (dragging a draft SL/TP line directly on the chart) sets that side's mode back to `'price'` and `tpSlEnabled(true)` when the drag sets a `kind: 'sl'`/`'tp'` value — a value arriving from the chart is always a concrete price, so it should never be interpreted as PnL%.
- **`Advanced`** opens `AdvancedTpSlModal` — the reference exchange's actual "Take Profit / Stop Loss" dialog shape: one section per side (Take Profit, Stop Loss), each with a `Price` / `PnL %` segmented toggle and a single input whose meaning changes with the toggle, plus a live-computed preview line underneath (price → estimated PnL%, or PnL% → estimated trigger price, via `estimatePriceFromPnlPercent`/`estimatePnlPercentFromPrice`, pure display helpers — not authoritative). The reference's own Mark-Price/Last-Price trigger-type toggle was deliberately left out, same reasoning as the Cross/Isolated toggle below: this engine has no live mark price, only one historical/replay price stream, so a trigger-type switch would imply a distinction that doesn't exist here. **PnL % mode is real, not cosmetic** — `stop_loss_pnl_percent`/`take_profit_pnl_percent` are new validated inputs on `POST /market-backtest/positions` (`gt:0`, capped at `max:95` for stop loss and `max:100000` for take profit), converted server-side by `MarketBacktestController::priceFromPnlPercent($side, $entryPrice, $leverage, $pnlPercent, $isLoss)` into the same `stop_loss`/`take_profit` price columns the price-mode path already writes — `price = entry * (1 ± pnlPercent / (100 * leverage))`, sign depending on side and whether it's a loss. The conversion happens once, at order-creation time, using the leverage locked in for that position, so the stored trigger is an exact price like any other — nothing downstream (monitoring, chart badges, `process-candle`) needs to know or care that it originated as a PnL% target. When a side's mode is `'pnl'`, `submitBacktestOrder` sends only `stop_loss_pnl_percent`/`take_profit_pnl_percent` for that side (never a redundant computed price) so the backend conversion is the single source of truth, not a client-side approximation. `updatePositionRisk` (dragging an existing open position's SL/TP line) is unaffected — that flow only ever sets an absolute price, since dragging a line on the chart has no PnL% concept.
- **`Managed Exits`** (with a live count badge, e.g. `Managed Exits (2)`, when any of the three fields has a value) opens `ManagedExitsModal` — the same component and content previously reachable from `Advanced` (Trailing stop % / Break-even % / Partial close %, each its own `AdvancedExitField` checkbox-reveals-input row, a read-only Buy/Long–Sell/Short bar for context, no staged draft/Cancel), just renamed and moved to its own trigger so it no longer collides with the reference exchange's actual meaning of "Advanced".

**Margin mode and leverage are two separate pill buttons, not one combined control.** First built as a single button reading `Isolated · 20x` (rejected — the reference screenshot shows "Cross"/"Isolated" and the leverage figure as two independent pills side by side). `liquidationPrice()` only implements the isolated-margin formula, and `PositionsPanel.jsx`'s Order History tab already documents that "every position badge always reads **Isolated** — neither concept exists anywhere in this app's schema or engine (no partial/reduce-only close, no cross-margin mode)" for futures. A functional Cross/Isolated switch would need real cross-margin accounting (shared liquidation risk across positions) that doesn't exist here, so the margin-mode pill is `disabled`, always reads **Isolated**, and carries a `title` explaining why — it matches the reference's visual layout (two pills in a `grid-cols-2` row, margin amount input full-width below) without implying a capability the engine doesn't have. The leverage pill next to it is unchanged in behavior — still opens `LeverageModal` — just no longer sharing a button with the margin-mode label.

The Isolated and leverage explanations use `IconTooltipButton`, whose outer wrapper owns hover/focus events so tooltips still work for the disabled Isolated button. These controls pass grid sizing through `wrapperClassName` and keep border/background styling on the inner button only; applying the full visual class list to both elements produces a visible nested double border.

## Spot support in the order ticket

Spot markets were originally rendered with the exact same futures-shaped ticket described above — Long/Short toggle, Isolated pill, leverage — despite Spot having no leverage, no margin, and no shorting in real trading. `openPosition()` accepted a `category` field but never acted on it, so a "spot" order was silently booked as a leveraged, liquidatable, potentially-short position.

`ReplayPanel.jsx` now receives `marketCategory` as a prop (threaded from `MarketChart.jsx`'s existing `marketCategory` state — it was already sent to the backend on every submit, just never forwarded into the ticket component for UI branching). When it's `'spot'`, the ticket is buy-only: the Long/Short toggle is replaced with a static "Buy" indicator, the Isolated and leverage pills don't render, the notional input reads "amount" instead of "margin", and the submit button reads "Buy". `orderSide`/`orderLeverage` are reset to `'long'`/`'1'` whenever `marketCategory` becomes `'spot'`, so a leverage or Short selection left over from a previously-charted futures symbol can't silently reach the backend and get rejected. The Alt+S quick-short hotkey (`MarketChart.jsx`) is a no-op for spot; Alt+L still quick-buys.

Server-side, `market_backtest_positions` gained a `category` column (migration `add_category_to_market_backtest_positions`) — `MarketBacktestSession.market_category` can't stand in for this, since `getActiveSession()` returns the account's latest active session regardless of symbol/category, so a session can span mixed categories across trades. `openPosition()` rejects `side: 'short'` or `leverage > 1` for a spot order with a 422 rather than silently coercing it, otherwise forces `leverage = 1` and skips `liquidationPrice()` (stored as `null`). No other simulation logic changed — `closePosition()`, `processPositionCandle()` (PnL, TP/SL, trailing stop, break-even, and the liquidation check above, which already null-guards on `liquidation_price`), and the PnL%-based TP/SL conversion (`priceFromPnlPercent`) were all already correct for a long-only position at `leverage = 1`; category only needed to be persisted and enforced, not built into those formulas.

Every place that renders "Long"/"Short" off a position or order (`PositionsPanel.jsx`'s five tabs, `TradeReport.jsx`'s journal, and the price-line labels `MarketChart.jsx` draws directly on the chart for a position's entry/SL/TP lines and the pre-submit order draft) now checks `category === 'spot'` first and shows "Buy" instead — same underlying `side` value (`'long'`), different label. The Isolated/leverage badges in Order History and Trade History are hidden for spot rows for the same reason the ticket hides them. `estimateLiquidationPrice()` (`PositionsPanel.jsx`) returns `null` for spot so the Liq. Price column reads `---` rather than computing a meaningless isolated-margin estimate at 1x.

Verified end-to-end against a live position (not just static review): direct API calls confirmed `side: 'short'` and `leverage > 1` are both rejected with the specific 422 messages for a spot order, and a valid spot buy creates a position with `category: 'spot'`, `leverage: 1`, `liquidationPrice: null`, correct quantity/fee math, and a session whose `marketCategory` matches. The resulting position rendered "Buy" correctly in the positions table — the chart's own in-canvas position-line label ("LONG OPEN ...") was the one spot-labeling gap static review missed, since it's built from three separate `position.side === 'short' ? 'SHORT' : 'LONG'` sites in `MarketChart.jsx` (the shared `buildLine()` helper, the open-position entry/SL/TP line label, and the pre-submit order-draft line label) rather than going through `PositionsPanel.jsx`'s helper.

## Positions panel (`PositionsPanel.jsx`)

A tabbed table renders below the chart (non-fullscreen only — gated on `!isFullscreen` where it's rendered in `MarketChart.jsx`, after the `ml-[52px]` chart wrapper closes but still inside the outer bordered chart frame, so it spans the full chart width). `TABS` in `PositionsPanel.jsx` has five tabs — Positions, Open Orders, Order History, Position History, Trade History — and **all five are now wired to real data**; the earlier "Coming soon" stub fallback (`!['positions', 'openOrders', 'orderHistory', 'tradeHistory', 'positionHistory'].includes(activeTab)`) is left in place only as a safety net for a future tab added without its own render branch, not because anything currently falls through to it. **Assets, Bots, and Transaction History were deliberately left out of `TABS` entirely** (not even as stubs) — they don't map to any concept this app already tracks here (bots don't exist at all; account balance/assets are shown elsewhere, e.g. the trader Assets panel referenced in `## Custom demo balance` below; transaction history wasn't wanted alongside the others). Add a tab back only once its underlying dataset actually exists somewhere in this app; if reintroducing Assets specifically, decide first whether it should link to/reuse the existing Assets panel rather than duplicating it here.

**Positions tab** lists `backtestAccount.openPositions` (all symbols, not filtered to the active chart's symbol — a real multi-position table, unlike the "Open Positions" list still inside `ReplayPanel.jsx`'s Enter Position flyout, which stays filtered to `position.symbol === symbol`). Columns: Symbol, Side, Size, Entry Price, Mark Price, PnL (ROI%), Margin, Liq. Price (est.), TP/SL, Close.

- **Mark Price / live PnL only exist for the currently active chart symbol.** This backtest engine only advances a live/replay price for whichever symbol is currently charted (`executionPrice`) — the account-refresh effect in `MarketChart.jsx` only recomputes `unrealizedPnl` for positions matching `symbol`, leaving other symbols' `unrealizedPnl` as `null` (see the effect right after `indicatorPaneTops`). `PositionsPanel` shows `---` for Mark Price and PnL/ROI on any row whose `position.symbol !== symbol`, rather than fabricating a stale or borrowed price.
- **Close is disabled for non-active-symbol rows** for the same reason: `handleCloseBacktestPosition` needs a real execution price for that position's own symbol, which only exists while that symbol is the active chart. The disabled button's `title` tells the user to switch symbol first, rather than silently no-opping or (worse) closing at the wrong symbol's price.
- **Liq. Price is a display-only estimate**, not an enforced value — this backtest engine has no liquidation logic anywhere (client or server); positions only close via explicit user action or SL/TP triggers. The estimate is a standard isolated-margin approximation (`entry * (1 ∓ 1/leverage)`) ignoring fees and maintenance margin, labeled "(est.)" so it isn't mistaken for a real, enforced figure.

**Open Orders tab** lists `backtestAccount.pendingPositions` (also all symbols). Columns: Symbol, Side, Trigger Price, Size, Margin, SL, TP, Cancel. Cancel has no symbol restriction — `handleCancelBacktestPosition` just removes the pending order server-side, no execution price needed.

Both tabs reuse the exact same `onClosePosition`/`onCancelOrder` handlers (`handleCloseBacktestPosition`/`handleCancelBacktestPosition` in `MarketChart.jsx`) already used by `ReplayPanel.jsx`'s flyout lists — this is a second render surface for the same account state and actions, not a parallel data path.

**Order History tab** fetches `GET /market-backtest/order-history` (`MarketBacktestController::orderHistory()`) lazily — only when the tab becomes active (`useEffect` keyed on `activeTab`/`activeSessionId` in `PositionsPanel.jsx`), scoped to the active session if one exists. This is a **new** endpoint and, unlike `buildPayload()`'s `trades` (last-30, all-symbols, used for chart trade markers), it exists specifically to answer "what happened to every order I placed", including ones that never filled:

- **Each row is one order-lifecycle event, not one position.** A single round-trip position produces two separate rows — an `open` trade and a `close` trade — matching the reference exchange's own history view (and `MarketBacktestTrade`'s existing one-row-per-fill shape). A pending order that got cancelled before it could fill produces one synthetic row built directly from the `MarketBacktestPosition` (`status = 'cancelled'`) instead, since **cancelled orders never create a `MarketBacktestTrade` row** (`cancelPosition()` only flips the position's status) — `orderHistory()` unions both sources in PHP (not a SQL `UNION`) and sorts by timestamp before truncating to `limit` (default 50, max 100).
- **`order_type` is a new column** (`market_backtest_positions.order_type`, migration `2026_08_12_000001_add_order_type_to_market_backtest_positions`, nullable string). Before this, `openPosition()` validated an incoming `order_type` request field (`market|conditional|limit|trigger`) but discarded it — it's now persisted on the position at creation. **Positions created before this migration have `order_type = null`**; both the controller (`?? 'market'` for trade rows, `?? 'limit'` for cancelled rows) and the frontend (`ORDER_TYPE_LABELS[order.orderType] ?? ORDER_TYPE_LABELS.market`) fall back sensibly rather than showing a blank Type column for old data.
- **Reduce Only is always `false`/`'No'`** and every futures position badge always reads **Isolated** — neither concept exists anywhere in this app's schema or engine (no partial/reduce-only close, no cross-margin mode), so these aren't real per-order flags, just fixed labels matching what the app actually does in every case. Don't read them as live data. Spot rows (`order.category === 'spot'`) skip both the Isolated and leverage badges entirely — see "Spot support in the order ticket" above.
- **Type/Price display mirrors how fills actually work here**: `triggerPosition()` fills a pending limit/trigger order at exactly its stored `entry_price` (no slippage simulation), so a filled limit order's Avg Price and target Price columns are identical by construction — this isn't a coincidence in the data, it's how `MarketBacktestController::triggerPosition()` (`app/Http/Controllers/MarketBacktestController.php:573`) works. Market orders show `Market` in the second Price line (`order.targetPrice` is `null` whenever `orderType === 'market'`) instead of a target figure, since a market order has no separate trigger price.
- The Symbol cell's leverage/SL/TP badges are read straight off the position (`getPositionLeverage()`, `stop_loss`/`take_profit !== null`) — for trade rows this means eager-loading the trade's `position` relation (`->with('position:id,order_type,leverage,stop_loss,take_profit')`), since none of those fields live on `MarketBacktestTrade` itself.

**Trade History tab reuses the exact same `/market-backtest/order-history` fetch** as Order History — no second network call. `PositionsPanel.jsx`'s data-fetch `useEffect` triggers on either `activeTab === 'orderHistory' || activeTab === 'tradeHistory'`, and the Trade History table simply filters the already-fetched `orderHistory` list to `order.status !== 'cancelled'` at render time and shows a different column set (Futures, Date, Side, Average Price, Volume, Closed Value, Realized PnL, Fee, Taker/Maker — no Type/Expiration, Reduce Only, or Status column, since every row here is by definition a completed fill). Two derived-only values, computed client-side, not sent by the backend:

- **Volume's base-asset ticker** (`getBaseAsset`) strips the account's `quoteCurrency` suffix off the symbol (`SNDKUSDT` + `USDT` → `SNDK`) — a plain string-suffix strip, not a lookup against real per-symbol base/quote metadata (which this endpoint doesn't carry). Every symbol traded in this app is USDT-margined today, so this always resolves correctly in practice; if a non-USDT-quoted symbol is ever tradable here, this needs a real base-asset field from the backend instead.
- **Taker/Maker** (`getTakerOrMaker`) is inferred, not stored: `close` actions are always `Taker` (this engine has no resting/limit close order — `closePosition()` always executes immediately at the given price), `open` actions are `Taker` for market orders and `Maker` for limit/trigger orders (mirroring real-exchange semantics: a market order takes existing liquidity, a resting limit/trigger order that later fills provided it). This is a reasonable inference from `order_type` + `action`, not a literal maker/taker fee-tier distinction this app's engine actually implements (fees are always the same flat `FEE_RATE` regardless of this label).

**Position History tab reuses the existing `GET /market-backtest/report` endpoint** (`MarketBacktestReportService`, otherwise powering [Trade reports](trade-reports-and-journals.md)) instead of a new one — closed positions already carry every field this card view needs (`entryPrice`, `exitPrice`, `pnl`, `pnlPercent`, `openedAtTime`, `closedAtTime`, `quantity`, `leverage`). Rendered as a card list (not a table) to match the reference layout: a header row (symbol, side, Isolated/leverage badges, "Closed" status) over a 4-column detail grid (Time Opened/Closed, Entry/Close Price, Position PnL/ROI, Max held/Closed Qty.). **"Max held" and "Closed Qty." always show the identical value** (`position.quantity`) — this engine has no partial-close/scale-in mechanism, so a position's size never changes between open and close; there is no separate "peak size" to track. No Details link/drill-down page exists for either Order History, Trade History, or Position History rows — all three intentionally omit that column rather than link to nowhere.

## Chart order lines (`ChartStage.jsx`'s `BacktestOrderOverlay`)

Each backtest TP/SL/entry line on the chart renders as **two adjacent SVG badges** rather than one combined text string: a solid-colored price/kind badge (e.g. green `TP 64,949.77`) and, for TP/SL lines only, a separate dark PnL badge (e.g. `+4.60`, text colored green/red by sign) immediately to its left. This split is driven by `renderedBacktestOrders` in `MarketChart.jsx` (`buildLine`'s `pnlText`/`pnlPositive` fields, computed via `estimatePositionNetPnl` for live pending/open positions or passed explicitly for the draft preview's `estimatedProfit`/`estimatedLoss`) — `item.label` holds only the price/kind text now, PnL is never concatenated into it. Entry/trigger lines have no PnL badge (`pnlText` stays `null`).

The line itself spans the full overlay width (`x2 = overlaySize.width`, not stopped short of the price-scale gutter) with a thin (`strokeWidth={0.5}`) dashed or solid stroke. Badges stay anchored near the right edge, just left of the price-scale gutter and the cancel "x" hotspot (`groupRightEdge` reserves extra space when `item.canCancel` so the PnL/price badges never overlap the cancel box). Hovering the cancel hotspot shows a pointer cursor: `MarketChart.jsx`'s `handleMouseMove` runs `hitTestBacktestOrder` on every move (not just on click) and sets `isHoveringBacktestOrderCancel` state, which `ChartStage.jsx` reads to override its wrapper `cursor` style to `'pointer'` (ranked below the existing drag/space/tool cursor states, above the default crosshair/default cursor).

**An open position's managed-exit rules are marked directly on its SL/TP badge labels, not only in a side list.** Before this, a position with trailing-stop, break-even, or partial-take-profit configured looked visually identical on the chart to one without — the only place any of it surfaced was a small text row in `ReplayPanel.jsx`'s Open Positions list, and that row was a ternary chain that showed at most one of the three settings and silently dropped partial-take-profit entirely. `renderedBacktestOrders` in `MarketChart.jsx` now builds the open position's SL/TP labels explicitly instead of relying on `buildLine`'s default `${side} ${KIND} ${price}` format: the SL badge gets a `TRAIL`/`BE`/`TRAIL+BE` prefix when `trailingStopPercent`/`breakEvenTriggerPercent` is set (e.g. `LONG TRAIL+BE SL 67,592.03`), and the TP badge gets a `· N% close` suffix when `partialTakeProfitPercent` is set **and** `partialTakeProfitExecuted` is still false (e.g. `LONG TP 68,840.84 · 50% close`) — checking the executed flag matters because after a partial exit fires, the position's *next* TP hit is a normal full close, and the badge must stop implying otherwise. `partialTakeProfitExecuted` had to be added to `buildPayload()`'s `openPositions` serialization first; it previously existed only in backend logic (`processPositionCandle()`'s partial-vs-full branch), never reaching the frontend. The Open Positions list badge was fixed the same session to join every active setting (`Trail 2% · BE 1% · Partial 50%`) instead of the old drop-one-silently ternary.

### Ghost SL/TP lines (unset levels)

`buildLine()` returns `null` for a `null` price, so a pending order or open position created without a stop or target used to render **no line at all** — there was nothing on the chart to grab, and the only way to add one was `PositionsPanel`'s TP/SL modal. Each missing level now falls back to a **ghost**: `buildGhostLine()` in the same `renderedBacktestOrders` memo, emitted as `sl ?? ghost` / `tp ?? ghost` for both the pending and open branches.

A ghost inverts the normal construction. Real lines go price → `priceToCoordinate()` → `y`; a ghost has **no price at all** and derives its `y` from the entry line's, via `ghostLineY(entryY, kind, side, mainPaneHeight)` in `utils.js`:

- 80px from the entry line, on the side that level belongs on (long TP above, long SL below, short inverted — remembering screen `y` grows downward).
- A **screen** distance, not a percentage of entry, deliberately: a percentage overlaps the entry line when zoomed out and lands off-pane when zoomed in, and a ghost you cannot grab is worse than no ghost.
- Clamped into the pane with an 8px margin, and **returns `null`** when the result would land within 20px of the entry line — no room to grab it there, so no ghost is drawn.
- Guards `entryY == null` explicitly, because `Number(null)` is `0`: `priceToCoordinate()` returns `null` for an entry it cannot place, and coercing that would pin a ghost to the top of a chart whose entry line is not even drawn.

The badge reads `SET SL` / `SET TP` with **no number**, and the whole group — line, badge, and handle — draws at 45% opacity (`<g opacity>` in `BacktestOrderOverlay`) with a fine `2,4` dash. Both matter: a price on an unset level reads as protection the trader never set. The right-edge grab handle is kept — faint along with everything else, but present, because it is the affordance that says the thing is draggable.

**Ghosts commit on drag only.** `dragBacktestOrderRef` carries `isGhost`/`startY`/`moved`; pointer travel under `GHOST_DRAG_THRESHOLD_PX` (3px) leaves the ghost completely alone and `handleMouseUp` skips the PUT entirely, so a stray click cannot put a stop loss on a live position. Past the threshold the existing path takes over unchanged: `updateLocalBacktestPositionLine` gives the position a real level in local state, the ghost stops being emitted, and a normal line renders in its place for the rest of the drag. There is no separate dragging-a-ghost render state.

**Wrong-side drags clamp, for ghosts and existing lines alike.** `clampRiskPrice(kind, side, entryPrice, price)` (`utils.js`) keeps a stop or target on the side of entry the server accepts, so an invalid level is unreachable rather than rejected on release. `updatePositionRisk` rejects a level that merely *equals* entry (`$stopLoss >= $entryPrice`), so the clamp lands at `entryPrice * (1 ∓ 0.0001)` — strictly inside, never on it. The epsilon is relative because prices here span sub-cent tokens to five-figure indices. `MarketBacktestPositionRiskTest` pins both halves server-side: equality is rejected, the epsilon value is accepted. This is a change to the pre-existing drag path too, which previously let a line go anywhere and relied on the 422.

Both new helpers are pure and live in `utils.js` precisely so they can be tested without a component harness: `tests/js/orderRiskLines.test.js` (`npm run test:order-risk-lines`, Node's built-in runner, same shape as `marketChartUtils.test.js`) covers the clamp's four side/kind combinations and its strictly-inside-entry guarantee, and `ghostLineY`'s offset direction, pane clamping, and the two `null` returns. Run it with `MarketBacktestPositionRiskTest` when touching either — the JS clamp exists only to satisfy the PHP validator, so the two suites pin opposite ends of the same rule.

`buildLine()` gained an `entryPrice` field so a drag can clamp without re-finding the position. Draft lines carry none and so pass through unclamped — the Enter Position ticket validates those itself.

Hovering any order line (ghost or real) sets `isHoveringBacktestOrderLine` → `ns-resize`. Cancel keeps precedence, since `hitTestBacktestOrder` returns its `action: 'cancel'` hit before it considers a line hit.

Out of scope, deliberately: clearing a set SL/TP back to none from the chart (matching the TP/SL modal's set/edit-only posture), and de-cluttering when several unprotected positions stack ghosts near each other at fixed pixel offsets. Design: [2026-08-29-chart-ghost-sl-tp-lines-design.md](../superpowers/specs/2026-08-29-chart-ghost-sl-tp-lines-design.md).

## Lifecycle toasts

`MarketChart.jsx` fires a toast (via `useToast()`/`handleToast`, the app-wide single-message `ToastContext`) for every position/order lifecycle transition: a pending order placed, an order filled (market fill or a pending limit/trigger auto-triggering), a pending order cancelled, and a position closed for every reason this app tracks (`manual`, `stop_loss`, `take_profit`, `partial_take_profit`, `liquidation`). Failed requests are unaffected — they still surface through the existing `setBacktestError` inline banner in `ReplayPanel.jsx`, never a toast.

`closePosition()` is the one place that needed a backend change: it now returns a `closedTrade` object (`positionId`, `symbol`, `side`, `category`, `reason`, `isPartial`, `quantity`, `price`, `netPnl`) alongside the usual `account` payload, built from values already computed inside its transaction. This exists specifically for the managed-position path — `processPositionCandle()` delegates to `closePosition()` when a level is crossed, and it's the only path that decides `stop_loss`/`take_profit`/`liquidation`/`partial_take_profit` entirely server-side with no way for the frontend to already know which one fired. `closedTrade` is `null` on `closePosition()`'s no-op branch (position already not `open`) and absent entirely on `processPositionCandle()`'s "nothing crossed a level" early return — the frontend treats both as falsy and skips the toast. The manual-close and simple client-checked SL/TP paths already knew their own reason before the request went out, so this field is redundant-but-consistent for them, not load-bearing.

Toast message builders (`buildFillToastMessage`, `buildCancelToastMessage`, `buildCloseToastMessage`, `getPositionSideLabel`) are module-level functions in `MarketChart.jsx`, colocated with `formatOverlayPrice`/`formatOverlayPnl` (reused for toast copy so figures match the chart's own SL/TP/entry badges). `getPositionSideLabel` is a deliberate local duplicate of `PositionsPanel.jsx`'s `positionSideLabel` — this codebase already keeps several independent inline copies of the Long/Short/Buy branch (see "Spot support in the order ticket" above), so this is one more rather than a new shared module. Toast color is binary (this app's `ToastContext` only has `'success'`/`'error'` styling): fills, placements, cancellations, take-profit, and partial-take-profit are `'success'`; stop-loss and liquidation are `'error'`; a manual close is colored by whether `netPnl` was non-negative.

**No queueing.** `ToastContext` still shows one message at a time — a new toast immediately replaces whatever's on screen, exactly as it already worked for every other toast in the app before this feature. A burst of near-simultaneous closes (e.g. a Replay timeline drag across a gap that closes several positions in the same monitoring pass) may only show the most recently fired toast; this is an accepted tradeoff, not a bug — see `docs/superpowers/specs/2026-08-26-position-lifecycle-toasts-design.md` for the full design discussion.

## Editing SL/TP on an already-open position or pending order

Full design: `docs/superpowers/specs/2026-08-26-position-risk-editor-design.md`. Before this, SL/TP could only be set at order-entry time or by dragging the chart's SL/TP line — and dragging only works when a line already exists, since `buildLine()` in `MarketChart.jsx` renders nothing for a `null` price. A position or pending order opened without SL/TP therefore had no way to add one afterward. This is unrelated to margin mode: Isolated and Cross positions hit the exact same gap and get the exact same fix, since the backend endpoint it uses (`updatePositionRisk`) was already margin-mode-agnostic.

**Entry point (`PositionsPanel.jsx`).** A **TP/SL** button sits next to the existing action button in each row of both the **Positions** tab (next to Close) and the **Open Orders** tab (next to Cancel), opening `PositionRiskModal` scoped to that row. Unlike Close, this button is not gated on the row's symbol matching the chart's active symbol — editing SL/TP doesn't require the chart to already be showing that market.

**`PositionRiskModal`.** Visually and behaviorally matches the entry ticket's Advanced TP/SL dialog (`AdvancedTpSlModal` in `ReplayPanel.jsx`) rather than duplicating it: `ReplayPanel.jsx` now exports `TpSlAdvancedField` (the per-field Price/PnL% segmented input with live preview text) and the `estimatePriceFromPnlPercent`/`estimatePnlPercentFromPrice` conversion helpers, and `PositionsPanel.jsx` imports them to build its own modal shell around the same two fields. It opens pre-filled from `position.stopLoss`/`position.takeProfit` with mode always `'price'` (the backend never stores a PnL% origin, so there's nothing to reconstruct a starting `%` from).

Client-side validation mirrors `updatePositionRisk`'s own server-side checks (long: SL below entry, TP above; short: reversed) and blocks Save with the same message wording on failure. **No clear/remove action this round** — a field that already had a value can't be saved blank; leaving it blank (or typing something invalid) reverts to its original value rather than clearing it, so "blank" never silently doubles as "remove." A field that started blank stays `null` until a valid value is entered.

Save sends one `PUT /market-backtest/positions/{id}/risk` with both `stop_loss` and `take_profit` always present, via a new `MarketChart.jsx` handler, `handleUpdatePositionRiskLevels`. It's deliberately a sibling to the existing chart-drag handler (`handleUpdateBacktestPositionRisk`), not a shared implementation: the drag handler swallows its own errors into the page-level `backtestError` banner and re-syncs via `loadBacktestAccount()`, but this modal needs the raw rejection to show its own inline error and stay open, so `handleUpdatePositionRiskLevels` does not catch anything itself — `PositionRiskModal` awaits it directly and reads `err.response?.data?.message`.

## Strategy playbooks and pre-trade checklist

Authenticated traders manage owned strategy playbooks from the top of `/trade-report`. A playbook stores its name, description, entry/confirmation/invalidation/stop/target rules, up to 20 checklist items, and active/archive state.

| Route/file | Responsibility |
|---|---|
| `GET/POST /market-backtest/playbooks` | List and create the authenticated trader's playbooks |
| `PUT/DELETE /market-backtest/playbooks/{playbook}` | Update or archive an owned playbook |
| `MarketBacktestPlaybookController.php` | Validation, ownership, normalization, and serialization |
| `StrategyPlaybooks.jsx` | Playbook management UI on Trade Report |
| `ReplayPanel.jsx` | Optional playbook selection and required checklist during order entry |

When a playbook is selected, `POST /market-backtest/positions` verifies that it is active and owned by the authenticated user. Every checklist answer must be present and true. The created position stores both the nullable playbook foreign key and an immutable `playbook_snapshot` with the rules and checklist as they existed at entry, plus `checklist_answers`. Archiving or editing the source playbook therefore never changes historical trade evidence. The playbook name also seeds `setup_tag`, preserving compatibility with existing journal filters and coaching insights.

Playbooks are optional so existing untagged/free-form trading remains supported. Deleting from the UI archives rather than hard-deletes; archived playbooks disappear from order entry but remain visible in the management list.

**The order-entry playbook picker is a searchable `react-select`, not a native `<select>`.** `react-select` is already a project dependency, used the same way for the compact watchlist "add a saved market" picker (`WatchlistPanel.jsx`) — this is a second, independent usage, not a shared component, since `ReplayPanel.jsx` has its own established dark/light token set (`black-table-color` `#151617` / `gray-700` `#374151`, resolved from `tailwind.config.js` since `react-select`'s `styles` prop takes real CSS values, not Tailwind class names) distinct from `WatchlistPanel.jsx`'s own hex tokens — `playbookSelectStyles(isDark)` matches `ReplayPanel.jsx`'s own `fieldClass` look rather than reusing `watchlistSelectStyles`. `playbookOptions` prepends a real `{ value: '', label: 'No playbook' }` entry ahead of the trader's playbooks (mirroring the native select's original first `<option>`) rather than using `isClearable`, so "No playbook" stays a normal searchable/selectable list entry instead of a separate clear-affordance.

**Create/edit is a modal, not an always-visible inline form.** `StrategyPlaybooks.jsx` used to render the full name/description/rule-fields/checklist form permanently alongside the list in a two-column grid, which ate roughly half the `/trade-report` page's width even when nobody was creating or editing anything. The form now lives in a page-level modal (`isModalOpen`, `z-[10010]` matching `PaymentActionModal.jsx`'s page-modal convention rather than the chart-context `z-[100XX]` range), opened by the header's "New playbook" button, a card's Edit button (`edit()`), or the empty-state card itself when there are no playbooks yet. The freed width is used by turning the playbook list into a responsive `sm:grid-cols-2 xl:grid-cols-3` grid instead of a single narrow column.

The component now tracks two separate error strings on purpose: `error` (from `load()`, shown above the list regardless of whether the modal is open) and `formError` (from `save()`, shown inside the modal and cleared on `reset()`). Sharing one `error` state between both would have made a stale save-validation message linger in the closed modal's place, or a genuine list-load failure disappear the moment the modal opened. `closeModal()` (backdrop click, header X, footer Cancel, and a successful save) always calls `reset()` too, so the draft never survives past the modal closing — reopening via "New playbook" or a different card's Edit always starts from a clean slate.

**The order-entry playbook picker updates live, without a reload.** `StrategyPlaybooks.jsx` lives on `/trade-report`, a different page from the chart's order-entry panel (`ReplayPanel.jsx`) — previously, `ReplayPanel.jsx` only fetched `/market-backtest/playbooks` once on mount, so a playbook created/edited/archived on the Trade Report page (in the same tab or a different one) wouldn't show up in the chart's picker until a full reload. `StrategyPlaybooks.jsx` now calls `broadcastChange('backtradelab-playbooks-changed')` (`utils/crossTabSync.js`) after every successful create, update, and archive; `ReplayPanel.jsx` subscribes via `subscribeToChange` and re-fetches for as long as it's mounted. If the currently-selected playbook disappears (archived elsewhere) or is renamed, the picker updates immediately, and a removed selection is cleared back to "No playbook" rather than silently continuing to reference it. Same mechanism as the analogous symbol-sync fix — see the "Known inconsistency" note in [Trading chart](trading-chart.md).

## Replay-day risk guardrails

Traders configure optional guardrails on `/trade-report`. Limits include maximum realized loss per replay day, opened trades per replay day, concurrent pending/open positions, and consecutive closed losses. A replay day is the UTC calendar day containing the order's `executed_at_time`; this intentionally follows historical replay time instead of the user's real-world current date.

| Route/file | Responsibility |
|---|---|
| `GET/PUT /market-backtest/risk-settings` | Read and update the authenticated trader's single settings row |
| `MarketBacktestRiskSettingController.php` | Owned settings defaults and validation |
| `MarketBacktestRiskGuardrailService.php` | Replay-day metrics, loss-streak calculation, and breaches |
| `RiskGuardrailSettings.jsx` | Warning/enforced mode and limit configuration |

Warning mode returns current breaches after allowing a new order. Enforced mode rejects `POST /market-backtest/positions` with `422` before balance, position, or trade records change. Evaluation and position creation run in the same transaction, and the settings row is locked so concurrent order attempts use one consistent rule configuration. A configured maximum is considered reached when the current metric is greater than or equal to it: for example, a five-trade limit allows trades one through five and blocks the sixth.

Guardrails affect new entries only. They do not prevent closing or cancelling a position, because risk-reducing actions must remain available.

## Liquidation and managed exits

New positions persist an isolated-margin liquidation price using a 0.5% maintenance-margin approximation. Unlike the former display-only estimate, replay candles are processed by `POST /market-backtest/positions/{position}/process-candle`; crossing liquidation closes the position with `close_reason=liquidation`. Liquidation has priority over stop loss and take profit when one candle spans multiple levels.

Order entry can optionally configure:

- trailing-stop distance as a percentage; `favorable_price` records the best high for longs or best low for shorts and the stop only tightens;
- a favorable-move percentage that moves the stop to entry (break-even);
- a partial take-profit percentage (1–99) that closes that share when TP is first reached, clears the TP, and leaves the remainder open.

Partial exits proportionally release margin and allocate entry fees, append a close trade, accumulate realized PnL and exit fees, and preserve original quantity/margin/entry-fee fields for accurate final reporting. Closing snapshots continue to be captured for final exits. Manual, stop-loss, take-profit, liquidation, and partial-take-profit reasons are stored explicitly.

**The three managed-exit fields are three different units, not interchangeable percentages** — Trailing stop % and Break-even % are both *price*-move percentages, while Partial close % is a percentage of *position size*, not price. Each field's `title`/help text spells this out explicitly, particularly Partial close % calling out that it's SIZE not price. For where these three fields currently live in the order-entry UI (the `Managed Exits` modal, distinct from the TP/SL `Advanced` modal), see `## Order ticket UI (ReplayPanel.jsx)` above — that section reflects the current layout; this one only documents the backend fields themselves.

**The margin input no longer defaults to a pre-filled `1000`.** `orderNotional` starts empty (`useState('')`), matching how the 25/50/75/100%-of-cash quick-select buttons already work and how real exchange order forms leave size unset until the trader types a value or picks a preset — a stale prefilled number a trader didn't consciously choose invites an accidental order at an unintended size. No other change was needed: `canSubmitOrder` already requires `Number(quoteNotional) > 0`, and `getOrderPlan()` already returns `null` margin/fee figures (rendering `---`) for a non-positive notional, so an empty field already degraded correctly before this change — it just used to start non-empty for no functional reason.

Each candle also updates `adverse_price`, a mirrored running-worst-price tracker seeded at entry and updated identically to `favorable_price` — the worst low for longs or worst high for shorts — except it only ever moves against the position. Neither field is touched by `closePosition()`, so both freeze at their last processed value once a position closes, and that frozen pair becomes the excursion data point the trade report's MAE/MFE analytics feed on.

The trader Assets panel accepts a starting balance from `1` through `1,000,000,000`. Applying it uses the existing demo reset operation and requires confirmation because it deletes positions and demo trades and resets cash, realized PnL, and fees.

**Data model.** `market_backtest_positions` gained `exchange` (defaults `bybit`) and `margin_mode` (`isolated`|`cross`, defaults `isolated`) — see migration `2026_08_26_000001_add_cross_margin_support_to_market_backtest.php`. `liquidation_price` stays populated only for Isolated futures; it is always `null` for Cross (and Spot), since Cross liquidation is a whole-portfolio condition, not a fixed per-position price. A new `market_backtest_marks` table (model `MarketBacktestMark`) is a small ledger of simulated marks — one row per account/session/exchange/category/symbol/mode — used only for Cross's own calculations; it does not touch the chart's candle pipeline.

**Services.**
- `CrossMarginService` is the pure, side-effect-free calculator (`calculate()`): given a cash balance, open/pending Cross positions, and a mark map, it returns `equity`, `initialMargin`, `unrealizedPnl`, `pendingReserve`, `closingFeeBuffer`, `maintenanceRequirement`, `availableMargin`, `marginRatio`, `complete`/`missingMarkets`, and `liquidationRequired`. Maintenance is a fixed `0.5%` of notional (`MAINTENANCE_RATE`) plus a closing-fee buffer. It owns the platform's simulated fee rate as `CrossMarginService::FEE_RATE` (`0.0004`) — `MarketBacktestController::FEE_RATE` now aliases this constant rather than repeating the literal, since the entry-validation and liquidation paths must never price fees differently. A market with no mark, or a non-positive one, marks the whole result `incomplete` and never contributes to `liquidationRequired` — a missing price is never treated as a green light.
- `CrossMarkService` records/reads that mark ledger (`record()`, `mapForAccount()` for a plain `market key => price` map, `resolvedMarksForAccount()` when a caller also needs each mark's `candle_time`, as the liquidation service does for timestamping its close trades). Live-mode rows always have a `null` `market_backtest_session_id`, and SQL treats every `NULL` as distinct for uniqueness purposes, so the table's unique index alone can't stop two concurrent `record()` calls (a request racing the Live monitor, say) from both inserting a row for the same market; `record()` wraps its upsert in a short per-market `Cache::lock()` (the same pattern `ExchangeMarketDataGateway` already uses) and falls back to an unlocked upsert if the lock can't be acquired in time, rather than ever failing the request placing an order.
- `MarketBacktestController::resolveCrossEntrySizing()` is Cross's counterpart to `resolveEntrySizing()` — it computes margin/fee/quantity the same way but has no `cashBalance` parameter and never trims or rejects against it. A Cross entry can be legitimately backed by unrealized profit sitting in other open Cross positions (pooled equity), which `cash_balance` alone doesn't reflect; affordability for Cross is decided entirely by the `cross_available_margin` check below. `cash_balance` is still the real ledger the entry's margin+fee gets deducted from, and it can go negative for a Cross account exactly like a real cross-margin account borrowing against portfolio equity — only Cross's own available-margin check gates that, not a cash-on-hand floor.
- `CrossLiquidationService::evaluate($accountId, $mode, $sessionId, $feeRate)` runs in one DB transaction: locks the account and every open Cross position, resolves a fresh mark map, recalculates, and — only when `liquidationRequired` — closes every open Cross position at its mark, creates one close trade each (`close_reason = cross_liquidation`), and reconciles cash/realized-PnL/fees in a single account update. Re-running it after a liquidation (or a second concurrent caller) finds no open Cross positions and mutates nothing, so it is safe to call repeatedly from a monitor loop or an optimistic frontend request.

**Controller integration.** `openPosition()` validates `margin_mode` (previously missing from the request's validation rules — without it Cross could never actually be selected over HTTP even though the surrounding logic already existed) and rejects Spot+Cross. A Cross entry — market or pending — locks the account, records a mark at the submitted price, and is rejected with the open Cross book's `missingMarkets` if any open Cross market lacks a current mark, or with "Insufficient shared Cross available margin" if its required cash exceeds `availableMargin`; a pending Cross order still reserves that capacity in `pendingReserve` without touching `cash_balance` until `triggerPosition()` fires it, which re-validates available margin against the *rest* of the portfolio (excluding its own existing reservation — an earlier version of this check double-counted the position being triggered against itself and would have wrongly rejected legitimate triggers). Cancelling a pending Cross order needs no special handling: it flips to `cancelled` and drops out of every metrics query automatically. Manual/TP/SL closes are margin-mode-agnostic; the response's `account.cross` block always reflects the book *after* the mutation. Every `buildPayload()` response includes `cross` (the current Cross metrics) and each position's `exchange`/`marginMode`. `POST /market-backtest/cross/evaluate` lets the frontend request an immediate liquidation check after an order mutation or a visible tick — this is only ever an optimization; the Live monitor below is authoritative; nothing in the frontend calls it yet since phase 5 hasn't wired up any Cross UI to trigger it from.

`buildPayload()`'s "overlay the request's own current tick" step (used so the account payload reflects the very price a request just supplied, not only whatever was last persisted to the mark ledger) matches candidate positions by symbol only, since the parameters it receives are just a plain symbol/price pair with no exchange context. That overlay only fires when exactly one Cross market uses that symbol string for the account — if the same account somehow holds Cross positions on the same symbol across two different exchanges, the ambiguous tick is skipped and each market's own already-persisted mark is used instead, rather than guessing and risking writing one exchange's price onto another's distinct market.

**Known limitation:** `buildPayload()` still merges Live and Replay marks together for its informational `cross` display block (fetching `mode: 'live'` marks unconditionally, then merging in the session's `mode: 'replay'` marks on top when a session is active) — which is not what the design spec means by "BacktradeLab does not mix current Live prices into a Replay portfolio". This has no effect on anything that actually gates money movement: entry validation (`buildCrossMetrics()`) and `CrossLiquidationService` both already resolve a single explicit mode with no merging, so this only affects the *displayed* metrics in the response body, and there is no UI yet rendering that block. Fixing it properly requires deciding how the server infers "is this request live or replay" in the several call sites where no explicit signal exists today (e.g. `updatePositionRisk()`, `cancelPosition()`) and in `processPositionCandle()`, whose `executed_at_time` is sent by the frontend for both a live tick and a replay tick — that's a pre-existing, project-wide ambiguity in how live/replay context reaches the server, not something to resolve as a side effect of this change. Track it alongside phase 5's UI work, once there's an actual consumer of this display block to get right.

**Live monitoring.** `CrossMarginLiveMonitor::runOnce()` (run via `php artisan cross-margin:monitor`, following the existing `market-alerts:monitor`/`MarketAlertMonitor` operational pattern) scans every open/pending Cross position across all accounts, coalesces them into distinct markets so N accounts sharing a symbol cost one price fetch, pulls each price through the existing `MarketCurrentPriceService` (no new exchange integration), and evaluates every affected account through `CrossLiquidationService`. A market whose fetch fails gets an exponential per-market backoff (same shape as the alert monitor) and simply isn't refreshed that cycle — the account's Cross metrics fall back to whatever mark it already has, and if that's stale or absent the evaluation reports `incomplete_marks` and never liquidates. Toggle with `CROSS_MARGIN_MONITOR_ENABLED` / `CROSS_MARGIN_MONITOR_POLL_SECONDS` (`config/cross-margin.php`); like the alert monitor, it's a supervisor-managed long-running process, not a scheduler entry — see [Deployment](deployment-and-production.md).

**Replay evaluation is intentionally not built yet.** The design spec calls for resolving every open Cross symbol's replay-time candle "at or before" the shared replay cursor, independent of which chart is open — but (a) there is no session-level replay cursor column today (the cursor is a client-supplied `executed_at_time`/`candle_time` request parameter, same as Isolated positions' own SL/TP replay checks), and (b) the existing candle-fetching machinery for historical bars lives entirely as private methods on `MarketDataController`, with no public "latest candle at/before timestamp" service method to call from a Cross-specific service without a separate refactor. Building that is tracked as follow-up work, not silently skipped: until it lands, a Replay Cross position's marks only update when a request already happens to touch that symbol (the same limitation Isolated position SL/TP already has during Replay today), and `CrossLiquidationService`'s `mode: 'replay'` path is exercised by tests but not yet driven by any real per-tick server loop.

**Tests.** `tests/Unit/CrossMarginServiceTest.php` (pure calculator: multi-symbol/mixed-side PnL, pending reservations, missing marks, the liquidation boundary). `tests/Feature/MarketBacktestCrossMarginTest.php` (entry acceptance/rejection at the exact available-margin boundary, missing-marks rejection, Spot+Cross rejection, pending reserve/cancel/trigger, manual close recalculating the remaining portfolio, Isolated/Spot exclusion, a Cross entry backed entirely by unrealized profit in another open Cross position despite low `cash_balance` — all through the real HTTP endpoints). `tests/Feature/MarketBacktestCrossLiquidationTest.php` (all-and-only-Cross-positions liquidation with exact cash/PnL/fee reconciliation, idempotent re-evaluation, no liquidation above maintenance, no liquidation on incomplete marks, and — since Phase 5 — that liquidation creates exactly one `cross liquidation` `AdmNotifications` row carrying the id the response's `liquidation.notificationId` points at, and that a repeated evaluation creates no duplicate). `tests/Feature/CrossMarginLiveMonitorTest.php` (shared-market coalescing, a breach liquidating only the affected account, a failed fetch not blocking evaluation of accounts on other markets — the breach test now exercises the same notification-creation path since it goes through the same `CrossLiquidationService::evaluate()`). These feature tests need the `pdo_sqlite` PHP extension; if it's compiled but not enabled in `php.ini` (as in this project's default local PHP), run them via `php -d extension=pdo_sqlite vendor/bin/phpunit` rather than `php artisan test`, which shells out to a fresh `php` process that won't inherit a CLI `-d` flag.

`tests/Feature/CrossMarginRealDatabaseTest.php` is a different kind of check: it hits the real `routes/web.php` entries (not test-only routes) through the real `auth`/`account.active`/`replay.access`/throttle middleware stack against whatever database `.env` actually points to (MySQL locally, real migrated schema) — the sqlite-backed tests above register their own bare routes against a hand-built schema and can't catch a routing/middleware mistake or a MySQL-specific behavior. It uses `DatabaseTransactions` so the throwaway user and every row it creates roll back when the test ends; nothing is left in the real database (verified after the fact via `AdmUser::where('email','like','cross-margin-realdb-%')->count()` returning `0`).
