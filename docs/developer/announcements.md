# Announcements

## Purpose

Administrators create/edit announcements; authenticated users (trader and admin alike) get a modal on their next page load showing any they haven't acknowledged yet, and can also browse recent ones passively from Market Summary.

| Route/file | Responsibility |
|---|---|
| `GET /announcements` | Admin list/search/paginate (`AnnouncementPage.jsx`) |
| `/announcements/*` | Admin add/edit/delete actions |
| `GET /unread-announcement` | JSON: current user's unread, active announcements, newest first |
| `POST /read-announcement` | Marks one announcement read for the current user (pivot `syncWithoutDetaching`, idempotent); clears the `unread-announcement` session flag once none remain |
| `GET /market-overview` | Latest four active announcements with sanitized excerpts and read state |
| `GET /updates` | Full "News & updates" page — every active announcement, paginated 10/page, full rich `message` (not excerpted) |
| `GET /changelog-feed` | JSON: latest 15 active announcements with `is_read`, for the Product Hub modal's Changelog tab. A separate method from `getAllAnnouncements()` because that one renders an Inertia page and cannot be called from inside a modal — see [Feedback](feedback.md) |
| `AnnouncementsController.php` | Announcement CRUD and unread/read-state logic |
| `Announcement.php` | Many-to-many user relationship (`announcement_user`, pivot `hidden_at`) |
| `DELETE /notifications/announcement/{id}` | Hides one announcement for the calling user only (pivot `hidden_at`) — see [Alerts and notifications](price-alerts-and-notifications.md) |
| `Components/Announcements/AnnouncementGate.jsx` | The modal itself — mounted once in `Layouts/layout/layout.jsx`, so it's live on both the admin and trader shell |
| `Pages/AdmVram/AnnouncementPage.jsx`, `AnnouncementForm.jsx` | Admin list and create/edit UI (`WyswygTextEditor` for `message`) |

## Flow

1. Admin creates content (rich HTML `message` via a WYSIWYG editor) and it becomes active immediately — there is no separate audience/targeting step; every active announcement is unread for every user until they've individually acknowledged it via `announcement_user`.
2. `LoginController::completeLogin()` sets the `unread-announcement` session flag to `true` if any active announcement isn't yet in the logging-in user's `announcement_user` rows. This runs for both trader and admin logins.
3. `HandleInertiaRequests` shares that flag as `auth.announcement` on every Inertia response (already wired, no extra request needed).
4. `AnnouncementGate.jsx` (mounted in `layout.jsx`, so present for both `AdminNavbar`/`TraderNavbar` shells) watches `auth.announcement`; the first time it's truthy, it fetches the real list from `/unread-announcement` and shows a theme-aware modal, one announcement at a time, with a progress-dot indicator when there's more than one. "Next"/"Got it" calls `/read-announcement` for the current item before advancing; closing via the X hides it for the rest of the session without marking anything read, so it reappears on the next full page load (matching the old behavior).

The Product Hub modal's Changelog tab is the fourth surface rendering this admin-authored HTML through `dangerouslySetInnerHTML`, on the same trust model as the three below — it adds a surface, not a new trust assumption. Expanding an unread entry there calls the same `POST /read-announcement`, so read state stays consistent everywhere. See [Feedback](feedback.md).

Market Summary separately reuses active administrator announcements as trusted "News & updates" via `/market-overview`. That endpoint returns only plain-text excerpts (latest 4), newest first, and never exposes executable rich content. Its "View all" link goes to `Pages/Announcements/Index.jsx` (`GET /updates`), a paginated, click-to-expand list of every active announcement with the full rich `message` HTML (same trust model as `AnnouncementGate.jsx` — admin-authored, rendered via `dangerouslySetInnerHTML`). Expanding an unread row there calls `/read-announcement` the same way the excerpt card and the modal do, so read state stays consistent across all three surfaces.

## Announcements run before the page's spotlight tour, never alongside it

A first login could hand the user two full-screen surfaces at once: this modal and whichever page's uncompleted `WorkspaceTour.jsx` tour (the chart workspace one on `/dashboard`, plus the journal/mentor/training tours — see [Trading chart](trading-chart.md)). They are unrelated features that happen to share the same trigger, so both fired: the tour's spotlight measured and highlighted a control the announcement backdrop was already covering, and the user had to dismiss two things stacked over each other. Announcements now go first; the tour appears once this modal is done.

`Context/AnnouncementGateContext.jsx` is the handshake, deliberately a context rather than a `window` CustomEvent or a prop chain — `AnnouncementGate` is mounted in `layout.jsx` while every tour lives inside the page component that `layout.jsx` renders as `children`, so they are distant relatives in one tree, the same shape that made `WatchlistContext` a context (see [Dashboard and layouts](dashboard-and-layouts.md)). `layout.jsx` wraps both in `AnnouncementGateProvider`.

Two details are load-bearing:

- **`initialPending` is seeded from `auth.announcement` in the provider's `useState` initializer**, not set later by `AnnouncementGate`. The gate learns the real list from an async `GET /unread-announcement`; a tour rendering during that request would appear and then be covered a moment later, which is the same bug in a shorter window. Seeding the flag from the already-shared Inertia prop means the hold is in place from the very first render.
- **`settled` is a separate state from the existing `fetched`.** `fetched` flips synchronously as the request goes *out* (it exists only to guard against refetch loops), so it cannot stand in for "the response came back." `settled` is set in the request's `finally`, and on the `!auth?.announcement` branch where no request is made at all.

`markAnnouncementsResolved()` fires once `settled` is true and there is nothing left to show — every announcement acknowledged, closed via the X, nothing unread, **or the lookup failed**. Releasing on failure is deliberate: a network blip must not silently suppress a user's onboarding tour for the whole session.

Each tour keeps its own `tourStep` state untouched and only gates its render (`showTour = tourStep >= 0 && !announcementsPending`), so it is held rather than cancelled — it appears on the step it was already on, and the completion flag is unaffected. Anything else added later that wants the screen on login should consume this same context instead of adding a second ordering mechanism.

## History note (fixed 2026-08-08)

Before this fix, the acknowledgment flow only actually fired for admins: the `unread-announcement` session flag was set on every login, but only the `check.user` middleware (applied only to the admin route groups) ever read it, redirecting to `GET /unread-announcement`'s **old** Inertia-page response — which additionally rendered a dead `Components/Dashboard/Overview.jsx` placeholder ("Dashboard 1/2/3" cards linking to nonexistent `/customer` and `/list_of_orders` routes) behind the modal. Traders never saw this at all; the "News & updates" card was their only announcement surface. Separately, `GET /announcement` pointed at a controller method rendering `AdmVram/DefaultAnnouncement.jsx`, a page that never existed, while the real admin list page (`getIndex()` → `AnnouncementPage.jsx`) had no route at all, so the "Announcements" sidebar link (`slug: announcements`) 404'd. All of this is now replaced by the client-driven `AnnouncementGate` described above, and `GET /announcements` correctly routes to `getIndex()`.

`AnnouncementPage.jsx` (the admin list) had two more bugs fixed the same day: its Title and Message columns were sortable `TableHeader`s wired to `name="description"`/`name="id_adm_users"` — columns that don't exist on `announcements` (copy-pasted from `Logs.jsx`) — so clicking either header sent `orderBy('description', ...)`/`orderBy('id_adm_users', ...)` and threw `SQLSTATE[42S22]: Column not found`, a 500 for the admin. Fixed to `name="title"` (real, sortable) and `sortable={false}` on Message (sorting by rich HTML has no meaningful order). The Message cell also used to `dangerouslySetInnerHTML`-dump the entire raw `message` body inline into the table row, unstyled and outside the theme system (`style={{paddingLeft:'20px'}}`, no dark-mode text color) — a long or image-heavy announcement blew up row height and could render illegibly in dark mode. `getIndex()` now attaches a plain-text `excerpt` (`strip_tags` + `Str::limit(160)`, same sanitization shape as `MarketOverviewService::sanitizeExcerpt` but not shared code — keep both in sync if the truncation approach changes) and the page renders that through the normal theme-aware `RowData` cell instead. The list also gained a working delete action (`POST /announcements/delete-announcement/{id}`, `announcements,delete` privilege, `Swal.fire` confirm matching `Menus.jsx`'s convention) — cascade-deletes the row's `announcement_user` read-state rows via the existing FK — since there previously was no way to remove an announcement from the UI at all.

**`WyswygTextEditor.jsx` (shared by `AnnouncementForm.jsx` only) had a critical bug: it was impossible to create or meaningfully edit an announcement.** Its `handleContentChange`/`toggleHtmlMode` handlers only ever called `setContent()` (the component's own local state) and never invoked the `onChange` prop passed down from `AnnouncementForm.jsx`. Typing in the rich-text box updated the editor and its own live preview (both driven by the same local `content` state, which is why it looked like it was working), but `AnnouncementForm`'s `forms.message` never left its initial empty string, so `validate()` always failed with "Message is required" on Add, and on Edit any changes typed into the editor were silently discarded on save (the original unmodified message got resubmitted instead). Fixed by having both handlers call `onChange({ name, value })`, matching the `{name, value}` shape `AnnouncementForm.jsx`'s `handleChange` already expected. This is what the report leading to this fix actually surfaced (a screenshot showing "Testtest" typed and previewed, with "Message is required" still shown) — the fix was confirmed by tracing the prop chain, not by reproducing in a browser.

`WyswygTextEditor.jsx` and `AnnouncementForm.jsx` were also restyled to the standard `isDark` dark/light tokens (`border-[#2a2e39] bg-[#131722]`/`bg-[#0b0e14]` dark, `border-slate-200 bg-white`/`bg-slate-50` light, `#2962ff` accent), matching the rest of this app rather than the legacy multi-skin-color `Button`/`useThemeStyles` system the Save button used before (that system is still used elsewhere and wasn't touched globally — this was a page-local swap, not a removal of the shared components). React-Quill's "snow" theme is hardcoded light with no dark variant; `resources/css/wyswyg-dark.css` adds scoped dark-mode overrides for its toolbar/container/picker classes under a `.wysiwyg-dark` wrapper class, applied only when `isDark` is true, so light mode is untouched. The HTML-source toggle button (previously an unstyled, ambiguously-labeled "DecodeHtml"/"EncodeHtml" text link) is now a small icon button labeled "View raw HTML" / "Switch to rich text" — same underlying encode/decode behavior, just legible.

**Fixing the WYSIWYG `onChange` bug still wasn't enough — saving was independently broken by two more bugs, found by driving requests through the real HTTP kernel (`Illuminate\Contracts\Http\Kernel::handle()`) rather than reading code, after a "the message error still shows even though I typed something" report turned out to actually be "it doesn't save at all" once the first bug was fixed:**

1. **Wrong URLs.** `AnnouncementForm.jsx` posted the Edit save to `/saveEditAnnouncement` — a route that has never existed (the registered path always had an `announcement(s)/` prefix) — a guaranteed 404. The Add save posted to the *relative* URL `announcement/SaveAnnouncement` (no leading slash) from the add-announcement page, whose own URL is two path segments deep (`/announcement/add-announcement`); a relative reference with no leading slash resolves against the *current URL's directory* (everything up to the last `/`), so it resolved to `/announcement/announcement/SaveAnnouncement` — also a 404. Both were confirmed by literally sending those exact requests through the app's kernel and reading the status code back (404 for both), not by inspecting the code and assuming. Fixed by switching every announcement CRUD `href`/`axios.post` in `AnnouncementPage.jsx`/`AnnouncementForm.jsx` to absolute, leading-slash paths — the same convention every other nav link in this app already uses, specifically so a page's own URL depth can never change where a link or POST resolves to.
2. **A lying `Content-Type` header silently dropped the entire request body.** `handleSubmit` sent the plain JS `forms` object with `headers: { 'Content-Type': 'multipart/form-data' }` — but axios's default `transformRequest` only skips its `JSON.stringify()` step for a real `FormData`/`Blob`/`ArrayBuffer` instance; a plain object still gets JSON-stringified regardless of what `Content-Type` you told it to claim. The result: a JSON string body declared as `multipart/form-data` with no `boundary=` parameter, which PHP's multipart parser can't split at all — confirmed directly (`Illuminate\Http\Request::create()` with that exact header/body combination) that `$request->all()` comes back `[]` and every field is `null`. There was no file input anywhere in this form to justify multipart in the first place; removing the header override entirely (letting axios use its default `application/json`) fixed it, confirmed by the same direct-request test now returning the full posted data intact.
3. **Also renamed the CRUD routes from `announcement/*` to `announcements/*` (plural)**, aligning them with `adm_modules.path = 'announcements'` (the actual permission-lookup key). `CommonHelpers::hasAdminPermission()` derives the "current module" purely from the first URL path segment (`CommonHelpers::getModulePath()`), so every add/edit/save/delete request was resolving to a nonexistent `'announcement'` (singular) module and silently failing its own internal `isCreate()`/`isUpdate()`/`isDelete()`/`isView()` re-checks — invisibly masked for superadmins only, since `AdminAccessService::allows()` short-circuits to `true` for `is_superadmin` before ever reaching the module-path lookup. A regular "admin" role (not superadmin) with explicit per-module privileges would have hit `CommonHelpers::redirect()`'s silent-redirect branch on every attempt. Confirmed via `CommonHelpers::getModulePath()` returning `"announcements"` for all five routes after the rename, matching the module row.

None of these three were guessed from reading the code and reasoning about what "should" happen — each was confirmed by actually constructing the request (real headers, real body, real URI) and observing Laravel's real response, since earlier in this same investigation the WYSIWYG fix looked complete by code-tracing alone but wasn't the whole story.

## Maintenance and verification

- Keep announcement `message` HTML admin-authored only; don't relax `announcements,create`/`edit`/`delete` privilege gating, since the modal and the "News & updates" full page both render it unsanitized by design.
- A user deleting an announcement from their notification history must never delete the `announcements` row — it is published for everyone. That path sets the per-user `hidden_at` pivot column instead; treat any new "remove announcement" surface the same way.
- The notification history page is the one surface that renders announcement HTML *sanitized* (`NotificationsController::sanitizeAnnouncementHtml()`) and its list rows as plain text, because that feed mixes announcements with system notifications. Don't paste raw `message` into a mixed feed — it prints literal tags.
- Never let a user mark another user's pivot record.
- Enforce admin privileges on create/edit/delete, not only menu visibility.
- Log in as a user with at least one unread announcement, on a page whose spotlight tour is still uncompleted (easiest: a fresh account landing on `/dashboard`): only the announcement modal renders. Acknowledge every announcement and confirm the tour appears immediately afterward, at step 1. Repeat, closing the modal with the X instead — the tour must still appear, even though nothing was marked read. Repeat with `/unread-announcement` blocked in devtools — the tour must still appear rather than being suppressed for the session.
- A user with no unread announcements sees the tour immediately, with no added delay — the hold must not depend on a round trip that never happens.
- Test unread count, mark-read idempotency (including the multi-item carousel advancing correctly), expired/inactive items, and that `auth.announcement` going false after the last item is read doesn't require a manual refresh to stop refetching (`fetched` state guards against refetch loops within a session).
- If you add a sortable `TableHeader` to any legacy table, verify its `name` is a real column on that table's query — there is no compile-time check, only a runtime SQL error on first click.
- Always use absolute, leading-slash URLs for `href`/`axios` calls in this app. A relative URL's resolution depends on how many path segments deep the *current* page happens to be, which is exactly what made the Add/Edit save bugs above so easy to miss by reading the code alone.
- Never manually set `Content-Type: multipart/form-data` on an axios request unless the payload is an actual `FormData` instance (i.e. a real file upload) — axios still JSON-stringifies a plain object regardless of that header, producing a boundary-less multipart body that PHP cannot parse at all.
- Not addressed here, and worth deciding on purpose rather than defaulting into: there is no draft/scheduled state (every save goes live immediately to every user) and no expiration, so an inactive user returning after a long gap can face a backlog of unread announcements to click through. Revisit if that becomes a real complaint, not preemptively.
