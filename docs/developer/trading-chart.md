# Trading Chart

## Purpose

The workspace chart renders candlesticks and volume with Lightweight Charts, indicator panes, replay controls, drawings, alerts, and simulated orders.

| File | Responsibility |
|---|---|
| `Pages/Market/Market.jsx` | Workspace page and onboarding entry |
| `Pages/Dashboard/Dashboard.jsx` | Full chart workspace for traders and explicit admin workspace mode |
| `MarketChart.jsx` | Main state, refs, fetching, chart events, feature coordination |
| `ChartHeader.jsx` | Market/timeframe/replay/indicator/appearance commands |
| `TimeframeSelector.jsx` | Favorite-timeframe pill row + "Select period" grid, used by both `ChartHeader.jsx` layouts |
| `ChartSettingsModal.jsx` | Chart settings dialog (Symbol/Status line/Scales/Canvas) opened from the chart legend's "•••" menu |
| `FullscreenChartHeader.jsx` | Fullscreen command bar |
| `ReplayPanel.jsx` | Drawing, replay, and order rail |
| `ChartStage.jsx` | Chart container and SVG overlays |
| `IndicatorSettingsPanel.jsx` | Indicator configuration |
| `PositionsPanel.jsx` | Positions/Open Orders table below the chart (non-fullscreen only) — see [Backtesting and orders](backtesting-and-orders.md) |
| `constants.js`, `utils.js` | Shared chart values and transformations |

## Flow

1. `Market.jsx` loads saved symbols and renders `MarketChart`.
2. The chart requests normalized candles from `/api/klines`.
3. Lightweight Charts series are created and updated.
4. Header/rail state changes symbol, timeframe, indicators, replay, drawings, alerts, or positions.
5. Authenticated preferences and domain records are persisted through their feature endpoints.

Spot/Futures selection is presented as tabs inside the symbol picker rather than as a persistent header control, keeping the compact chart toolbar clear. The right price scale trims trailing zero decimals and does not use thousands separators. Buy/sell execution markers use compact 14-pixel badges.

`renderedTradeMarkers` (`MarketChart.jsx`) positions each B/S badge via `estimateDrawingLogicalFromTime(allCandles, trade.executedAtTime, ...)` — the full, unsliced trade history's logical coordinate, not `visibleCandles` (the Replay-sliced subset actually rendered on the chart). `chart.timeScale().logicalToCoordinate()` extrapolates a pixel position for a logical index past the last real bar rather than returning `null`, so a trade that executed later than wherever Replay has been scrubbed back to still resolved to a valid on-screen `x` — its badge floated in the empty space past the last visible candle instead of disappearing with the future candles it belongs to. `backtestAccount.trades` (the account's last 30 fills across all symbols, independent of the current replay position) is now filtered to `executedAtTime <= ` the last currently-visible candle's time before any marker is positioned, so a trade the user hasn't reached yet in Replay renders no badge at all, consistent with future candles themselves being hidden. This is a Replay-only distinction in practice — `visibleCandles` equals `allCandles` outside Replay, so the filter is a no-op in live mode.

The chart header's Market Info control fetches `/market-metadata` on demand and displays normalized 24-hour exchange statistics plus optional CoinMarketCap fundamentals with CoinGecko fallback. The popover follows chart theme colors, omits missing values, and never participates in candle loading. Market Summary uses the batch metadata endpoint to add the same identity and headline statistics to saved-market cards.

In fullscreen mode, the left chart rail keeps Replay available alongside drawing tools. Its Replay flyout uses the same access checks and playback controls as the embedded chart, and an open Replay flyout is preserved when entering or leaving fullscreen. The drawing Tool Style and Templates editor floats at the top center of the usable chart pane in both embedded and fullscreen modes; other rail flyouts remain left-aligned.

The fullscreen Enter Position panel is non-modal. On large screens it docks at the right and reduces the chart width so the price scale remains visible; on smaller screens it becomes a bounded bottom sheet. The exposed chart remains interactive in both layouts.

The fullscreen wrapper's `className` carries a fixed `bg-black-screen-color` (`#1c1c1c`) fallback so it never flashes unstyled while mounting, but that alone left the container permanently dark regardless of theme once mounted — a light-theme user entering fullscreen got a `#1c1c1c` frame around a light chart. The inline `style` now always sets `backgroundColor: chartTheme.panel` (in both fullscreen and embedded branches, previously only the embedded one set any background/border style at all), which as an inline style wins over the Tailwind class and keeps the fullscreen frame following the active theme the same way the embedded, non-fullscreen container already did via `chartTheme.panel`/`chartTheme.border`.

The component deliberately coordinates several domains; put reusable pure logic in `utils.js`, constants in `constants.js`, and isolated UI in subcomponents rather than expanding the container unnecessarily.

Superadmins open the same complete workspace at `/admin/workspace`; the route is authorization-protected and keeps browser preferences scoped to the authenticated administrator ID.

Right-clicking a valid chart price opens a cursor-anchored action menu instead of immediately opening an order ticket. **Set Alarm** passes the selected price into the existing live-market alert dialog, while **Trigger Position** passes it into the existing Enter Position flyout. **Clear Tools** uses the existing confirmed, persisted, undoable drawing-clear action and is disabled when there are no drawings. **Reset Chart** (same section as Clear Tools, no divider between them — both are "undo a manual chart change" actions) calls `handleResetChartView()`: `chart.timeScale().fitContent()` plus `resetPriceScalesToAutoScale(chart)` (module-level helper, `chart.priceScale('right', paneIndex).applyOptions({ autoScale: true })` looped over every pane via `chart.panes()`), so it undoes horizontal zoom/pan *and* any manual vertical price-scale drag on the main pane or any indicator pane in one action. It does **not** touch drawings, indicator visibility/config, pane heights, or chart display settings — those already have their own dedicated actions (Clear Tools, the indicator toggles, Chart Settings) and resetting them wasn't asked for; conflating "reset the view" with "reset everything" would make an accidental click far more destructive than intended. No confirmation dialog, unlike Clear Tools — nothing is deleted, so it costs nothing to undo by scrolling/zooming again. **Chart Settings** (below its own divider, after Reset Chart) just calls `setIsChartSettingsOpen(true)` — the same state the market-legend gear button (`ChartMarketLegend`'s `onOpenSettings`, `MoreHorizontal` icon) already opens `ChartSettingsModal` with, so right-click is a second entry point onto the identical modal/state, not a separate settings surface. Unlike Set Alarm/Trigger Position, both Reset Chart and Chart Settings ignore `chartContextMenu.price` entirely — neither is price-scoped. The menu is keyboard accessible, constrained to the viewport, and closes on selection, outside click, Escape, scrolling, resizing, or a market-context change. Existing hover shortcuts remain available.

**Switching symbol or timeframe now also re-enables autoscale on every price scale — not just horizontal `fitContent()`.** Reported live: switching to the 30m timeframe left the chart showing no candles at all (an empty canvas, empty Volume pane) despite the legend correctly displaying real OHLC for the new data — `legendCandle` reads from the same `visibleCandles` array `candleSeries.setData()` uses, so the data had genuinely loaded; only the rendering was affected. Root cause: a manual vertical price-scale drag disables `autoScale` **inside `lightweight-charts` itself**, invisibly to React state — there is no subscription event for it (documented above, for the same reason the drag-sync fix had to poll via `requestAnimationFrame` rather than an event). The three viewport-init effects (`viewportInitializedKeyRef`-gated, keyed on `exchange:marketCategory:symbol:timeframe`) already called `chart.timeScale().fitContent()`/`setVisibleLogicalRange`/`setVisibleRange` on every symbol/timeframe change, correctly re-framing the *time* axis — but nothing re-enabled `autoScale` on the *price* axis alongside it. A price scale left disabled by an earlier manual drag kept whatever fixed range that drag had set, indefinitely, across every subsequent symbol/timeframe switch; if that stale range didn't overlap the new data's actual price levels, the new candles rendered genuinely off-screen — present in the series, invisible in the viewport — while drawings (positioned independently, by time) still looked correctly placed, which is what made this look like a data problem rather than a viewport one. All three effects now call the same `resetPriceScalesToAutoScale(chart)` helper `handleResetChartView()` uses, so this self-corrects on every symbol/timeframe change instead of requiring the user to find Reset Chart (or re-drag the scale themselves) after the fact. `resetPriceScalesToAutoScale` was extracted to module scope specifically so both the effects (which run long before `handleResetChartView` is defined in source, though after it in the render's closure — pulling it to module scope sidesteps needing to reason about that ordering at all) and the manual action share one implementation.

**The autoscale fix above did not actually resolve the reported bug — a second, unrelated mechanism was compressing the candles to nothing before autoscale ever got a chance to matter.** Same symptom (30m + Replay = blank canvas, real legend values, drawings/playhead positioned fine), still reproducing after the `resetPriceScalesToAutoScale` fix shipped. The real cause lives entirely on the *time* axis, in the fetch effect's `applyCandles` (`MarketChart.jsx`, the `shouldFrameDrawings` branch): whenever a timeframe/symbol switch happens while in Replay **and** the chart has drawings (`wasInReplay && drawingTimes.length > 0`), the new viewport is framed around every drawing's anchor time plus the (remapped-by-time, not stale) Replay position — `frameLogicals`, built by running each anchor time through `estimateDrawingLogicalFromTime(complete, time, intervalSeconds)` against `complete`, the **full** newly-fetched candle array. But the series actually rendered on screen in Replay mode is not `complete` — it's `visibleCandles = allCandles.slice(0, replayIndex + 1)`, truncated at the replay point; no bar past it is ever loaded into the chart at all, by design. Any drawing anchored *after* the current replay time (ordinary: drawings are usually made against the live chart, then Replay gets scrubbed back to an earlier point) resolved to a logical index past `nextReplayIndex`, and nothing clamped it — `pendingVisibleLogicalRangeRef.current.to` was set to `maxLogical + padding` with no upper bound, even though the symmetric `from` side was already defensively clamped (`Math.max(minLogical - padding, -20)`). Requesting a visible logical range whose upper portion has no corresponding series data doesn't error; it just squeezes the real, truncated candle cluster into a sliver at the extreme left edge of an otherwise-empty window — at typical chart widths, effectively invisible, i.e. "blank." The Replay playhead and the drawings themselves stayed correctly placed throughout because their positioning comes straight from the time scale's coordinate mapping, not from how many on-screen pixels the candle cluster happens to occupy — which is exactly why this looked like a data/price problem rather than a horizontal-framing one, and why the autoscale fix (a *price*-axis fix) couldn't have touched it. Fix: every value that feeds `frameLogicals` is now clamped to `Math.min(logical, nextReplayIndex)` before the `minLogical`/`maxLogical` reduction, so a future-anchored drawing can pull the frame's *left* edge further back but can never push `to` past the last bar Replay has actually revealed. This is Replay-specific by construction (`shouldFrameDrawings` requires `wasInReplay`); it does not reproduce live, since `visibleCandles === allCandles` there and nothing is truncated. Not conclusively confirmed to be 30m-specific — the mechanism is about a drawing's time relative to the replay point, not about bar size, so the same steps on any other timeframe with a similarly-placed drawing should reproduce it too; worth confirming live in the browser.

**Third round on the same "30m + Replay = blank canvas" report — this time reproduced with neither drawings nor a manual pan involved, which rules out both fixes above.** The autoscale fix (price axis) and the `shouldFrameDrawings` clamp (time axis, requires `wasInReplay && drawingTimes.length > 0`) each targeted a real bug, but both are inert when the chart has no drawings on it. A third, sibling gap existed in the *other* time-axis viewport-restore path — `pendingVisibleViewRef`, populated by `handleTimeframeChange` from the pre-switch visible range and consumed once the new timeframe's (Replay-truncated) `visibleCandles` arrive — which had no clamp at all; it's only reachable when `followReplay` is `false` (the user manually panned/zoomed while Replay was paused), which the live auto-follow effect (`scrollToPosition(5, false)`) would otherwise mask on every other switch. That's now fixed the same way, clamping `centerLogical` to `visibleCandles.length - 1` in Replay mode. But this user's repro had **no drawings and no manual pan** — just Play → pick a point → switch straight to 30m — so none of the three fixes above apply to it, and live testing (real login, real Replay activation confirmed via the header button's `aria-label` flipping to "Back to live", not just visual inspection) reproduced something different: the fetch was not failing or misframing anything, it was simply *slow*. A timeframe switch during Replay re-requests up to `max_candles=20000` of history, which the backend gathers via up to ~20 sequential paginated requests to the exchange (`MarketDataController::fetchKlineRows`'s pagination loop, capped by `market-data.replay_max_pages`) — confirmed to take mid-teens of seconds locally even before accounting for a single-threaded `php artisan serve` also queuing every other concurrent page request (drawings, price alerts, tool settings, etc.) behind it. The interaction shield shown during that wait had zero visual feedback by design (see below) — a slow-but-working load and a genuinely stuck one were indistinguishable, so a user who gave up after even 10-15 seconds would reasonably call the chart permanently broken. Fix: `isTimeframeLoading` now drives a `showTimeframeLoadingHint` flag (a plain delayed-`setTimeout` effect, 1500ms) that renders a small spinner + "Loading {timeframe} history…" pill centered on the shield — delayed specifically so the common fast switch still shows nothing and doesn't flash. Separately, the candle fetch is now raced against a timeout (30s live, 60s Replay, matching the heavier pagination budget) that rejects with a real user-facing error instead of leaving the fetch pending forever on a stalled upstream connection — without that, `isTimeframeLoading` (`timeframe !== loadedTimeframe && !error`) would never flip false and the shield would never lift, spinner or not, if a request genuinely hung.

The full chart skeleton is reserved for initial navigation/reload and market identity changes. A timeframe change keeps the current chart visible beneath a light 25%-black interaction shield until the replacement history is ready. The shield itself still renders no spinner/text/backdrop-blur for a normal fast switch; only once loading has run past ~1.5s (the Replay-heavy-fetch case above) does a small spinner pill appear, so a fast switch still doesn't flash. Chart interactions are blocked while header controls remain available. The compact Replay control does not duplicate connection text; connection state remains in the bottom-right chart badge.

The chart footer owns market-feed status/details and the user's live profile-timezone clock/selector. Candle histories remain full-size, are cached in a bounded per-session browser cache, and are revalidated in the background. Only one adjacent timeframe may be prefetched during browser idle time. Backtest account data is refreshed after identity/session/mutation changes rather than on every live tick; unrealized PnL is updated locally between server refreshes.

### Timeframe selector: favorite pills + "Select period" grid

The header's timeframe control used to be a plain native `<select>` (both in `ChartHeader.jsx`'s compact/fullscreen layout and its full desktop layout — two separate render sites, both `<select value={timeframe} onChange={...}>` over the same `timeframeOptions` list). `TimeframeSelector.jsx` replaces both with a TradingView-style favorites row (e.g. `1m 5m 15m 30m 1h 4h`, the active one in the accent color) plus a chevron that opens a "Select period" grid of every timeframe `supportedTimeframes(exchange)` actually returns, each cell carrying a star to add/remove it from the row.

- **No custom/arbitrary periods** (TradingView lets a user type e.g. "27m" and derives it by resampling a smaller fetched interval). This app has no candle-resampling layer anywhere — `constants.js`'s `TIMEFRAME_SECONDS`/`INTERVAL_MAP`/`TIMEFRAMES` are a fixed, exchange-native set (13 entries: 1m/3m/5m/15m/30m/1h/2h/4h/6h/12h/1d/1w/1M, further trimmed per-exchange by `supportedTimeframes()` — MEXC only exposes 9 of them). Building a text-entry "custom period" control without real resampling behind it would silently either do nothing or request an interval the backend can't serve — scoped out for that reason, the same reasoning already applied to skipping fake capabilities elsewhere in this app (Cross margin mode, the indicator context menu's unsupported items — see [Backtesting and orders](backtesting-and-orders.md) and the indicator legend section above).
- **Favorites persist through the existing `toolSettings` sync**, not a new one-off `localStorage` key or backend column — `toolSettings.timeframeFavorites.list` (an array of value strings, e.g. `['1m','5m','15m','30m','1h','4h']`), read via a `useMemo` in `MarketChart.jsx` (falling back to `DEFAULT_TIMEFRAME_FAVORITES`, exported from `TimeframeSelector.jsx` so the default lives next to the component that defines what it means) and written via the same `saveToolSettingsForType('timeframeFavorites', { list })` helper `chartDisplay` and drawing-tool presets already use — same `/market-tool-settings` endpoint, same local-cache-then-server-sync behavior, no new persistence path introduced. Capped at `MAX_TIMEFRAME_FAVORITES` (10, matching the "`N`/10" counter shown in the grid header) — un-starring is always allowed even at the cap, starring past it is a silent no-op (the star button just does nothing further, since exceeding it clutters the pill row this feature exists to keep compact).
- **The active timeframe always appears in the pill row even if it isn't starred** — otherwise picking a non-favorite from the grid would land on a timeframe with no visible pill highlighted, looking like nothing is selected. `TimeframeSelector` appends it to the displayed list (not the stored `favorites` array) whenever `timeframe` isn't already among the favorites currently supported by this exchange.
- **The grid cell and its star are separate targets, not one control**: clicking anywhere on a cell (a `<div role="button">`, not a real `<button>`, specifically so a real `<button>` — the star — can nest inside it without violating "buttons can't contain interactive content") switches to that timeframe and closes the dropdown; the star toggles favorite status via `event.stopPropagation()` so it never also triggers a timeframe switch. Same split TradingView itself uses.
- **Dismissal is a full-screen invisible backdrop button behind the panel** (`fixed inset-0 z-[99]`, panel at `z-[100]`), not a `document`-level `mousedown` listener — matching the pattern already established for `ReplayPanel.jsx`'s currency-settings popover rather than introducing a third dismissal mechanism into this codebase (`chartContextMenu`/`indicatorContextMenu` use a real listener-based approach instead, since those need Escape/scroll/arrow-key handling this simpler popover doesn't).
- `data-tour="timeframe"` (the workspace tour's target selector) moved from the `<select>` itself onto a wrapping `<div>` around `TimeframeSelector` in the compact layout, since the tour's spotlight needs a stable outer bounding box, not a specific interactive element inside it.

Returning from Replay to Live keeps the last selected Replay price guide and axis label visible while live candles resume. The retained price participates in live-mode autoscaling. Back to Live waits until the complete live candle series has replaced the Replay slice before scrolling to real time and refreshing the scale; this keeps the latest price line aligned with the displayed live candles without requiring a timeframe change. The guide is replaced by the next Replay selection or cleared by the existing market-context reset. Saved chart drawings, including horizontal lines, are not cleared, and the replay checkpoint remains available when Replay is opened again.

Selecting a Replay candle anchors the guide to that candle's close price rather than the pointer's vertical position, so the axis price and horizontal guide match the selected candle. Ready-tool buttons retain the same 36-pixel (`h-9 w-9`) footprint and left position as Replay; each sits centered inside a wider 48-pixel (`w-12`) cell so the compact 8-pixel chevron trigger has room to sit flush against it without visually clipping. The chevron area starts directly after the tool button and has a gray hover background. The rail's outer box uses 2-pixel horizontal padding to preserve as much chart width as possible.

`RailButton` and the tool-group chevron render their hover labels through `RailTooltipPortal` (`ReplayPanel.jsx`), a `createPortal`-into-`document.body` tooltip positioned from `getBoundingClientRect()` via the `useAnchoredTooltip` hook — not the native `title` attribute and not a plain CSS `group-hover` tooltip. The rail's own box has `overflow-x-hidden` (to avoid a stray horizontal scrollbar), so an in-flow tooltip gets silently clipped the moment it renders outside the rail's width; the portal escapes that entirely and floats at `z-[9999]`. Any new rail control that needs a hover label should reuse this pattern rather than `title`.

The rail's absolute offset (`-left-[52px]` on `ReplayPanel`'s wrapper, both the embedded and fullscreen-loading-shield instances in `MarketChart.jsx`) and the chart content wrapper's `ml-[52px]` **must stay numerically equal**. The margin reserves horizontal space for the rail; the rail's negative offset pulls it back into that reserved space so its absolute page position lines up with the chart header's logo box above it. If the rail's own rendered width changes (button size, cell width, padding), both numbers need to move together — moving only one either reopens a gap between the rail and the candles (canvas overlap) or leaves dead space between the rail and the header. The current 52px matches the rail's measured outer width (button + `w-12` cell + rail padding) with zero gap to the canvas.

The right price scale's `layout.fontSize` is `10` on desktop, the only lever available since `lightweight-charts` has no direct max-width option for the price scale — its width is always auto-computed from the widest visible label at the current font size. Below `NARROW_CHART_BREAKPOINT` (480px of *chart* width, i.e. after the rail's 52px is already subtracted — roughly any phone in portrait), it drops to `9` and `formatPriceScaleValue(value, compact)`'s `compact` argument switches to fewer max fraction digits (0/4/6 instead of 2/6/8 for the ≥100 / ≥1 / <1 price tiers) — on a narrow mobile chart the price scale was consuming a disproportionate share of the already-small width (confirmed via a live screenshot: candles reduced to a thin sliver next to a wide number column). This only shortens the *axis* labels; the OHLC legend and order forms keep full precision. `isNarrowChartRef` (a plain ref, not state — this must not trigger a re-render on every resize tick) tracks the current side; it's set at chart-creation time and re-evaluated on every `ResizeObserver` tick (orientation change, sidebar toggle, etc.), which also re-applies `layout.fontSize` but only when the narrow/wide side actually flips (avoids a redundant `applyOptions` call every resize). **Three places now read this ref and must stay in sync if tuned further:** the chart-creation options, the `ResizeObserver` callback, and the theme-`applyOptions` effect (which would otherwise stomp the narrow font size back to a hardcoded `10` on every theme toggle). The `localization.priceFormatter` passed at chart creation is a closure over `isNarrowChartRef` (`(value) => formatPriceScaleValue(value, isNarrowChartRef.current)`), so it reads the *current* ref value on every label redraw without needing to be re-registered.

## Header command buttons: icon-only with anchored tooltips

`ChartHeader.jsx`'s four primary command buttons — the Replay/Live toggle, Alert, Info, and Indicators — are icon-only in both layout variants (compact/fullscreen and full desktop), matching Info's original icon-only look rather than the icon+text the other three used to show. Each carries a hover/focus tooltip built from the shared anchored-portal pattern in `resources/js/Components/Tooltip/AnchoredTooltip.jsx`: a `createPortal`-into-`document.body` label positioned from `getBoundingClientRect()` (`top` at the anchor's vertical center, `left` 8px past its right edge by default), `z-[9999]` by default, no native `title` and no plain CSS `group-hover` tooltip.

That module exports three things, used throughout this file and `ReplayPanel.jsx`/`WatchlistPanel.jsx`/`TimeframeSelector.jsx`: `useAnchoredTooltip(placement, externalAnchorRef)` (the position-tracking hook — `placement` is `'right'` by default, also takes `'left'`/`'top'`/`'bottom'` for anchors near a viewport/popover edge; `externalAnchorRef` lets a caller that already owns a ref for some other reason, e.g. a click-opened panel positioned off the same trigger, reuse it instead of attaching a second `ref` to one DOM node — see `TimeframeSelector.jsx`'s "Select period" chevron), `AnchoredTooltipPortal` (the portal-rendered label, takes an optional `zIndexClass` override), and `IconTooltipButton` (a convenience wrapper for the common "icon-only button + hover label" case — anything that isn't a plain `<button>`, e.g. a color swatch `<input>` or a drag-handle `<header>`, wires the first two primitives manually instead). This used to be copy-pasted independently in four places (`ChartHeader.jsx`, `ReplayPanel.jsx`, `WatchlistPanel.jsx`, `TimeframeSelector.jsx`), each with its own hook/portal names and its own `zIndexClass` default tuned to that file's stacking context; all four now import the shared module instead (see `docs/superpowers/specs/2026-08-23-tooltip-modernization-design.md` for that consolidation, plus every native-`title` tooltip converted to it in the same pass).

`IconTooltipButton`'s hover/focus handlers live on the wrapping `<span>`, not the `<button>` itself, on purpose: Chrome does not dispatch `mouseenter`/`mouseleave` to a disabled `<button>`, so a listener on the button would silently never show a tooltip explaining *why* a disabled action is disabled — e.g. `PositionsPanel.jsx`'s "Close position" button, which must still show its disabled-reason tooltip (`showTooltipWhenDisabled`, default `true`). Manual-wiring call sites that attach their own hover handlers directly to a `<button>` (rather than going through `IconTooltipButton`) and that ever need a tooltip on a *disabled* instance should follow the same span-level pattern.

The same pattern backs the icon-only Star/Bookmark/remove-favorite buttons on each symbol-search result row (see "Symbol search panel layout: tabs and Favorites" below) via `IconTooltipButton` — each row needs an independently-positioned tooltip rather than one shared instance, which the hook naturally gives it since every `IconTooltipButton` instance owns its own. These rows previously used a plain native `title` attribute; that was replaced for visual consistency with the rest of the header.

`WatchlistPanel.jsx` uses the same shared module for its icon-only Edit/Delete-watchlist buttons, the per-row "delete saved symbol" `X` inside the "Add a saved market" `Select`, "Remove all saved symbols", and the per-row "remove from watchlist" `X` — all previously either a native `title` or no hover label at all. **It passes `zIndexClass="z-[10022]"` to every one of them, not the shared default `z-[9999]`**: `WatchlistPanel.jsx` is itself opened from a `z-[130]` popover (`FullscreenChartHeader.jsx`'s "Watchlists" button) whose own react-select menu already portals at `z-[10050]`, and a `document.body` portal's stacking is decided purely by z-index against every other portaled sibling, not by DOM nesting — a tooltip left at the default `9999` would paint *underneath* the `z-[10021]`-and-up popovers/panels used elsewhere in this app (this exact bug shipped once, in the symbol-search row tooltips above, before being caught and fixed). Any future tooltip added to a control that itself lives inside one of those higher-z popovers should pass a matching `zIndexClass`, not rely on the plain-header default.

`ReplayPanel.jsx`'s drawing-tool editor toolbar (the bottom bar with Templates/Color/Line width/Line style/Text style/Drawing settings/Duplicate/Delete/More, all `ToolEditorButton`) used to carry a native `title` plus an optional, non-portaled CSS `group-hover` span (`showTooltip`, only ever passed by the Templates button — every other button in that row had no visible hover label at all, just the native one). `ToolEditorButton` now owns its own `useAnchoredTooltip()`/`AnchoredTooltipPortal` instance from the shared module, same pattern as `RailButton` just above it in this file; `showTooltip` was replaced by an inverted `hideTooltip` (still only used by Templates, to suppress the tooltip while its own presets menu is open). **Gotcha hit and fixed during this conversion:** the row this toolbar lives in is a plain `flex` with several buttons positioned via Tailwind `order-N` passed through `ToolEditorButton`'s `className` prop (some buttons wrapped in their own `<div className="relative order-N">` when they own a dropdown menu, others passing `order-N` straight through). `order` only affects an element's position among *its own parent's* flex children — once the button got wrapped in a tooltip-anchoring `<span>`, the span became the actual flex item and the button's `order-N` (and anything else in `className`, e.g. `rounded-r-lg`) stopped doing anything useful. Fixed by applying `className` to both the wrapping span and the button, not just the button — the layout-affecting classes (`order-N`) take effect via the span, the button's own visual classes (rounded corners, hover colors) keep working exactly as before since it's still the visible element. Any future button that gets wrapped in an anchored-tooltip span for the first time, inside a `flex`/`grid` parent that positions it via a class on that button, needs the same double-application — it's easy to miss since nothing errors, the row just silently renders in the wrong order.

Tooltip copy: the Replay toggle carries the same dynamic text its native `title` used to ("Back to live" while `replayMode` is on, "Start replay" otherwise — unaffected by the `checking-access`/`pick-candle` access states, matching the original `title`'s logic exactly); Alert reads "Create alert"; Info reads "Market information" (unchanged from its previous `title`); Indicators reads "Indicators". These four buttons no longer carry a `title` attribute — doubling it up with the new portal tooltip would show two overlapping labels — `aria-label` now carries that accessibility role instead, the same convention `RailButton` uses. The Replay toggle's tooltip is suppressed while `replayAccessStatus === 'checking-access'` (the button is disabled then), mirroring `RailButton`'s own `{!disabled && <RailTooltipPortal .../>}` guard.

### Info/Indicators panels and the timeframe grid are portaled too, not just their hover tooltips

`FullscreenChartHeader.jsx`'s compact command bar (the "☰ SYMBOL ⌄" mobile toggle) opens `ChartHeader.jsx`'s mobile menu — `absolute ... overflow-y-auto` below the `lg` breakpoint — and on a real phone viewport that menu is narrow (its own flex-wrap row competes for width with the fullscreen header's Watchlists/Enter Position/Exit-fullscreen buttons, confirmed via a live mobile screenshot to be ~207px wide, not the ~380px it looks like it should have). Three popovers used to render as plain `absolute left-0 top-full` children *inside* that narrow, `overflow-y-auto` menu: `TimeframeSelector.jsx`'s "Select period" grid, the Market information popover (`MarketMetadataPopover`), and the Indicators panel. All three got clipped by the menu's own scrollport — visually, the popover's top-left corner was cut off and partially covered by the still-open menu behind it, not fully hidden, which reads as a rendering glitch rather than an obviously-scrolled element.

Fixed the same way as the header tooltips above: each is now `createPortal`-ed into `document.body` and positioned with `position: fixed` from the trigger's own `getBoundingClientRect()`, clamped so it never runs past the right edge of the viewport (`Math.min(Math.max(8, rect.right - width), window.innerWidth - width - 8)`). `TimeframeSelector.jsx` has its own small `useAnchoredGridPosition` hook for this; `ChartHeader.jsx` has a local `useAnchoredPanelTooltip` hook that composes the shared module's `useAnchoredTooltip()` (for the point-anchored hover label's `show()`/`hide()`) with an added `openPanel(width)`/`closePanel()` pair, both reusing the same `anchorRef` rather than adding a second ref to the same button. `infoTooltip` and `indicatorsTooltip` both call `openPanel`/`closePanel` from the buttons' `onClick` handlers (`toggleMarketInfo`/`toggleIndicators`).

**These portaled panels use `z-[10021]` (backdrop, where present, `z-[10020]`), not the surrounding `z-[100]`/`z-[110]`/`z-[150]` this file uses elsewhere.** Once portaled to `document.body`, they become *siblings* of `MarketChart.jsx`'s fullscreen wrapper (`fixed inset-0 z-[9999]`) rather than descendants of it — sibling stacking is decided by z-index alone, so anything left at the old, lower values renders fully correct-looking in the DOM (right size, right position, right content) but paints *underneath* the opaque fullscreen container and is invisible. `10021` mirrors the watchlist-modal portals' `z-[10020]`/`z-[10021]` convention documented in [Dashboard and layouts](dashboard-and-layouts.md) for exactly this reason — any further popover portaled out of the compact mobile menu should clear `9999` by the same margin, not reuse a value that only made sense inside the old containing block. (The "Search all symbols" popover, portaled in a later pass below, follows the same `z-[10021]` convention.)

### The "Search all symbols" popover is portaled too, in both layout variants

It was the fourth `absolute`-positioned popover triggered from inside these `overflow-y-auto` mobile menus, and was missed in the earlier pass documented above — it stayed `absolute left-0 top-full` (compact) / `absolute left-0 right-0 ... sm:w-[28rem]` (full desktop layout's own mobile menu), so it was still clipped by its collapsible's scrollport rather than floating over the chart, showing only a sliver of itself pinned to the container's edge instead of a full popover. Fixed identically to Info/Indicators: `symbolPickerTooltip` (another `useAnchoredTooltip()` instance, shared between both layout variants the same way `infoTooltip`/`indicatorsTooltip` already are) anchors the "Search all symbols" trigger button in both variants, and the popover is `createPortal`-ed to `document.body` at `z-[10021]`.

`openPanel(width, align)` gained a second parameter for this: the Info/Indicators panels anchor from the trigger's *right* edge (`rect.right - width`, since those triggers sit near the right side of the header), but the symbol picker's popover has always opened flush with its trigger's *left* edge — `symbolPickerTooltip.openPanel(compact ? 384 : 448, 'left')` passes `align: 'left'` (default remains `'right'`, so `infoTooltip`/`indicatorsTooltip`'s existing calls are untouched) to anchor from `rect.left` instead. The two widths (384/`w-96` for compact, 448/`w-[28rem]` for the full desktop layout) match what each variant's popover was already sized to before the fix — only its positioning mechanism changed, not its dimensions. `toggleAddOpen()` (replacing the bare `setIsAddOpen((v) => !v)` both buttons used to call directly) is the shared open/close handler that also drives `openPanel`/`closePanel`, mirroring `toggleMarketInfo`/`toggleIndicators`; the popover's own "X" close button and `handleSelectSymbol` still call `setIsAddOpen(false)` directly rather than through the toggle, which is fine since the popover's render guard is `isAddOpen && symbolPickerTooltip.panelPos` — once `isAddOpen` goes false the stale `panelPos` left behind is simply never read until the trigger reopens it.

Both `ChartHeader.jsx` mobile toggle buttons (the "☰ SYMBOL ⌄" one below `lg`, in both the compact/fullscreen variant and the full desktop layout's own `lg:hidden` toggle) used to render `<Menu/>` icon + the current symbol + a chevron. ## Symbol search panel layout: tabs and Favorites

The "search all symbols" panel puts the search input first, then a `MarketCategoryTabs` row (Favorites / Spot / Futures, underline-tab style with a `#2962ff` active indicator — this app's own brand blue, not Binance's yellow-green, for consistency with the rest of the UI), then the result rows — in that order, in both the compact and desktop variants. Rows are two lines: bold symbol on top, muted `EXCHANGE Category` label underneath (the desktop variant used to also show a third `coin_name`/`baseCoin`/`status` line inline with the symbol; that was dropped for row density parity with the compact variant).

**Favorites is a client-side filter layered on top of the existing category-scoped list, not a fourth `marketCategory` value.** Clicking Spot or Futures behaves exactly as before (calls `onCategoryChange`, which drives `MarketChart.jsx`'s `marketCategory` state and re-fetches `availableSymbols` from `/api/market-symbol-options?category=...`). Clicking Favorites leaves `marketCategory` untouched and instead filters `filteredAddSymbolOptions` down to rows whose `exchange:category:SYMBOL` key is in a `favoritedKeys` set built from `savedSymbols.filter(item => item.is_favorite)` (`savedSymbols`, already available via `useWatchlist()` — no new fetch). This means Favorites always shows favorites *within whichever category was last selected* (Spot or Futures); switching Spot ↔ Futures while Favorites is active exits Favorites (`handleCategoryTabChange` resets `showFavoritesOnly` before calling `onCategoryChange`). Empty state reads "No favorites in this market yet" instead of "No symbols found" when nothing in the current category is favorited. Keep any future favorites-like filtering client-side and layered the same way, rather than adding a new value to the `marketCategory` state machine.

**Favoriting is a plain `is_favorite` flag on the saved symbol, entirely independent of watchlist membership** — see `docs/superpowers/specs/2026-08-23-symbol-favorites-design.md` for the full design. This used to be conflated: an earlier version of this panel had Favorites mean "in the active watchlist" and the star icon open the watchlist-picker menu, requiring two clicks (star, then pick a list) to favorite anything. Each row now has two separate icon buttons instead of one:

- **Star** (filled amber/`text-amber-400` when `is_favorite` is true, outline otherwise) — one click, calls `useWatchlist()`'s `toggleFavorite(item, nextValue)` directly. No menu. `toggleFavorite` hits `PUT /market-symbols/favorite`, a self-contained upsert (`MarketDataController::toggleFavoriteSymbol`) that creates the symbol if it isn't saved yet, so favoriting works straight from the Spot/Futures tabs on a symbol that's never been added before. Toasts on success ("Added/Removed {symbol} … favorites.") and on failure.
- **Bookmark** — opens the existing per-list watchlist picker (see the next section below). This is the old star's click behavior, unchanged, just moved to its own icon so it no longer overloads the favorite toggle.

The Favorites tab also gets two removal controls, both scoped to that tab only (they don't render on Spot/Futures):

- A per-row `X` next to Bookmark, confirm()-gated ("Remove {symbol} from favorites?"), calling `toggleFavorite(item, false)`, with a toast on success/failure — same as the Star toggle above (this used to be toast-free, matching `removeSymbolFromWatchlist`'s convention in `WatchlistPanel.jsx`, but was made consistent with the Star's own toast once that was added).
- A "Remove all" `Trash2` button above the result rows, shown whenever the current Favorites view has at least one row, calling `useWatchlist()`'s `removeAllFavorites()` (`DELETE /market-symbols/favorites` → `MarketDataController::clearAllFavorites`) with a toast on success/failure.

**Both are non-destructive by design: neither ever deletes a `market_symbols` row or touches `watchlists`.** `clearAllFavorites` is a bulk `UPDATE ... SET is_favorite = false`, not a delete — this was a deliberate correction during design after the first draft had it hard-delete the underlying saved symbols (mirroring `WatchlistPanel.jsx`'s "Remove all saved symbols"), which would have also pruned them from every watchlist as a side effect. A symbol can be unfavorited, per-row or in bulk, while remaining saved and remaining in any watchlist it was already in.

## Add to watchlist from symbol search

Each search result row has an "add to watchlist" button — a `Bookmark` icon (outline, or filled and colored `#2962ff` when the row's symbol is already in the **active** watchlist specifically, not just any watchlist) next to "Open" — that opens the same small per-list picker menu it always has: click it to see every watchlist name with a checkmark for lists that already contain the symbol, and click any name to add it there. The bookmark's filled/outline state and the picker menu's checkmarks answer two different questions (active-watchlist membership vs. per-list membership) but the click behavior that opens the menu is unchanged. This icon used to be a `Star` and doubled as the favorite toggle before favoriting became its own `is_favorite` flag (see above) — it kept its click behavior and menu verbatim, only the icon and its role changed. `ChartHeader.jsx` gets this data by calling `useWatchlist()` directly (`Context/WatchlistContext.jsx`) — **not** via props threaded through `MarketChart.jsx`'s `chartHeaderProps` bundle, and **not** a `window` CustomEvent either. This changed from an earlier props-based version once the same watchlist data also needed to reach a second, independent render site (the fullscreen-docked `WatchlistPanel` — see [Dashboard and layouts](dashboard-and-layouts.md)); Context is the right tool once more than one distant component needs the same cross-cutting state. `MarketChart.jsx` itself carries no watchlist-related props or state at all now.

The picker menu lists the **active** watchlist (whichever was last clicked in the sidebar, or in the fullscreen panel) first, then the rest — a convenience ordering only, not a restriction; any list can be picked directly. Adding is add-only (clicking an already-checked list is a no-op, matching `addSymbolToWatchlist`'s own duplicate guard) — there's no remove-from-watchlist action here, that stays in the panel. If a symbol isn't saved yet, it's saved first via the chart's own `onAddSymbol` (a separate, unsynchronized `/market-symbols` consumer — see below) before being added to the watchlist; this doesn't need to be awaited since the watchlist key (`exchange:category:SYMBOL`) is computed client-side, not from the save response. Picking a list closes the menu immediately (`handleAddToWatchlist` resets `watchlistMenuOpenKey` to `null`) — it's a single pick per open, not a multi-select session; the menu also resets whenever the search panel itself closes.

**Selecting an unsaved symbol switches the chart immediately; saving it happens in the background.** `ChartHeader.jsx`'s `handleSelectSymbol` always calls `onSymbolChange` (`MarketChart.jsx`'s `handleSymbolChange` — synchronous `setExchange/setMarketCategory/setSymbol`) first, then separately fires `onAddSymbol` (`handleAddSymbol`, the `POST /market-symbols` call) without awaiting it, only when the symbol isn't already saved. This used to be inverted — switching an unsaved symbol *awaited* the save before updating the chart at all, so a slow or failed save left the user staring at the old symbol with no clear feedback. `handleAddSymbol` no longer touches `exchange`/`marketCategory`/`symbol` on success, and its `NProgress` calls were removed — the candle-fetch effect's own `NProgress.start()` (fired the instant the switch happens) already covers loading feedback for the switch itself; a background save failing or lagging must never visibly affect the chart. A `symbolPersistIdRef` generation guard keeps an out-of-order save response from clobbering `symbolError`/`isSavingSymbol` state set by a newer one.

This creates a real hazard for `loadMarketSymbols` (`MarketChart.jsx`, refetches `/market-symbols` on every `symbol`/`exchange`/`marketCategory` change and snaps back to a fallback saved symbol if the current one "doesn't exist" in the response — originally meant to recover from a restored-but-since-deleted symbol on mount): a symbol the user just picked, deliberately, is *by definition* not yet in that list until its background save succeeds, so this validation would otherwise immediately revert the very switch that just happened, every time — worse, more reliably during a fast burst of switching, since each one's `/market-symbols` refetch is unsynchronized against its own save. Guarded with `justSwitchedSymbolKeyRef` (`MarketChart.jsx`): `handleSymbolChange` records the `exchange:category:symbol` key of every deliberate pick (search result or watchlist chip — its only two callers), and `loadMarketSymbols` skips the fallback-correction whenever the *current* active key still matches the *latest* recorded pick. Comparing against the latest pick rather than consuming a one-shot flag is what keeps this correct through a rapid burst: an older, superseded `loadMarketSymbols` call is already discarded by its own `loadSymbolsRequestIdRef` staleness guard before this check even runs, so only the current call's comparison matters.

**`handleAddSymbol` used to send a stale CSRF token on every call after login, found while fixing the above.** It manually read `document.querySelector('meta[name="csrf-token"]')` and sent it as `X-CSRF-TOKEN` — but that `<meta>` tag is only ever set once, in the initial full-page HTML load. `LoginController.php` calls `$request->session()->regenerate()` after login (correct — also rotates the CSRF token as a side effect), and login goes through Inertia's `router.post()` (`Login.jsx`), a client-side SPA visit that never reloads the document or its `<head>`. Every other axios call in this codebase (bar one, next paragraph) skips this manual header entirely and lets axios's built-in mechanism handle it — reading the `XSRF-TOKEN` cookie fresh on *every* request (`bootstrap.js`), which self-heals through token rotation since Laravel reissues that cookie on every response. The manually-set, stale header took precedence over axios's own correct one (Laravel's `VerifyCsrfToken` checks an explicit `X-CSRF-TOKEN` header before falling back to `X-XSRF-TOKEN`), so this call was silently broken for the rest of any session that included a login, until a hard refresh. Fixed by deleting the manual header and letting axios's default handle it, matching every other endpoint.

The `keepalive: true` `pagehide` flush in the replay-progress-persistence effect just above had the identical bug, for the identical reason — it just can't use axios (no `keepalive` support), so the fix there reads the `XSRF-TOKEN` cookie by hand and sends it as `X-XSRF-TOKEN`, replicating what axios does automatically rather than reading the meta tag. Any future raw `fetch()` call that needs a CSRF header (bypassing axios for `keepalive`, streaming, or similar) should follow this same cookie-read pattern, not the meta-tag one.

**Known inconsistency, kept as two copies but now kept in sync**: `MarketChart.jsx` fetches `/market-symbols` into its own local `symbols` state, entirely separate from `WatchlistContext`'s `savedSymbols` (also an independent `/market-symbols` fetch) — two unsynchronized copies of the same server data. `ChartHeader.jsx` used to have its own "remove saved symbol" trash-can button (deleting against `MarketChart.jsx`'s local `symbols` state and dispatching `backtradelab-symbols-changed` itself) sitting right next to the symbol picker; it was removed as a duplicate of `WatchlistPanel`'s own per-symbol delete (`deleteSavedSymbol` in `WatchlistContext.jsx`, which already does the same `DELETE /market-symbols/{id}` call). Deleting a saved symbol now only ever happens through `WatchlistContext.deleteSavedSymbol`, and saving a new one only ever happens through `MarketChart.jsx`'s `handleAddSymbol` — both ends now broadcast `backtradelab-symbols-changed` via `utils/crossTabSync.js` (`broadcastChange`/`subscribeToChange`, a thin wrapper around `window` `CustomEvent` plus a same-name `BroadcastChannel` relay for other tabs), and both `MarketChart.jsx` and `WatchlistContext.jsx` subscribe to it and re-fetch. So an add or delete from either side reaches the other — and any other open browser tab — without a reload, instead of leaving a stale entry until the next full reload. `WatchlistContext`'s `toggleFavorite`/`removeAllFavorites` (see the Favorites section above) broadcast the same event after every `PUT /market-symbols/favorite` / `DELETE /market-symbols/favorites` call, for the same reason — `MarketChart.jsx`'s local `symbols` copy doesn't carry `is_favorite` at all (only `savedSymbols` does, since only `ChartHeader.jsx` needs it), but a symbol favorited for the first time from the Spot/Futures tabs may not exist in either copy yet, and this is what makes both refetch and pick it up. The two states remain genuinely separate copies rather than being consolidated into one source of truth (e.g. `MarketChart.jsx` reading `savedSymbols`/save logic from `useWatchlist()` instead of its own parallel fetch): `MarketChart.jsx`'s symbol state has several already-hardened timing guards around it (`justSwitchedSymbolKeyRef`, `symbolPersistIdRef` — see above) that a state-ownership rewrite would risk disturbing for no behavioral gain over just keeping the two copies in sync.

## Floating header UI closes on outside click

`isAddOpen` (symbol search), `isIndicatorsOpen` (indicator picker), `isMarketInfoOpen`, and `isMobileMenuOpen` (all `ChartHeader.jsx`), plus `isWatchlistPanelOpen` (`FullscreenChartHeader.jsx`), used to have no outside-click dismissal at all — only their own trigger button or picking an item inside them closed them, so clicking the chart while one was open just left it sitting there. This codebase already had a proven pattern for exactly this problem, just not applied consistently: the chart legend's "•••" menu (`MarketChart.jsx`'s `isLegendActive` effect) closes on any `mousedown` that doesn't land inside an element carrying `data-chart-ui="market-legend"`, checked via `event.target.closest(...)`.

Extended the same pattern to the five states above. `ChartHeader.jsx` uses **one combined effect** (not four separate ones) since all four live in that component with identical dismissal semantics — the marker values (`symbol-search`, `indicator-picker`, `market-info`, `mobile-menu`) are OR'd together in a single `closest()` selector. `FullscreenChartHeader.jsx` gets its own small effect, copied verbatim from the legend's single-purpose form, since it's a different component with only one relevant state. Registered `mousedown` listeners are always guarded behind `if (!anyOpen) return undefined`, matching the legend — no listener sits on `document` while nothing is open.

Marker placement had to account for portals: `isAddOpen` and (only in the compact/mobile layout) `isIndicatorsOpen` render their dropdown via `createPortal(..., document.body)`, so the panel isn't a DOM descendant of its trigger button — both need the marker attribute independently, or clicking the trigger to close would itself register as an "outside" click and fight the toggle. Where trigger and panel are inline siblings under one wrapper instead (desktop `isIndicatorsOpen`, both `isMarketInfoOpen` instances, the `isWatchlistPanelOpen` wrapper), marking that one shared wrapper is enough. `isMobileMenuOpen`'s trigger and panel are marked separately rather than via a shared ancestor, since their nearest common ancestor also contains unrelated header controls that shouldn't be swept into the same exclusion.

**`ChartSettingsModal` needed nothing** — its backdrop already has its own `onMouseDown={(event) => event.target === event.currentTarget && onClose()}` (`ChartSettingsModal.jsx:217`), the standard backdrop-click-to-close pattern, and a real backdrop blocks the chart click from reaching through anyway.

**`ReplayPanel.jsx`'s left rail (`activeGroup` state, `toggleGroup()`) is split: the Tools picker got the same fix, Enter Position and Tool Style did not.** Its panels render via a shared `Flyout` component with no outside-click dismissal of its own (just an X button and re-clicking the triggering rail icon) — same underlying gap as the header dropdowns, just a different component.

The **Tools picker** (`activeGroup === 'tools'`, the flat list, and each group's own flyout — `activeGroup === 'tools:${group.name}'`, e.g. Fibonacci) got the identical `data-chart-ui`/`mousedown` treatment: `data-chart-ui="tools-flyout"` on `RailButton`'s optional `dataChartUi` prop (used for the flat-list trigger), on `ToolGroupRailItem`'s chevron button (`ReplayPanel.jsx:222`, opens a specific group's flyout — the group's *main* icon is a separate, unmarked trigger that arms that group's default tool directly via `handleToolChange`, no flyout involved, so it's correctly left unmarked), and on both `Flyout` wrapper divs. The guarding effect lives next to `toggleGroup()` and only attaches while `activeGroup` is `'tools'` or starts with `'tools:'`. This is safe specifically because picking a tool from the flyout (`handleToolChange`) never touches `activeGroup` from that call site — it only sets the separate `tool` state — so closing the flyout on the next chart click doesn't interrupt placing the drawing; only the picker's own visibility is affected, confirmed by drawing a Fibonacci retracement through the full flow (open flyout → pick "Fib Retrace" → two chart clicks to place both anchors → correct retracement levels render, flyout closes on the first of those two clicks with no effect on placement).

**Enter Position** (`activeGroup === 'backtest'`) and **Tool Style/Templates** (`activeGroup === 'tool-editor'`, renders `TopToolEditorBar`, a different kind of surface — not a `Flyout`) were deliberately left alone: Enter Position has its own "click the chart to pick a price" feature, and both are plausibly meant to stay open while referencing the chart. Auto-closing either on chart click risks breaking a real workflow, not fixing a gap — worth revisiting only with a concrete report that it's actually a problem in practice, not by symmetry with the Tools picker.

**`DrawingSettingsDialog`** (`ReplayPanel.jsx`, opened via the "Drawing settings" gear in `TopToolEditorBar` once a drawing is selected — the tabbed Style/Text/Coordinates/Visibility dialog, e.g. for a selected Line or Fib Retracement) **had the same gap `ChartSettingsModal` already avoided**: a real `fixed inset-0` backdrop (`ReplayPanel.jsx:621`) with no click-to-close handler on it at all — unlike its sibling, clicking the backdrop (which is what a click anywhere else on the chart actually lands on, since the backdrop covers the full viewport) did nothing. Fixed with the identical `onMouseDown={(event) => event.target === event.currentTarget && onClose()}` pattern. Its Cancel button already just calls `onClose()` with no side effects (`onApply(draft)` is separate, wired to Ok only), so backdrop-dismiss is exactly equivalent to Cancel — no draft-loss surprise beyond what Cancel already does.

`watchlistMenuOpenKey` (the per-row "add to watchlist" submenu inside the search dropdown) needed no direct change — it already cascades closed whenever `isAddOpen` closes (existing effect, `ChartHeader.jsx:117-119`), so fixing `isAddOpen` fixes it for free.

**Left alone, already correct**: the legend menu itself; the two right-click context menus (`chartContextMenu`, `indicatorContextMenu` — `pointerdown` + ref `.contains()`, a different but already-working mechanism); `TimeframeSelector` and `ReplayPanel`'s template/currency menus (each has its own invisible full-viewport click-catcher button that already self-closes on any outside click); and every full-backdrop modal (`ChartSettingsModal`, `IndicatorSettingsPanel`'s settings dialog, `ReplayPanel`'s save/leverage/exits/TP-SL/order-draft dialogs) — a backdrop already blocks the chart click from reaching through, so there's nothing for this mechanism to do there.

## Chart settings modal

The chart's top-left legend (`ChartMarketLegend` in `MarketChart.jsx`) is plain/unhighlighted until the user clicks precisely on a candle — its body or wick, not empty chart background, gridlines, or an indicator pane. `handleChartClick` (`chart.subscribeClick`, alongside its pre-existing indicator-pane-click logic) checks the click's `param.point.y` against that candle's high/low converted to pixel coordinates via `candleSeries.priceToCoordinate()` (a few pixels of padding for thin wicks); only a hit within that vertical range counts, and `setIsLegendActive(isClickOnCandle)` runs unconditionally on every chart click — a hit turns the highlight on, a miss turns it off, so there's no separate "off" branch to keep in sync. A qualifying click highlights the legend with a bordered box, reveals a "•••" (`MoreHorizontal`) button, and reveals `swingPointMarkers`. The bordered box only wraps `Symbol · Timeframe · Last price {Exchange}` plus the "•••" button — it's a separate inner `<div>` from the outer flex row, so the OHLC/change spans (`showOhlc`/`showChange`) always render as plain unboxed siblings after it, never inside the highlight, regardless of `isActive` — small hollow blue-ring `<circle>`s at significant swing highs/lows across the chart's *currently visible* time range (`chart.timeScale().getVisibleRange()`, not the full loaded history), detected with a ZigZag-style scan: track the running high/low extreme, confirm it as a pivot and flip direction only once price reverses by at least 5% **of the current price level** (`reversalPct`, the standard ZigZag definition), then start tracking the opposite extreme from that same candle. Two things were tried and rejected before landing here — worth knowing if this needs revisiting: a raw local-fractal test ("is this candle more extreme than its 2 neighbors") marks nearly every wiggle, and a threshold based on a *percentage of the visible high-to-low span* looked fine on trending data but collapses in choppy/sideways stretches (the span barely grows while price keeps wandering, so the threshold shrinks to near-nothing and pivots fire almost every candle — confirmed by simulating both against synthetic choppy data before shipping the price-percentage version). The confirming candle's own single-candle range must never be allowed to immediately satisfy the *opposite* direction's threshold in the same loop iteration (a `continue` after each pivot push prevents that) — otherwise a single big-wick candle cascades into a burst of spurious alternating pivots on adjacent candles, which is what produced the tight overlapping clusters seen during earlier testing. Pivots are drawn in `ChartStage.jsx`'s existing trade-marker SVG overlay and recomputed on pan/zoom/new-candle the same way `renderedTradeMarkers` is (via `overlayRenderVersion`). `reversalPct` is a starting default, not a tuned constant — adjust it in the `swingPointMarkers` memo if it needs to surface more or fewer pivots. Clicking "•••" opens `ChartSettingsModal.jsx` — a real modal with left-rail tabs (Symbol, Status line, Scales, Canvas) and Cancel/Ok. The highlight and markers stay visible through mouse movement (click-driven, not hover-driven) and clicking the legend itself (needed so clicking "•••" doesn't dismiss its own target before the click registers — `data-chart-ui="market-legend"` is the exclusion the dismiss listener checks via `event.target.closest(...)`), but a `mousedown` document listener dismisses them on **any other click**, anywhere — chart background off a candle, an indicator pane, `ReplayPanel`, the header, or elsewhere on the page. There is no separate "Style" header button anymore; the legend's "•••" is the only entry point. This app uses `lightweight-charts`, not TradingView's own charting library, so the settings offered are deliberately narrower than a real TradingView dialog — **not implemented, by design**: Bid/Ask price lines (no live bid/ask feed reaches this chart), chart-axis Timezone (the library has no per-chart timezone-shift API; the only timezone setting elsewhere in the app is the unrelated footer clock), Watermark, named Template save/load, and "color bars based on previous close" (would need per-candle color overrides threaded through the whole data-loading pipeline). If any of these get requested again, that's new scope, not a settings-panel afterthought.

**Persistence — reuses `/market-tool-settings`, no new endpoint.** `MarketChart.jsx` already fetches/saves a `toolSettings` blob there for drawing-tool `presets`/`readyTools`, through `getToolSettingsForType(type)`/`saveToolSettingsForType(type, updates)` (immutable merge, PUT the whole blob). The new settings are one more sibling key, `chartDisplay` (defaults in `DEFAULT_CHART_DISPLAY`, deep-merged with whatever's saved via the `chartDisplay` `useMemo`). Candle body color (`candleColors`) stays exactly where it was — its own separate localStorage-only state — the modal just edits it via the same `onCandleColorChange` prop that already existed; only the new border/wick/price-line/status-line/scales/canvas settings are new and go through `chartDisplay`.

**Cancel/Ok is a real staged draft, not per-field live-apply.** Unlike the old dropdown (which applied instantly), `ChartSettingsModal` snapshots `candleColors`/`candleSize`/`chartDisplay` into local state when it opens and only calls `onCandleColorChange`/`onCandleSizeChange`/`onChartDisplayChange` on **Ok**. Cancel (or the backdrop/X) just closes it — nothing was touched. This is a deliberate UX change for candle colors specifically (previously instant), made because they moved into the same dialog as everything else and a dialog with a visible Cancel/Ok button that silently already-applied your edits would be misleading.

**The dialog is draggable by its header.** `ChartSettingsModal` is otherwise still flex-centered by its full-viewport backdrop, but a `dragOffset` state (reset to `{x:0,y:0}` each time it opens, same as the other drafts) is applied as an additional `translate3d()` on top of that centering via inline `style`, so it opens centered and can then be moved anywhere without changing its centering logic. Dragging is Pointer Events (`onPointerDown` on the header, `pointermove`/`pointerup` on `document` for the duration of a drag) rather than the mouse/touch-normalization pattern used for chart drawing gestures elsewhere in this app — this dialog has no existing mouse-only handler to reuse, so Pointer Events (native mouse/touch/pen unification) was the simpler choice for new code. The header click target excludes the close (X) button (`event.target.closest('button')`) so closing still works with a plain click. The panel's own `getBoundingClientRect()` at drag-start is used to clamp the drop position so at least `DRAG_MARGIN` (32px) of the header stays reachable within the viewport on every edge — the modal can be moved out of the way of the chart underneath it, but never dragged fully off-screen.

**Live updates never recreate the chart.** Every setting applies via small dedicated `useEffect`s calling `.applyOptions()`/`.createPriceLine()`/`.removePriceLine()` on the existing `chartRef`/`candleSeriesRef` instances (`MarketChart.jsx`, immediately after the `candleColors` live-update effect this pattern was copied from) — never by adding to the chart-*creation* effect's dependencies, which would destroy and rebuild the whole chart (losing zoom/viewport) on every settings tweak. Follow this same pattern for any future chart-display setting.

- **Candles**: extends the existing `candleColors` effect with `borderVisible`/`wickVisible` and independent up/down colors (falling back to the body color when unset).
- **Price lines**: `last` toggles `priceLineVisible` on the candle series (was always-on before). `previousClose` is the most recently **completed candle's** close from already-loaded history — not a true calendar-day close, which would need a separate daily-resolution fetch this chart doesn't do; say so plainly in the UI, don't imply more. `highLow` uses the min/max of `visibleCandles`. Lines are tracked via refs (`previousClosePriceLineRef`, `highPriceLineRef`, `lowPriceLineRef`) and removed/recreated on change, mirroring the existing `selectedPriceLineRef` pattern for the Replay price marker.
- **Scales**: `logScale` sets `chart.priceScale('right').applyOptions({ mode })` via `lightweight-charts`' `PriceScaleMode`. `precision` overrides the custom `priceFormat` formatter (falls back to the existing `formatPriceScaleValue` when `'default'`). `autoScale` is now an explicit user preference — kept **independent** of the one-off `autoScale: true` reset that already exists for the Replay→Live transition (that reset is intentional/delicate and was left untouched, not folded into this preference).
- **Canvas**: overrides `layout.background`/`grid.vertLines`/`grid.horzLines` on top of the current `chartTheme` values; `null` (the default) falls back to the theme exactly as before — this doesn't replace the dark/light theme system, just layers a per-user override on top.
- **Status line**: `ChartMarketLegend` gets 4 new boolean props (`showSymbol`/`showExchange`/`showOhlc`/`showChange`) gating its existing spans — no new data, it already computed everything it displays.

## Indicator panes (Volume, RSI, MACD)

Volume, RSI, and MACD are all real, separate stacked panes below the main price pane — one `createChart` instance, using `lightweight-charts` v5's native multi-pane API (`chart.addSeries(type, options, paneIndex)`, `series.moveToPane(n)`, `chart.panes()[n].setHeight(px)`). Volume used to be the odd one out: it was overlaid directly on the main pane (pane 0) and visually squeezed into the bottom of it via `priceScale().applyOptions({ scaleMargins: { top: 1 - size, bottom: 0 } })` — a shared-canvas trick, not a real pane, unlike RSI/MACD which already used `moveToPane`. Volume now follows the exact same pattern as RSI/MACD.

All three share one reset-and-reassign effect (the effect keyed on `indicators`, alongside every other indicator's `visible`/color/width `applyOptions` calls): every run first calls `moveToPane(0)` on all of volume/rsi/macd (plus MACD's signal/histogram series), then walks a single `nextLowerPane` counter starting at 1, assigning **volume first, then RSI, then MACD** — each only if currently visible — calling `moveToPane(nextLowerPane)` and `pane.setHeight(...)` (a percentage of `overlaySize.height`, from `indicators.volumeSize`/`rsiSize`/`macdSize`) before incrementing. This ordering (volume → RSI → MACD) is a convention, not a technical requirement — if it ever needs to change, it must change in every place that assumes it, all of which duplicate the same "reserve pane 1 for volume if visible" counting logic and must be kept in lockstep:

- The reset-and-reassign effect itself (pane assignment + height).
- `handleChartClick`'s manual hit-testing (`volumePane`/`rsiPane`/`macdPane` computed from `indicatorsRef.current`) — used to detect a click on the volume histogram or MACD histogram, which (being histograms, not lines) can't use the simple line-distance-to-cursor test the other indicators use.
- `indicatorPaneTops` (the `useMemo` that positions each pane's persistent clickable label badge, rendered by `IndicatorClickTargets` in `IndicatorSettingsPanel.jsx`) — walks the same volume-then-RSI-then-MACD order to compute each visible pane's top Y offset from `chart.panes()[n].getHeight()`.

**A pane's `setHeight()` doesn't reliably stick right after `moveToPane()` creates it** — observed live (repeated fresh page loads of the same workspace): on some loads the volume pane ends up at `0px` with the main price pane stretched to fill the gap, on others it correctly lands at its configured size, with no code difference between the two — a genuine timing race, not a logic bug. Separately, the *other* `ResizeObserver` (on `containerRef`, a few lines above the chart-creation code) calls `chart.applyOptions({ height })` on every container resize, which can silently reset per-pane heights back to an even split — undoing whatever the indicators effect just set. The fix has two parts: (1) the reset-and-reassign effect now builds its `moveToPane`/`setHeight` calls as a list of deferred jobs (`paneHeightJobs`) applied synchronously, again on the next animation frame, and then once more every 150ms for ~1.2s (a short self-healing watchdog, since a single fixed retry delay wasn't reliable — this was tuned empirically against repeated live reproductions, not by formula); (2) that same job list is stashed in `applyIndicatorPaneHeightsRef` so the container `ResizeObserver`'s callback can re-run it immediately after its own `applyOptions({ height })`, closing the gap between the two effects fighting over pane height. If pane heights are ever seen drifting again, reproduce with several consecutive full page loads (not just one) before concluding a fix worked — the failure is intermittent, not consistent. **Known limitation:** this fix measurably reduced the failure rate (from roughly half of loads to roughly a third, tested via repeated live loads) but did not fully eliminate it — a residual trigger, likely tied to the live-market WebSocket connecting shortly after mount, wasn't pinned down and would need live DevTools tracing (breakpoints in the reset-and-reassign effect and the container `ResizeObserver` callback) to find, not further headless retesting.

The pane separator line (`layout.panes.separatorColor` in the chart-creation options) and the `IndicatorClickTargets` pane-label pills (Volume/RSI/MACD, `buttonClass` in `IndicatorSettingsPanel.jsx`) are deliberately subtle — low-alpha `rgba()` for the separator (not `chartTheme.border` directly, which read as too solid/bright against the pane background) and a partially-transparent background with no drop shadow for the labels, tuned down from an original ~90% opacity in two rounds based on live visual feedback (first too solid, then too faint, settled at a middle value). If tuning either further, check both dark and light theme variants — the separator color branches on `chartTheme.mode`.

Toggling any indicator off calls `moveToPane(0)` on it (a no-op pane visually, since it's also set `visible: false`) and closes the gap for the ones below it, since the counter just skips hidden indicators rather than leaving empty slots. `INDICATOR_META.volume` in `IndicatorSettingsPanel.jsx` only has a `sizeKey` (`volumeSize`) — no `periodKey`/`colorKey`/`widthKey` — since volume has no configurable period or line color, just Pane size / Show-Hide / Remove.

### Indicator legend, context menu, and settings dialog

Interacting with an indicator is a two-step flow, mirroring TradingView's own: clicking never jumps straight to the settings dialog by itself — it only reveals the legend row's icon toolbar (or, if already revealed, hides it again). From there, the gear icon (or "···" → Settings...) is what actually opens settings. This is deliberate, not incidental: a stray click while just looking at an indicator's line shouldn't pop a full dialog over the chart.

- **`expandedIndicator`** (`MarketChart.jsx` state) tracks which indicator's legend toolbar is pinned open. It's set two ways — clicking the indicator's plotted line (canvas hit-test in `handleChartClick`, distance-to-cursor against each visible series) or clicking its on-chart label pill directly (`IndicatorLegendRow`'s `expand` action) — and cleared by clicking empty chart space, activating a drawing tool, selecting a drawing, or the indicator being removed. It is entirely independent of `selectedIndicator` (which controls the settings dialog) — expanding the toolbar never opens the dialog, and opening the dialog (from the header's indicator menu, for instance) doesn't require the toolbar to have been expanded first.
- **`IndicatorLegendRow`** (`IndicatorSettingsPanel.jsx`) still shows just a colored dot + label at rest. Its icon row — Eye (instant show/hide), a gear (opens settings), a trash can (instant remove), and "···" (opens the same menu right-click does) — appears either on hover (`group`/`group-hover`, no JS hover state needed) *or* whenever `expandedIndicator === thisKey`, so it stays visible after a click even once the mouse moves away, not just transiently on hover. SMA/EMA pills stay rendered-but-faded (`opacity-50`) while hidden, since they overlay the always-present main pane and have somewhere to anchor either way; Volume/RSI/MACD pills still disappear entirely while hidden, unchanged from before — their only anchor point (`indicatorPaneTops[key]`) doesn't exist once their pane collapses, so there's nowhere left to render a faded pill for them.
- **`IndicatorContextMenu`** (new) opens on right-click of the legend row or its "···" button — either way, regardless of whether the toolbar is currently expanded — and separately from `chartContextMenu` (the price-anchored menu for Set Alarm/Trigger Position/Clear Tools/Reset Chart/Chart Settings — a different menu, different state, different trigger). It has exactly three items: **Hide/Show**, **Settings...**, **Remove**. TradingView's real indicator context menu also has "Add to favorites," "Visual order," "Visibility on intervals," "Move to," "Pin to scale," "Copy," and "Object Tree..." — none of those map to anything this engine supports (no favorites list, no z-ordering between indicators, no per-interval visibility, no alternate pane assignment, no left-scale pinning, no multiple instances of one indicator type to copy, no object browser), so they were deliberately left out rather than built as non-functional menu items — the same reasoning already applied to the Cross/Isolated margin-mode toggle in the order ticket (see [Backtesting and orders](backtesting-and-orders.md)). Its open/close lifecycle (`indicatorContextMenu` state, outside-click/Escape/scroll/resize dismissal, arrow-key roving focus between `role="menuitem"` buttons) is a second, independent copy of the exact same pattern `chartContextMenu` already uses — not shared, since the two menus have unrelated trigger points and content.
- **The settings dialog itself is a centered, tabbed modal** (`fixed inset-0 ... items-center justify-center`), not a small popover anchored to wherever the triggering click landed — `indicatorSettingsPosition` (the state that used to track that anchor point) was removed entirely; there's nothing left to anchor since the dialog no longer moves with the click. Three tabs — **Inputs** (the period, or MACD's Fast/Slow/Signal trio; "Volume has no configurable inputs" for volume), **Style** (line color/width, MACD's four series colors, and pane height for the three paneable indicators), **Visibility** (a single Show/Hide checkbox — this app has no per-timeframe visibility concept, so unlike TradingView's real Visibility tab, this one only ever holds that one real toggle, not a set of fake interval checkboxes). Edits are staged in local `draft` state (seeded fresh via `buildDraft()` each time a *different* indicator's dialog opens, deliberately not re-seeded while the same one stays open — see the comment in `IndicatorSettingsPanel`) and only committed to the real `indicators` state on **Ok**; **Cancel** (or the X) discards the draft untouched. **Defaults** resets the draft's fields (not the live indicator) to `INDICATOR_DEFAULTS[key]`, staying open for further tweaks before Ok — it does not immediately apply, matching Cancel/Ok's own staged semantics. The old inline **Remove** button was dropped from inside the dialog entirely (matching where TradingView actually puts it — legend/context-menu only, never inside Settings); removing now only happens via the legend row's trash icon or the context menu's Remove item, both of which act on the live indicator immediately, no confirmation (consistent with how deleting a single drawing elsewhere in this app also doesn't confirm — only the bulk "Clear Tools" action does).

**Scrolling an indicator pane's own price axis zooms that pane's own value range**, independent of the main chart. `handlePriceScaleWheel` (`MarketChart.jsx`, mount effect) used to always operate on pane 0 / `candleSeriesRef` regardless of which pane's y-coordinate the cursor was actually over; it now walks the live `chart.panes()` heights to find which pane the cursor's y falls in, then uses `findSeriesForPane(paneIndex)` (matches `paneIndex` against `candleSeriesRef`/`volumeSeriesRef`/`rsiSeriesRef`/`macdSeriesRef`/etc. via each series' own `series.getPane().paneIndex()` — not the volume→RSI→MACD ordering convention documented above, so it stays correct even if that ordering ever changes) to get the right series for `coordinateToPrice`. The zoom math itself (anchor-price-under-cursor, `zoomFactor` 0.85/1.15, `setVisibleRange`) is unchanged, just scoped to `chart.priceScale('right', paneIndex)` and the cursor's y relative to that pane's own top (`paneLocalY = y - paneTop`) instead of the whole container. Pane height itself is unaffected by scrolling — resizing a pane's pixel height is still drag-the-separator only (`layout.panes.enableResize`).

## Right price scale width

The right price scale's rendered width is auto-computed by `lightweight-charts` from its widest visible label (across every pane sharing that scale — main + volume + any indicator panes), plus fixed padding; there's no direct "set width" API, so the only lever is keeping label content short.

- **`formatPriceScaleValue(value, compact)`** (module scope) already had narrow-screen logic (fewer fraction digits once the chart container is under `NARROW_CHART_BREAKPOINT` = 480px), but both call sites that wire it into the candlestick series' `priceFormat.formatter` (initial series creation, and the `chartDisplay.scales.precision === 'default'` re-apply effect) passed the function directly instead of `(value) => formatPriceScaleValue(value, isNarrowChartRef.current)` — so `compact` was always `false` regardless of screen width, and this was dead code. Fixed at both call sites. Desktop is unaffected (chart width stays well above the breakpoint); narrow/mobile charts now show whole-number prices instead of full decimal precision on the highlighted last-price badge and any non-round tick.
- **The volume series used `priceFormat: { type: 'volume' }`**, `lightweight-charts`' built-in formatter, which does not abbreviate large values — a 7-8 digit volume renders as literal digits. Since the price-scale width is shared across panes, an unabbreviated volume axis can be wider than the price axis and become the actual bottleneck. Replaced with `priceFormat: { type: 'custom', minMove: 1, formatter: formatCompactVolume }` — a module-scope helper that abbreviates with K/M/B suffixes, trims trailing zeros correctly (`1.60K` → `1.6K`), and re-tiers on rounding overflow (`999950` → `1M`, not `1000K`). Applies in every mode, not just narrow screens.
- **A stale "Replay" price line could stretch the price scale across a symbol switch.** `selectedReplayPriceRef.current` (a raw price *level*, e.g. a BTC-range value) used to be reused unconditionally as `previousSelectedReplayPrice` whenever `wasInReplay` was true, in the big candle-reload effect (`fetchKlines`, keyed on `[exchange, marketCategory, symbol, timeframe, ...]`). That effect runs on every symbol change too, not just timeframe changes — so switching symbols while replay mode was active carried the *old* symbol's raw price forward and plotted it as the new chart's dashed "Replay" price line (e.g. a ~68000-level BTC price rendered on an ETH chart trading near ~3700). `lightweight-charts` autoscales the price scale to fit every visible price line, so the axis stretched to cover both the real candle range and the stray far-off value, squashing the actual candles into a thin sliver and forcing wide, round-number tick labels (`80000`...`-20000`) — this was the real driver behind width complaints, not just formatting. Fixed by gating the reuse on `isTimeframeTransition` (an existing ref-backed flag, set only by `handleTimeframeChange`, that's already used to distinguish a same-symbol timeframe change from any other candle reload): `previousSelectedReplayPrice` is now `null` unless `isTimeframeTransition` is true, so a real symbol change falls through to the existing fallback (`complete[nextReplayIndex]?.close` — the new symbol's own nearby candle price) instead of carrying a foreign price forward. The `shouldRestoreSavedReplay` path (resuming a saved session) was already correct — `replayProgressKey` is per-symbol, so `savedReplayProgress?.selected_price` was never at risk of crossing symbols.

## Candle fetch rate limiting

`GET /api/klines` is throttled per user/IP via the `market-klines` limiter (`app/Providers/RouteServiceProvider.php`): live-tick polling (`?fresh=1`) and full history loads (no `fresh` param — symbol/timeframe/category changes, entering Replay) both allow 30/min. These two request shapes use **separate rate-limit bucket keys** (`{identity}:fresh` vs `{identity}:history`) — they must stay separate. Sharing one key was the original bug: routine live polling could exhaust the shared counter well within its own budget, then the next history/Replay-start request got rejected with 429 even though it hadn't made any requests itself yet, producing an intermittent "Too Many Attempts" error when opening Replay. If you add another `fresh`-style parameter to this endpoint, give it its own bucket suffix rather than folding it into an existing one. History was 10/min until it turned out that was tight enough to trip during ordinary watchlist-scanning (10+ symbol switches inside a minute is normal trading behavior, not abuse); raised to match `fresh`'s 30/min since the real anti-abuse layer against hammering exchange APIs is `ExchangeMarketDataGateway`'s own per-exchange budgets/cooldowns/backoff, one level down from this per-user limiter.

`fetchCandles` (`MarketChart.jsx`) retries once automatically on a 429, waiting up to 3s (capped — never the server's full `Retry-After`, which reports the whole remaining per-minute window and can be tens of seconds) before retrying. The cap matters: a longer wait would usually lose the race to the chart's own 30s overall failsafe timeout (`Promise.race` a few lines up), which fires a generic "taking longer than expected" message instead of this endpoint's accurate one. If the capped retry also fails, the chart shows "Chart data is temporarily rate-limited. Please wait a moment and try again." instead of Laravel's raw `Too Many Attempts.` message or the generic timeout text.

**Symbol/timeframe switching used to always wait on a saved-replay-progress round trip before fetching any candles at all, even when that data could never matter for the fetch about to run.** The candle-fetch effect's very first line was `if (replayProgressLoadedKey !== replayProgressKey) return;` — `replayProgressKey` is `` `${exchange}:${marketCategory}:${symbol}` ``, so every symbol change reset `replayProgressLoadedKey` to `null` (a separate effect, keyed the same way) and the candle fetch simply didn't run at all until `GET /market-replay-progress` resolved for the new key. There is no distinct loading indicator for this gap, so a symbol switch made while already in Replay (the common case reported: picking a fresh, never-charted symbol from search while scrubbed into Replay) looked like it silently did nothing — and once the progress call finally resolved and the real fetch started, an unfamiliar symbol requesting `max_candles=20000` could then run long enough on Replay's page-count budget to hit the 60s failsafe above, surfacing as "Chart data is taking longer than expected to load." The guard is now `if (!replayMode && replayProgressLoadedKey !== replayProgressKey) return;` — a switch made while already in Replay fetches candles immediately instead of waiting; only the "just arrived on this symbol from Live mode, might need to auto-resume a bookmark" path still waits for the fresh progress row.

**Replay no longer carries over from one market to the next just because the market you switched away from happened to be mid-replay — it's per-market now, gated on that specific market's own saved checkpoint.** Before this, `wasInReplay` was simply `replayMode || shouldRestoreSavedReplay`, and `shouldRestoreSavedReplay` (the "does *this* exchange/category/symbol have a real `market_replay_progress` row" check) explicitly required `!replayMode` — so it was only ever consulted when returning to a market from Live. While already replaying, switching to *any* symbol — including one genuinely never opened before — kept `wasInReplay` true purely from the stale `replayMode` flag, landing the new chart on whatever candle happened to sit nearest the old symbol's replay timestamp (or, failing that, the same proportional position through history). Reported as: brand-new symbols "having a record of Replay" they'd never actually earned.

Fixed by keying the whole decision off whether this is a genuine market change or merely a timeframe change on the same market (`isSymbolChange = !isTimeframeTransition`, the same flag `isTimeframeTransition` already tracked for cache/loading purposes just above). A timeframe change keeps whatever mode was already active, unchanged from before (`wasInReplay = replayMode || shouldRestoreSavedReplay` when `!isSymbolChange`). A genuine market change ignores the old `replayMode` value entirely — `wasInReplay = shouldRestoreSavedReplay` only, and `shouldRestoreSavedReplay`'s `!replayMode` requirement is now `isSymbolChange || !replayMode`, so the *new* market's own checkpoint is checked regardless of whether the market being left was mid-replay.

This interacts with the bypass above in a deliberate two-pass way for the common "switching while replaying" case: the first effect run fires before `replayProgressLoadedKey` has caught up to the new key, so `hasFreshCheckpointForKey` is false and the fetch goes out Live-shaped (fast, small, immediately visible — `setReplayMode(false)` fires as soon as it resolves). Once the real progress row for the new market arrives a moment later, the effect's dependencies change and it reruns: if that market turns out to have its own saved checkpoint, this second pass computes `wasInReplay = true`, promotes back into Replay at the saved point, and issues the real Replay-shaped fetch (parallelized per the section above) — a brief Live-then-Replay flash, but only in the case a checkpoint actually exists. The far more common case (no checkpoint for the new market) resolves on the first pass and this second run's candle fetch is served straight from `candleCacheRef`/the persisted cache (same cache key, no `end` anchor either time) with only a harmless background revalidation — the same stale-while-revalidate behavior every other cache hit already gets, not new cost introduced by this fix.

`handleVisibleRangeChange` (the `chart.timeScale().subscribeVisibleLogicalRangeChange` callback that bumps `overlayRenderVersion` to keep the SVG drawing overlay pixel-synced with the canvas during pan/zoom) wraps its `flushSync` call in `queueMicrotask`. `lightweight-charts` can invoke this callback synchronously — including from inside the chart-creation `useEffect` itself, when the initial visible range is set — and calling `flushSync` synchronously from inside React's own render/commit (more likely to actually surface under `React.StrictMode`'s double-invoked effects, which this app has enabled in `app.jsx`) triggers React's "flushSync was called from inside a lifecycle method" warning. Deferring to a microtask moves the call outside that stack; it still lands before the next paint, so there is no visible lag reintroduced. If this warning reappears elsewhere, the same pattern (not a plain `setTimeout`, which would wait for the *next* paint and reintroduce a frame of lag) is the fix.

**The right price scale's own drag-to-zoom gesture needed the identical fix, on a separate path — and needed it applied more robustly than a per-event handler.** Only the time scale exposes a subscription (`subscribeVisibleLogicalRangeChange`) for programmatic pan/zoom changes; `lightweight-charts` has no equivalent event for the price scale (confirmed against its own type definitions — no `subscribePriceScaleChange` or similar exists). Dragging it vertically is handled entirely inside the library, invisible to React; the canvas just repaints as part of the browser's own mouse handling.

The first attempt reused `handleViewportInteraction`, a generic `wheel`/`mousemove`/`mouseup`/`mouseleave` listener on `containerRef.current`, changed to do the same `cancelAnimationFrame` + `queueMicrotask(() => flushSync(...))` sequence as `handleVisibleRangeChange`. This did **not** fully resolve it live — reacting to individual native `mousemove` events is inherently best-effort: nothing guarantees every mousemove fired during a fast drag reaches a bubble-phase container listener in step with the library's own internal per-pixel canvas updates, so the overlay could still fall a frame behind and visibly wiggle on some drags even with `flushSync` in place once it did fire.

The actual fix decouples the overlay's sync cadence from counting on any particular native event arriving at all: `handleViewportDragStart`/`handleViewportDragEnd` (`mousedown`+`pointerdown` on the container, `mouseup`+`pointerup` on `window` — window-level so a release outside the container while dragging still ends it, both event models registered since nothing guarantees which one a given internal `lightweight-charts` gesture dispatches through, and `isViewportDraggingRef` naturally coalesces a duplicate start if both fire) drive a dedicated `requestAnimationFrame` loop (`stepViewportDragOverlay`, tracked via `isViewportDraggingRef`/`viewportDragFrameRef`) that calls `flushSync(() => setOverlayRenderVersion(...))` on **every** animation frame for the entire drag span, regardless of which internal gesture is happening or how many intermediate move events fire. This guarantees a real-frame sync no matter how the library internally throttles or batches its own pointer handling. The loop only starts when `!isSpacePressedRef.current && toolRef.current` is false (i.e. panning/scaling is actually possible) — matching the same condition `handleScroll`/`handleScale` already use — since a mousedown-drag with an active drawing tool means "draw a shape," not "move the viewport," and would otherwise run the loop for no reason. `handleViewportInteraction`'s own `mousemove` handling now short-circuits (`if (isViewportDraggingRef.current) return;`) whenever the frame loop is already running, so the two mechanisms don't do redundant work during an active drag; it still exists for the discrete, non-continuous triggers (`wheel`, and `mouseup`/`mouseleave` as a defensive final sync) where per-event handling is sufficient. `scheduleOverlayRender()` (plain rAF, no `flushSync`) remains correct for the many other, non-drag-continuous triggers elsewhere (symbol/theme/indicator changes, etc.) where a frame of slack is imperceptible — this pattern is specifically for a mouse-held-down, per-frame-continuous viewport change with no subscription event to hook.

**Indicator panes needed a second iteration.** `mainPaneHeight` and `indicatorPaneTops` (the `useMemo`s that position `IndicatorClickTargets`' Volume/RSI/MACD pane-label pills, reading `chart.panes()[n].getHeight()`) both already depend on `overlayRenderVersion`, so the same per-frame bump that keeps the main pane's drawings/order-lines/trade-markers synced was always going to keep these pills tracking their pane's actual top offset live during a resize drag too, once the loop actually starts. But indicator panes have two drag gestures the main pane doesn't — each pane's own right price scale, and `layout.panes.enableResize`'s divider between stacked panes (the "↕" resize-cursor strip between e.g. the main pane and Volume) — and registering `mousedown`/`pointerdown` on `containerRef.current` (the first attempt) did not reliably catch the start of either live, even though every pane renders inside that same root element. The specific reason wasn't conclusively isolated (a plausible culprit: `lightweight-charts` may attach the divider's own hit-target handling in a way that doesn't cleanly bubble a container-scoped listener, e.g. pointer capture on a nested internal element), so rather than keep chasing which exact DOM node needed a listener, `handleWindowViewportDragStart`/`handleViewportDragEnd` now listen on `window` for both event models, gated by `isPointInContainer()` (a plain `getBoundingClientRect()` bounds check against the pointer's `clientX`/`clientY`) so a click anywhere else on the page is still correctly ignored. A window-level listener sees the event regardless of which descendant it targets or how the library internally handles capture, sidestepping the bubbling question entirely instead of continuing to guess at it.

# Interactive workspace tour

First-time workspace users receive a spotlight tour of the actual market, timeframe, drawing, replay, simulated-position, and appearance controls. The highlighted control remains usable, while the rest of the page is blocked. The tour supports keyboard navigation, responsive/fullscreen repositioning, missing-target fallback, and restart via Help or the chart help button. `?tour=1` explicitly restarts it without clearing completion history.

`Pages/Help/Index.jsx` (`/help`, linked from the trader sidebar) is a static, theme-aware walkthrough page — the same eight steps as the tour, written out in beginner-friendly prose (each jargon term like margin, leverage, or PnL is defined inline) plus a glossary section and a "Contact support" link to `/feedback`. Its "Restart workspace tour" button links to `/workspace?tour=1`. It has no backend of its own; keep its step copy and CTAs (`/market`, `/workspace`, `/trade-report`) in sync if the real controls or routes it describes change.

This workspace spotlight tour is the first of two product tours sharing the same `WorkspaceTour.jsx` engine — see [Trade reports and journals](trade-reports-and-journals.md) for the second, on `/trade-report`. Each owns its own completion flag; they never share one. This one is gated by the nullable `chart_tour_completed_at` timestamp on `adm_users`, set by `POST /chart-tour/complete` (`ReplayAccessController::completeTour`) the first time the user finishes or skips it. There is intentionally no separate tour on the post-login `/market` landing page (`Pages/Market/Market.jsx`) — a modal "Getting started" tour used to fire there immediately after login and shared this same completion flag, which meant it consumed the flag before the user ever reached the real workspace tour. It was removed; do not reintroduce a tour trigger outside the workspace, or it will race this one for the same flag again.

`WorkspaceTour.jsx` itself is generic — a `step`/`steps`/`onStep`/`onFinish`/`dark` component with no chart-specific coupling, spotlighting whatever DOM node matches each step's plain CSS `selector` (conventionally a `data-tour="..."` attribute placed on the real control) via `getBoundingClientRect()`, scrolling it into view, and re-measuring on resize/scroll/fullscreen-change. A missing selector degrades to a centered dialog with an inline notice instead of erroring. Reuse it directly for any future tour rather than forking it — the two existing tours differ only in their `steps` array and completion endpoint, never in the engine.

`MarketChart.jsx` is mounted with `key={chartKey}` in `Dashboard.jsx` and fully remounts whenever the active symbol changes. Its tour-completed flag is therefore owned by the parent `Dashboard.jsx` (`chartTourCompleted` state, seeded from `auth.user.chart_tour_completed_at`) rather than re-read from the Inertia `auth` prop on every mount, which can be stale mid-session (a plain `axios.post` does not refresh Inertia's shared props). `Dashboard.jsx` passes `tourCompleted`/`onTourComplete` down; `MarketChart.jsx`'s `finishTour` calls `onTourComplete()` synchronously so a symbol change immediately after finishing the tour cannot re-trigger it.
